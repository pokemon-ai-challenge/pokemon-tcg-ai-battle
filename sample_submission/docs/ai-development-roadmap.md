# ポケモンカードAI：段階的な開発方針

このファイルは、提出用AIを「とりあえず選択できる状態」から、デッキ固有の戦術・盤面評価・探索まで段階的に強化していくための方針メモです。

提出方法や `main.py`、`deck.csv`、`cg/` の基本的な使い方は、提出フォルダ直下の `README.md` を参照してください。

この文書は、README の補足ではなく、**実装の優先順位と設計判断を揃えるための作業用ロードマップ**として使います。

---

## この文書の前提

このロードマップでは、AI の強さを単なる人間レベルの呼び方で区切るのではなく、**実装範囲と評価方法が分かる段階**として整理します。

各レベルは、次の3点で定義します。

- 何ができるか
- 何をまだやらないか
- どの評価を通ったら次へ進むか

また、現在の開発段階は、まだ「初心者AIを育てる段階」よりも前です。  
まず必要なのは、**合法かつ意図した選択を安定して返せる土台を作ること**です。

その前提で、全体像は次のように捉えます。

```text
Level 0: 正しく選べる
Level 1: 一般的なポケカを最低限プレイできる
Level 2: 1つのデッキを目的通りに回せる
Level 3: 盤面・確率・サイドを評価してプレイできる
Level 4: 複数手先を探索して最適な順番を選べる
Level 5: 相手のデッキ分布と大量自己対戦から改善できる
```

---

## このドキュメントの使い方

- README は「提出物の入口」
- このファイルは「何をどの順で実装するか」
- `main.py` は当面「提出用の薄い入口兼試作場所」
- `cg/` はゲームエンジンなので変更しない

チェックボックスは、概念整理のためではなく、**実際に手を動かすときの確認用**として使います。  
そのため、この文書では主に `Level 0` と `Level 1` の実装・完了条件にだけチェックボックスを入れます。

---

## 現在地

現行コードでは、`choose_main_action` の優先順位判定が `for` ループの中にあります。  
そのため、選択肢全体を分類し終える前に最初の候補で `return` してしまい、「エネルギー > 進化 > 特性 > 攻撃」という比較をまだ正しくできていません。

また、メイン以外の選択は先頭候補を返す処理が多く、次のような場面で戦略的な判断ができていません。

- 初手のバトルポケモン選択
- ベンチ選択
- サーチ対象選択
- 進化元選択
- 付け先選択
- 捨て札選択
- 入れ替え先選択
- 攻撃選択

したがって、いま最優先で作るべきものは「強いAI」ではなく、**選択コンテキストごとに意味のある合法手を返す構造**です。

---

# Level 0：合法・再現可能なエージェント

これは「初心者AI」の前段階です。

## 目標

どの選択コンテキストが来ても、少なくとも意味のある合法手を返し、なぜその手を選んだか確認できる状態にします。

`Observation` には盤面・ログ・選択肢があり、`SelectData` の `context`、`effect`、`contextCard` を使って「今どのカード効果の、何を選ぶ場面か」を判定できます。

## この段階で作るもの

### 1. 選択ルーター

まず、`SelectContext` ごとに処理を振り分けます。

```text
MAIN
SETUP_ACTIVE_POKEMON
SETUP_BENCH_POKEMON
TO_BENCH
TO_HAND
EVOLVES_FROM
EVOLVES_TO
ATTACH_FROM
ATTACH_TO
SWITCH
DISCARD
ATTACK
```

イメージは次のような形です。

```python
def choose_action(obs: Observation) -> list[int]:
    context = obs.select.context

    if context == SelectContext.MAIN:
        return choose_main_action(obs)
    if context == SelectContext.SETUP_ACTIVE_POKEMON:
        return choose_setup_active(obs)
    if context == SelectContext.SETUP_BENCH_POKEMON:
        return choose_setup_bench(obs)
    if context in {SelectContext.ATTACH_FROM, SelectContext.ATTACH_TO}:
        return choose_attach_target(obs)

    return choose_default_legal_action(obs)
```

最初から全コンテキストを賢くする必要はありません。  
ただし、「何の選択か分からないので先頭を返す」という状態からは抜けます。

### 2. カード情報辞書

`all_card_data()` と `all_attack()` から、次の辞書を作ります。

```text
card_id -> CardData
attack_id -> Attack
```

これにより、候補番号だけでなく、意味として扱えるようになります。

```text
- どのカードを出すか
- ポケモン・グッズ・サポート・エネルギーのどれか
- どのポケモンにエネルギーを付けるか
- どの攻撃を使うか
- その攻撃に必要なエネルギーやダメージはいくつか
```

### 3. DecisionTrace

毎回、少なくとも次のようなログを残します。

```text
turn=3
context=MAIN
candidates=[
  PLAY:ネストボール,
  ATTACH:炎エネルギー→リザード,
  ATTACK:ヒートタックル,
  END
]
selected=ATTACH:炎エネルギー→リザード
reason=main_attacker_energy_progress
```

これがないと、負けた理由が「戦略が悪かった」のか「選択バグだった」のかを切り分けられません。

### 4. シナリオテスト

実戦勝率だけでなく、固定盤面での正答テストを作ります。

例:

```text
- 初手にメインアタッカーと壁役がいる
  -> メインアタッカーをバトル場に置く

- 進化元が2体いる
  -> 育てるべき方を進化させる

- 1エネで相手を倒せる攻撃がある
  -> その攻撃を選ぶ

- サーチ対象がある
  -> 現在の目的に合うカードを取る

- 不要札をトラッシュする効果がある
  -> 重要カードを捨てない
```

## Level 0 の実装チェックリスト

- [ ] `choose_main_action` で分類処理と優先順位判断を分離する
- [ ] `OptionType` / `SelectContext` を数値比較ではなく Enum で扱う
- [ ] `SelectContext` ごとのルーターを作る
- [ ] カード辞書と攻撃辞書を用意する
- [ ] `DecisionTrace` を残せるようにする
- [ ] 主要コンテキストの固定シナリオテストを用意する

## Level 0 の完了条件

- [ ] ランダムな先頭候補選択が主要な選択処理に残っていない
- [ ] 固定シナリオで意図したカードを選べる
- [ ] 対戦中に不正選択・例外・無意味な先頭選択が起きない
- [ ] 選択理由をログから確認できる

# Level 1：初心者AI

## 目的

一人で最低限ポケカを回せる状態にします。

## できること

- 初手で最低限妥当なバトルポケモン・ベンチポケモンを選ぶ
- エネルギーを「今後攻撃する予定のポケモン」に付ける
- 進化可能なら、育てる価値のあるポケモンを進化させる
- ベンチを埋めるべきときに展開する
- 攻撃できるなら、基本的には最大ダメージまたはきぜつを取れる攻撃を選ぶ
- 攻撃対象・ダメカン対象・回復対象を最低限正しく選ぶ
- 明らかに損な行動を避ける

## まだやらないこと

- 相手のデッキ推定
- 複数手先の本格探索
- サイドプランの詳細計算
- 山札確率の厳密計算
- 複雑な妨害札の最適タイミング判断

## 初心者AIの基本方針

この段階では、まだ盤面全体の深い読みはしません。  
まずは次のようなルールベースで十分です。

```text
1. 今ターンに取れるきぜつがあるか
2. 次ターンに攻撃できるポケモンを育てられるか
3. メインアタッカーにエネルギーを付けられるか
4. 進化・展開で盤面が強くなるか
5. 手札を増やす・必要札を探す行動があるか
6. 攻撃する
7. END
```

ただし、これを全デッキ共通の完全固定順序にしすぎないことが重要です。  
Level 2 以降で、デッキ固有の例外や盤面評価を追加します。

## Level 1 の実装チェックリスト

- [ ] 初手のバトルポケモン選択基準を決める
- [ ] ベンチ展開の優先順位を決める
- [ ] エネルギーの付け先基準を決める
- [ ] 進化先・進化元の基準を決める
- [ ] 攻撃選択の基準を決める
- [ ] 基本的なサーチ・捨て札選択を実装する

## Level 1 の完了条件

- [ ] ランダムAIには安定して勝ち越せる
- [ ] 単純優先AIより勝率が高い
- [ ] 固定盤面テストで基本行動の正答率が高い
- [ ] 明らかにおかしい負け方がログからほぼ消える

---

# Level 2：中級者AI

## 目的

特定デッキの勝ち筋を理解し、そのデッキ固有の回し方ができるようにします。

## この段階の中心

カードごとに大量の `if` 文を書くことではなく、**デッキごとの方針を `DeckPlan` に寄せること**が中心です。

```python
DeckPlan(
    main_attackers=[...],
    sub_attackers=[...],
    setup_pokemon=[...],
    draw_support_pokemon=[...],
    pivot_pokemon=[...],
    energy_priority=[...],
    evolution_priority=[...],
    search_priority=[...],
    supporter_priority=[...],
    win_conditions=[...],
    recovery_rules=[...],
)
```

## 例として持たせる内容

```text
- メインアタッカーは誰か
- 序盤にベンチへ置きたいポケモンは誰か
- 最優先で進化させたいポケモンは誰か
- エネルギーは誰に何枚付けるか
- 逃げエネ0の入れ替え要員は誰か
- サーチで最初に探すべきカードは何か
- サポート権を使う価値が高いタイミングはいつか
- 盤面が崩れたときの復帰ルートは何か
- サイド残り枚数ごとの勝ち筋は何か
```

## デッキ状態の例

```text
SETUP
  ベンチ展開・進化元確保・メインアタッカー準備

ATTACK_READY
  毎ターン攻撃できる状態を作る

PRESSURE
  サイドを取り続けて押し切る

RECOVERY
  メインアタッカーが倒された後の立て直し

CLOSING
  残りサイドから勝利までの最短ルートを取る
```

## Level 2 の終了条件

- 1つの選んだデッキで想定した基本展開にかなりの頻度で到達できる
- エネルギー・進化・サーチの判断に一貫した理由がある
- 同一デッキで初心者AIより明確に勝率が高い
- デッキ変更時にロジック全体ではなく `DeckPlan` を中心に変更できる

---

# Level 3：上級者AI

## 目的

盤面評価を使って、そのターンの行動順を判断できるようにします。

## この段階の中心

PDF で扱っている内容は、主に次の3つに分けて実装します。

```text
1. 行動順序の最適化
2. 盤面評価・確率・リソース管理
3. サイドレース・妨害・相手の要求値の評価
```

## 評価関数の例

```text
評価値 =
  サイドレース価値
+ 次ターンの攻撃継続性
+ 盤面完成度
+ 手札の質
+ 山札内の到達確率
+ 相手への圧力
- 相手に取られるサイド価値
- 盤面崩壊リスク
- 重要リソース消費
```

## 具体的に評価するもの

```text
- 今ターンに何枚サイドを取れるか
- 次ターンも攻撃できるか
- 倒された後の次のアタッカーが準備できているか
- 自分が取られるサイドは1枚か2枚か3枚か
- ベンチに置いたポケモンは狙われる価値があるか
- ボス系・サポート系・入れ替え札を使い切っていないか
- 山札に必要カードが残っているか
- 山札から引くよりサーチした方がよいか
- サーチ後に引きたくない札を残していないか
```

## Level 3 の終了条件

- サポートを「使えるから使う」ではなく盤面状況で使い分けられる
- 山札・トラッシュ・公開情報を数えて重要札の残りを推定できる
- サイド枚数から攻撃ルートを考えられる
- 妨害カードを効果が高い局面で使える
- 中級者AIに対して同じデッキでも勝率差が出る

---

# Level 4：ハイレベルAI

## 目的

複数手先を見て、行動順まで比較できるようにします。

## 方針

いきなり全探索や大規模な MCTS はしません。  
まずは評価関数で候補を絞ってから、短い探索を入れます。

```text
1. ルールベースで候補を作る
2. 評価関数で上位3〜5候補に絞る
3. その候補だけを短い深さで探索する
4. 最も評価の高い行動列の最初の1手を選ぶ
```

## 初期設定の例

```text
幅: 5
深さ: 4〜8アクション
対象: まずは自分のターン終了まで
```

## 不確実情報の扱い

```text
世界A: 相手がボスを持っている
世界B: 相手がボスを引けない
世界C: 相手がサーチ札を多く残している
```

複数の仮説で探索し、平均評価や最悪ケース評価で行動を選びます。

## Level 4 の終了条件

- 行動順を変えた結果の差を比較できる
- 自分のターン終わりまでの複数行動列を評価できる
- 見えていない相手札を決め打ちしない
- 探索ありのAIが探索なしの上級者AIより明確に強い

---

# Level 5：超ハイレベルAI

## 目的

環境・相手デッキ・対戦データを利用して自己改善できるようにします。

## 5-A：相手デッキ推定

公開情報から相手のデッキ候補を確率分布で持ちます。

```text
ドラパルト型: 55%
リザードン型: 25%
その他炎デッキ: 20%
```

評価関数に入れる対象の例:

```text
- 相手がボスを持っている確率
- ベンチ狙撃が可能な確率
- 妨害札が残っている確率
- 次ターンに必要パーツを揃える確率
```

環境情報は、提出時にネットアクセスするのではなく、事前収集したローカル知識ベースとして扱う設計が安全です。

## 5-B：自己対戦による改善

```text
1. 複数デッキ・複数シードで自己対戦
2. 対戦ログを保存
3. 負け局面を分類
4. 評価関数やDeckPlanの候補を生成
5. 固定ベンチマークで比較
6. 改善したものだけ採用
```

## Level 5 の終了条件

- 相手の公開情報からデッキ候補を絞れる
- デッキ候補ごとに警戒行動を変えられる
- 自己対戦ログを使って改善候補を比較できる
- 改善前後を固定ベンチマークと自己対戦の両方で比較できる

---

# 実装の順番

今の状況からは、次の順番で進めるのがよいです。

## 1. `choose_main_action` を直す

```text
- 分類処理と優先順位判断を分ける
- for ループの外で優先順位を評価する
- 数値の 7, 8, 9 ではなく OptionType.PLAY のような Enum を使う
- select.context == 0 ではなく SelectContext.MAIN を使う
```

## 2. `SelectContext` ごとの処理を作る

優先順位は以下です。

```text
SETUP_ACTIVE_POKEMON
SETUP_BENCH_POKEMON
TO_BENCH
ATTACH_FROM / ATTACH_TO
EVOLVES_FROM / EVOLVES_TO
TO_HAND
DISCARD
SWITCH
ATTACK
```

## 3. カード情報と盤面情報を意味化する

```text
- これは手札の何番目か
- カード名は何か
- ポケモンか、サポートか、エネルギーか
- どのポケモンに付くか
- 何ダメージの攻撃か
```

## 4. 1デッキ限定の `DeckPlan` を作る

```text
- 育てるポケモン
- エネルギーの付け先
- サーチ優先順位
- 勝ち筋
- 立て直し方
```

## 5. 初心者AIを完成させる

ランダムAI・単純優先AI・旧版AIと対戦させ、改善を確認します。

## 6. 盤面評価関数を導入する

この段階で、PDF の「行動順序」「山札圧縮」「要求値」「サイドレース」を入れます。

## 7. 最後に探索APIを使う

評価関数が弱いまま探索をしても、「悪い評価を大量に計算するだけ」になります。  
先に中級〜上級のルールベース・評価関数を作り、その後に `search_begin` / `search_step` を使って複数手先比較へ進みます。

# コード構成案

`main.py` にすべて書き続けると、上級以降で管理しにくくなります。  
ただし、**Kaggle 提出用の入口はあくまで `main.py`** です。  
そのため、構成を分ける場合も `main.py` を残し、その下でロジックを `src/` に分離する形が自然です。

```text
sample_submission/
├─ main.py                  # Kaggle提出用の入口。agent(obs_dict) をここに置く
├─ deck.csv
├─ cg/
├─ src/
│  ├─ knowledge/
│  │  ├─ card_database.py   # CardData / Attack の辞書
│  │  ├─ card_tags.py       # ドロー、サーチ、妨害、進化などの意味タグ
│  │  └─ deck_plan.py       # デッキ固有の方針
│  ├─ decision/
│  │  ├─ router.py          # SelectContextごとの振り分け
│  │  ├─ setup_policy.py    # 初手・ベンチ選択
│  │  ├─ main_policy.py     # MAIN時の候補生成
│  │  ├─ target_policy.py   # サーチ、捨て札、進化元など
│  │  ├─ evaluator.py       # 盤面評価
│  │  └─ search_policy.py   # 複数手先探索
│  ├─ tests/
│  │  ├─ scenarios/         # 固定盤面テスト
│  │  └─ replay_tests.py
│  └─ evaluation/
│     ├─ self_play.py
│     └─ benchmark.py
└─ docs/
   └─ ai-development-roadmap.md
```

特に大事なのは、`main.py` を「提出用の薄い入口」として残し、`agent(obs_dict)` から内部ロジックを `src/decision/` や `src/knowledge/` に委譲することです。

---

# 提出境界

提出時に必須なのは、少なくとも次です。

```text
main.py
deck.csv
cg/
```

`docs/`、`tests/`、`evaluation/` は開発用です。  
ただし、将来的に `main.py` から `src/` を import する構成にした場合は、提出アーカイブにも実行に必要な `src/` を含める必要があります。

# 次に進めるべき作業

次に進めるべき作業は、Level 0〜Level 1 で必要な `SelectContext` の優先順位と、それぞれで何を基準に選ぶかを表にして確定することです。

そこが決まれば、現在の `main.py` を初心者AIとして成立する構造に直せます。
