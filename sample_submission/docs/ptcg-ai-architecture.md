## 1. 行動順序の最適化

**コアコンセプト:** 「不確定→確定」の順序でアクションを組む。ドロー（不確定）の前にサーチ（確定）を使い切る。

### 1-1. ドロー前サーチの基本順序

- **PDF の主張:** サーチカードを全て使い終えた後、山札を圧縮した状態でドローを行うと当たり確率が最大化される
- **現実装:** `choose_main_action` の優先順: `evolve > attach > play > ability > attack`
  - `play` の中では `SUPPORTER(25) > ITEM(20) > TOOL(15) > STADIUM(10) > POKEMON(5)` の順
  - サーチ系カード（アイテム）がサポーターより後に来る点は改善の余地あり
- **実装箇所:** `src/decision/main_policy.py:_pick_best_play()`

### 1-2. 例外処理：キーカード底沈時の空打ち → シャッフル → ドロー

- **PDF の主張:** 相手の手札干渉後など、キーカードが山札の底に沈んでいると推測される場合、
  サーチカードを「対象なし」で空打ちして山札をシャッフルしてからドローに移行する
- **現実装:** **未実装**。空打ちロジックなし
- **必要な実装:**
  - 直前ターンに相手が手札干渉（イオナ等）を使ったかをログから検知
  - 検知した場合に `choose_main_action` でサーチ系アイテムを「先に」使う優先度を上げる
  - `TO_HAND` / `DISCARD` context で「対象なし（minCount=0 の時は 0 枚選択）」を許容する

### 1-3. 確率のリアルタイム計算（ドロー最適タイミング）

- **PDF の主張:** ドロー実行前に「当たり札を引く確率」を算出し、確率が最大化されたタイミングでのみドローを実行する
- **現実装:** **未実装**
- **必要な実装:**
  - `deck_count` と残り必要カード枚数（トラッシュ・場から推定）から確率計算
  - ドローアクションのスコアに確率を反映（evaluator への組み込み候補）

### 1-4. 不要札の早期消費

- **PDF の主張:** 序盤用カード（ポフィン等）は終盤のドローのノイズになるため早急に消費する
- **現実装:** `deck_plan.py` に `do_not_discard_ids` はあるが「早期消費の強制」ロジックはない
- **必要な実装:** `DeckPlan` に `early_consume_ids: list[int]` フィールドを追加し、ターン数が閾値以下なら優先してプレイする

## 2. 確率とリスク管理

**コアコンセプト:** 勝ち筋の最大化より「負け筋の排除」。評価関数は自分の攻撃力より「相手の要求値」を高く保つ行動を優先する。

### 2-1. 要求値（Opponent's Requirement）

- **PDF の主張:** 評価関数の主軸を「相手が突破に必要な手札枚数（要求値）」に置く。
  ハイリスクなオーバーキルを狙うより「相手に特定カードを引かれなければ次のターンが来る」盤面を優先。
- **現実装:** `evaluator.py` は自陣スコア中心（side_lead・attack_ready・evolution_progress 等）。
  要求値に相当する指標は `prize_risk_score` のみで不十分。
- **必要な実装:**
  ```
  要求値スコア =
    相手アクティブを KO するために相手が必要なエネルギー枚数
    + 相手がボスを使わなければ自分の主要アタッカーを狙えないか（非EX壁）
    + 相手の手札から「今ターン完結する攻撃」が成立しにくいか
  ```
- **実装箇所（予定）:** `src/decision/evaluator.py` に `opponent_requirement_score()` メソッド追加

### 2-2. リソース残量の確率推定

- **PDF の主張:** 相手のトラッシュ・サイド（公開分）・盤面をスキャンし、
  「ボスの指令が相手デッキに何枚残っているか」を確率的に計算して行動決定に利用する
- **現実装:** `opponent_model.py` は公開カードIDを蓄積するが、
  特定カード（ボスの指令等）の残り枚数推定は行っていない
- **必要な実装:**
  - `OpponentModel` に `estimate_remaining(card_id: int) -> float` メソッドを追加
  - `revealed` リスト内の `card_id` 出現数と `meta_decks` のレシピ枚数から `(レシピ枚数 - 使用確認枚数)` を計算
  - `choose_main_action` でこのスコアを参照してリスク判断に使用

## 3. サイドレースと妨害

**コアコンセプト:** 相手のサイドプランを強要・拒否し、妨害札を最も効くタイミングで使う。

### 3-1. 壁役の配置

- **PDF の主張:** 非EX（サイド1枚）のポケモンをバトル場に出し、相手の攻撃回数を3回→4回に強制。
  相手が「2-2-2」で勝つ最短ルートを「1-2-2-2」等に変える。
- **現実装:** Crustle 対面向けの `crustle_swap_to_non_ex` はあるが、汎用的な壁役戦略ではない。
  `MatchupPolicy` に `wall_strategy: bool` フィールドはなく、他アーキタイプへの展開不可。
- **必要な実装:**
  - `MatchupOverride` に `use_wall: bool` フィールド追加
  - `main_policy.py` の `choose_main_action` に汎用壁役ロジックを追加
    （非EXアタッカーがベンチにいて、相手のサイドプランが「2-2-2」と推定されるとき、
    非EXをアクティブに出す判断を組み込む）

### 3-2. テンポアドバンテージ

- **PDF の主張:** サイドを1枚取らせる代わりに相手のリソース（ボスの指令等）を空打ちさせ、
  逆転の起点となるターンを作り出す。
- **現実装:** **未実装**
- **必要な実装:** 要求値スコア（2-1）と組み合わせて「サイドを渡しても相手リソースを消耗させる価値がある」局面を評価する

### 3-3. 妨害札（手札干渉）の「撃ちどき」

- **PDF の主張:**
  - **効果が薄い時（使用禁止）:** 相手の手札が少なく、ドローさせると逆に助けてしまうタイミング
  - **効果が高い時（最優先）:** 相手がサーチカードを多用し、「次のターンの準備」を完了させた直後
  - **ログ分析モジュール:** 直前ターンの相手の行動ログを分析し、手札の「質」を推測する
- **現実装:** イオナ（ID要確認）は `play_options` で `CardType.SUPPORTER` として処理されるだけ。
  使用タイミングの最適化ロジックなし。
- **必要な実装:**
  - `OpponentModel` に `estimate_hand_quality() -> float` メソッドを追加
    - 前ターン相手がサーチカードを何枚使ったかを `obs.logs` から推定
    - 相手の手札枚数（`opp.handCount`）と組み合わせてスコア化
  - `_pick_best_play` でイオナ等の手札干渉カードに `hand_quality_score` を掛け合わせて
    「今使うべき」かどうかをスコア化

## 4. 状態の遅延評価

**コアコンセプト:** 選択肢をギリギリまで保持する。
ポケモンが倒された時、すぐに最適アタッカーを出すのではなく、
「逃げエネ0のポケモンを一時的に出して→ドロー・サーチを全て終わらせてから→最適アタッカーに交代」する。

### 4-1. 逃げエネ0ポケモンの「前出し」戦略

- **PDF の主張:** 自分のポケモンが倒された時、まず「逃げるエネルギーが0」のポケモンをバトル場に出し、
  盤面の確定を保留する（バッファとして活用）。
  ドロー・サーチの処理を全て終え、最終的な手札と盤面が確定した「一番最後に」最適なアタッカーに交代させる。
- **現実装:** `choose_switch` / `TO_ACTIVE` context は即座に `energy_priority` で最終アタッカーを選ぶ。
  逃げエネ0を経由する Lazy Evaluation の概念なし。
- **必要な実装:**
  - `DeckPlan` に `free_retreat_ids: list[int]`（逃げエネ0ポケモンのID）を追加
  - `choose_switch` で「まだメインターン行動が残っている場合は `free_retreat_ids` を優先して出す」ロジックを追加
  - `main_policy.py` の終盤（attack / end の直前）で「逃げエネ0が今アクティブ + ベンチに攻撃準備完了アタッカーがいる」
    なら retreat して交代するロジックを追加

### 4-2. 実装上の注意点

- 逃げエネ0ポケモンが攻撃準備完了であれば前出しせずそのまま攻撃する（前出しはバッファ目的のみ）
- `SelectContext.TO_ACTIVE`（強制アクティブ）と `SelectContext.SWITCH`（任意交代）は
  現在 `choose_switch` で統一されているため、コンテキストを区別した処理が必要になる場合がある
