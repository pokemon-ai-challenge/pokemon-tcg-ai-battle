# 実装計画: 山札切れ＝回し方(piloting)の決定レベル診断

作成: 2026-07-21
状態: 実装計画
前提: 診断フェーズ Step1/Step4（[diag summary](../../../results/2026-07-21_diag_summary.md)）で「value網は山札切れに盲目」「山札切れは負けの25.9%」が確定。**ただし本計画は Step4 の"デッキ構築問題"という読みを訂正する（下記）。**
対象ブランチ: `experiment/pimc-hidden-info-integration`

---

## 前提の訂正（重要）

診断 Step4 は山札切れを「デッキ構築（サーチ密度25%）＋試合長期化」の構造問題と読んだ。しかし**現行 deck.csv は Kaggle 上位のデッキをそのまま持ってきたもの**（ユーザー情報）。上位プレイヤーが同じリストで26%も山札切れしないなら、**デッキ構築は冤罪で、犯人はそのデッキの「回し方(piloting)」**である。

この訂正で Step4 のデータはむしろ piloting 説を支持する:
- **山札切れ負けは試合が+47%長い（17.9 vs 12.2ターン）** ＝ AIが詰め切れず試合を長引かせ、山が尽きる前に勝てていない。これが最大の手がかり。
- **ターンあたり余剰ドローは+6%しかない** ＝ 「引きすぎ」ではない。遅い試合運びの結果として山が尽きている。
- **サーチ札25%** は上位デッキで実証済みなら「良い回し方で管理できるアーキタイプの特徴」であって欠陥ではない。

**帰結: 山札切れ対策の本筋は deck.csv 変更ではなく、AIの回し方の改善。** 本計画はその「回し方の何が悪いか」を決定レベルで特定する。

## 意思決定経路の事実（修正対象の特定）

本番 `ml_policy` の意思決定は **PolicyModel（模倣）＋ lethal_simple（終盤の確定リーサル）** が担い、**value網は shadow で意思決定に使われていない**。よって山札切れの修正対象は value網ではなく、**PolicyModel か、狙い撃ちのヒューリスティック**。加えて lethal_simple はサイド2〜3枚の終盤しか発火しないので、山札切れが起きる「長い中盤」は PolicyModel の領域。本計画はどちらを直すべきかを診断で決める。

## スコープ

**やること**: 山札切れ負けの試合を決定レベルで追い、AIが上位プレイヤーと違う具体的な誤りを特定する。「回復/山札戻し札を使えていない」のか「詰めが遅い」のか、あるいは両方か。

**やらないこと（Non-goals）**:
- 修正の実装（PolicyModel改修・ヒューリスティック追加）→ 本診断の結果で routing してから別フェーズ
- `deck.csv` の変更 → 前提（デッキは上位のもの＝無罪）に反する。かつ共有提出物なので勝手に触らない
- value網の山札切れ対応 → value網は本番の意思決定経路に無いため後回し（[[project_pimc_prod_validation]]）
- 足場固め（インフラ切り出し・統合）→ ユーザー判断で保留継続
- 探索（PIMC）関連 → 診断フェーズ Step2 の完了を待つが、本計画とは独立

## 事前確認済みの契約（Contracts）

### 1. リプレイの決定レベル解析

- `kaggle_replays/replays/episode-*.json`。`steps[i][p]["observation"]["current"]` が各プレイヤー視点の盤面 dict（`turn`, `result`, `players[].deckCount`, 自分側は `players[me].hand`（中身可視）, `prize` 等）、`steps[i][p]["action"]` がその手で選んだ選択。
- 既存パターン: `kaggle_replays/_analyze_missed_lethal.py`（読み取り専用の診断スクリプトの雛形。`_common.fetch_episodes`、`to_observation_class`、`TEAM_NAME`/`SUBMISSION_ID` フィルタ）。
- 勝敗は `rewards`（勝ち側が正）。自チーム名でのフィルタ、ミラー除外は README（`sample_submission/README.md`）記載の通り。
- 標本: 診断 Step4 で使った自チーム363試合（win162/loss201、山札切れ52件）を再利用。必要なら `fetch_my_episodes.py` で追加取得。

### 2. デッキとカード効果

- `sample_submission/deck.csv`（60枚のカードID）。`data/EN_Card_Data.csv` / `cg.api.all_card_data()` でカード名・効果。
- 分類対象: (i) サーチ/ドロー（山札消費）、(ii) 回復/山札戻し/リソース循環（山札維持＝sustain）、(iii) アタッカー/wincon。

### 3. 修正対象の切り分け先

- 「回復札を使えていない」or「詰めが遅い」→ それが PolicyModel の模倣漏れなのか、狙い撃ちヒューリスティックで足せるのかを Step4 で routing する。

## ステップ

### Step 1: デッキの山札切れ関連カードの棚卸し

- `deck.csv` ＋ カード効果を読み、60枚を (i)サーチ/ドロー (ii)回復/山札戻し/循環(sustain) (iii)アタッカー/wincon に分類。**特に sustain 機構（山札に戻す・デッキを増やす・過剰ドローを抑える札や特性）を具体的に特定**する。
- 完了条件: `results/2026-07-21_diag_deckout_deck_inventory.md` に3分類と、「良い回し方なら山札維持に使うべき札」の明示リスト。これが Step3 の「使えているか」の判定基準になる。

### Step 2: 「デッキは無罪」の裏取り（同デッキの上位プレイヤーの山札切れ率）

- 上位リプレイのうち同アーキタイプ（フーディン/Alakazam）を回している試合を特定し、その**山札切れ率**を測る。自チームの25.9%より明確に低ければ、「デッキ構築ではなく回し方が犯人」が確定する。
- 同デッキの上位試合が識別困難な場合はその旨を限界として明記し、ユーザー前提（上位デッキ＝構築は健全）を採用する。
- 完了条件: `results/2026-07-21_diag_deckout_topplayer_rate.md` に上位側の山札切れ率と、piloting説の裏取り可否。

### Step 3: 自チーム山札切れ負けの決定レベル・トレース

- 山札切れ負け52試合を1試合ずつ追い、2軸で定量化:
  - **(a) sustain札の未活用**: Step1で特定した回復/山札戻し札が「手札にあったのに使わずに山を削ったターン」の頻度。上位が使う場面で使えているか。
  - **(b) 詰めの遅さ**: サイド取得のペース（1サイドあたりターン数）、毎ターン攻撃できているか、盤面展開の遅延。非山札切れ負け・勝ち試合と比較。
- 完了条件: `results/2026-07-21_diag_deckout_decision_trace.md` に (a)(b) の定量結果と、「主因は sustain未活用 / 詰めの遅さ / 両方」の判定。

### Step 4: 統合と修正のルーティング

- Step1-3 を集約し、修正対象を証拠で決める:

| 決定レベル診断 | 主因 | 修正対象（次フェーズ） |
|---|---|---|
| sustain札が手札にあるのに使われていない | 回復札の未活用 | PolicyModel が模倣漏れ → 学習で補うか、狙い撃ちヒューリスティック（薄い山札で回復札を優先） |
| サイド取得が遅く試合が長引く | 詰めの遅さ | 中盤の攻め/展開判断 → PolicyModel の課題（lethal範囲外）。closing を促す評価/ヒューリスティック |
| 両方 | 複合 | 上記の組み合わせ。優先度は定量結果で決める |

- 完了条件: `results/2026-07-21_diag_deckout_routing.md` に、修正対象（PolicyModel or ヒューリスティック）と根拠。

## Definition of Done

- [ ] デッキの sustain/サーチ/wincon カードを棚卸しし、維持に使うべき札を明示
- [ ] 同デッキ上位プレイヤーの山札切れ率を測り、「回し方が犯人」を裏取り（or 限界明記）
- [ ] 自チーム山札切れ負けを決定レベルで追い、sustain未活用と詰めの遅さを定量化
- [ ] 修正対象（PolicyModel or 狙い撃ちヒューリスティック）を証拠でルーティング
- [ ] （明示的にやらないこと: 修正実装・deck.csv変更・value網対応・足場固め）

この診断が終われば、山札切れという実戦の主要敗因（25.9%）に対して、感覚でなく「AIが具体的に何を誤っているか」に基づいた修正を、正しい対象（PolicyModel か ヒューリスティック）に打てる。修正本体はその結果を見て別ファイルで計画する。
