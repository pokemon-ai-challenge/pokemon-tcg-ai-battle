# 実装計画: 実戦敗因の網羅的分類（loss taxonomy）

作成: 2026-07-21
状態: 実装計画
前提: 山札切れ診断は完了・クローズ（構造的コストとして許容、[[project_deckout_loss_cause]]）。PIMC/hidden info はミラー本番で null（[[project_pimc_prod_validation]]）。
対象ブランチ: `experiment/pimc-hidden-info-integration`

---

## この計画の目的

これまで**1つの敗因（山札切れ25.9%）だけを深掘り**し、構造的コストとして許容という結論に至った。しかし**残り約74%の負けは未分類**のまま。個別仮説の深掘り（探索・山札切れ）が null か「許容」に着地し続けた反省から、一歩引いて**実戦の負け全体を分類し、"最大の直せる敗因"を特定する地図を作る**。

これにより、次の大投資（PolicyModel改善／非ミラーでの相手モデリング検証／現状維持）を、成り行きや勘ではなく「**どこで一番負けているか**」という証拠で選べるようにする。

**重要な性質**: この分析対象は**実Kaggleの多様な相手との負け**であり、これまでの PIMC/本番検証がすべて**ミラー自己対戦**だったのと本質的に異なる。**初めて非ミラーの実戦敗因を体系的に見る**ことになる。

---

## スコープ

**やること**: 自チームの実戦負け（既存データセットで201試合）を、検出可能かつ行動可能なカテゴリに網羅的に分類し、相手アーキタイプ・接戦/大差とクロス集計して、最大の"直せる"敗因とその対処レバーを特定する。

**やらないこと（Non-goals）**:
- 修正の実装（PolicyModel改修・ヒューリスティック・deck.csv変更）→ 本分類の結果で routing してから別フェーズ
- 探索/PIMC のさらなる作り込み → ミラーで出尽くしたため本計画では扱わない（Step2の完了も本計画とは独立・低優先）
- 非ミラー対戦harness（`match_context` の deck.csv ハードコード修正）→ これは**本分類が「マッチアップ偏り」を示した場合の次の投資候補**。先に安い分類で必要性を判断する
- 足場固め（インフラ切り出し・統合）→ ユーザー判断で保留継続

読み取り専用の分析に徹する。

## 事前確認済みの契約（Contracts）

### 1. リプレイ解析（山札切れ診断と同じ基盤）

- `kaggle_replays/replays/episode-*.json`。`steps[i][p]["observation"]["current"]`（`turn`/`result`/`players[].deckCount`/`players[me].active`/`bench`/`prize`/`hand` 等）、`steps[i][p]["action"]`、勝敗は `rewards`、相手は `info.TeamNames`。
- 既存パターン: `kaggle_replays/_analyze_missed_lethal.py`、`_common.fetch_episodes`、`index/episodes_master.jsonl`。ミラー除外は `sample_submission/README.md` 記載の通り。

### 2. 再利用するデータセット

- 山札切れ診断で使った**自チーム363試合（win=162, loss=201）**をそのまま使う（[classification](../../../results/2026-07-21_diag_deckout_classification.md)）。**山札切れ52件は既に判定済み**なので、残り149件の分類に集中できる。必要なら `fetch_my_episodes.py` で標本追加。

### 3. 相手アーキタイプの事後同定

- 実戦の**事後分析**なので、相手が試合を通じて公開したカード（プレイ・トラッシュ・場）を集約して同定するのが最も確実。既存の `ptcg_ai/opponent_modeling`（hybrid predictor、21アーキタイプ、[[project_ml_deck_predictor]]）を最終観測カードに適用するか、`data/EN_Card_Data.csv` とメタデッキ照合でクラス分けする。

## ステップ

### Step 1: 敗因タクソノミ（分類定義と検出ルール）

負けを相互排他（優先順位つき）のカテゴリに定義し、リプレイ状態から検出するヒューリスティックを設計する。たたき台:

| カテゴリ | 検出の目安 | 想定レバー |
|---|---|---|
| (1) 山札切れ | 判定済み（自ターン開始でドロー不能） | 構造的・許容済み |
| (2) サイドレース負け・接戦 | 相手がサイド6枚完了、最終サイド差が小さい・試合が標準的長さ | PolicyModel の中盤テンポ/攻め |
| (3) サイドレース負け・大差(アグロ) | 相手が速いターンでサイド完走、序盤から一方的 | 序盤の受け・マリガン耐性・デッキ相性 |
| (4) ベンチ壊滅 | active/bench が全滅し出すポケモンが無い | 展開判断・ベンチ保護（n=28で2件observed） |
| (5) 序盤事故 | 一定ターンまで盤面が育たず崩れた | マリガン・初動の安定性 |
| (6) timeout/error | エラー・時間切れ・不正手 | 実装健全性（ほぼ0のはず、要確認） |
| (7) その他/分類不能 | 上記に当てはまらない | — |

- 完了条件: `results/2026-07-21_loss_taxonomy_definitions.md` に各カテゴリの検出ルールと、相互排他/優先順位の規約を明記。

### Step 2: 全負けの分類

- 201負けを Step1 の定義で分類し、**カテゴリ別の割合**を出す。あわせて (a) 試合長、(b) 最終サイド差（接戦 vs 大差）とクロス集計。
- 完了条件: `results/2026-07-21_loss_taxonomy_breakdown.md` にカテゴリ別内訳＋クロス集計。山札切れ25.9%を含む全体像。

### Step 3: 相手アーキタイプとのクロス

- 各敗因カテゴリを**相手アーキタイプ**でクロス。負けが特定マッチアップに**偏っている**か（→ マッチアップ特化＝相手モデリングのレバー）、**広く分散**しているか（→ 一般的な棋力/テンポのレバー）を判定。
- 完了条件: `results/2026-07-21_loss_taxonomy_by_matchup.md` にカテゴリ×相手アーキタイプの表と、偏り/分散の判定。

### Step 4: 統合と次の大投資へのルーティング

- 山札切れ（許容済み）を除いた**最大の"直せる"敗因**を特定し、対処レバーに割り当てる:

| 敗因が集中する先 | 示唆される次の大投資 |
|---|---|
| 中盤テンポ/攻めのサイドレース負けが最大 | **PolicyModel の改善**（本番の実際の律速。何を直すかがここで具体化する） |
| 特定マッチアップに負けが偏る | **非ミラーでの相手モデリング検証**（`match_context` deck.csv修正＋多様デッキ対戦）。hidden info/PIMC投資を救う唯一の未検証設定の必要性がここで裏付けられる |
| アグロ大差・序盤事故が最大 | 序盤安定性・受けの強化（PolicyModel or デッキ相談） |
| どれも分散し決め手なし | 現状の提出を受け入れ、別コンペ(challenge-strategy等)や足場固めへ |

- 完了条件: `results/2026-07-21_loss_taxonomy_routing.md` に、証拠に基づく次の大投資1点の推奨。

## Definition of Done

- [ ] 敗因タクソノミの定義と検出ルールを明文化
- [ ] 201負けを全分類し、カテゴリ別内訳＋接戦/大差クロスを記録
- [ ] 敗因カテゴリ×相手アーキタイプのクロスで、マッチアップ偏り vs 一般的弱点を判定
- [ ] 山札切れ以外の最大の"直せる"敗因を特定し、次の大投資（PolicyModel改善／非ミラー相手モデリング／受け入れ）を証拠でルーティング
- [ ] （明示的にやらないこと: 修正実装・deck.csv変更・探索の作り込み・非ミラーharness実装・足場固め）

この分類が終われば、「次にどこへ投資すれば実戦の勝率が最も上がるか」を、個別の深掘りの成り行きでなく、実Kaggleの負け全体の地図に基づいて選べる。特に「負けがマッチアップに偏るか」は、これまで一度も検証できなかった **hidden info/相手モデリングの価値**（非ミラー投資に進むべきか）を、安く判断する材料になる。大投資本体はこの結果を見て別ファイルで計画する。
