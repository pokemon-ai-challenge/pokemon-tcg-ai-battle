# ML 版 相手デッキ予測器 フェーズ2: データスケールアップと「ベース + チューニング」構成

ブランチ: `feature/ml-opponent-deck-predictor`
作成日: 2026-07-19
前提: [ml-predictor-plan.md](ml-predictor-plan.md)(フェーズ1)が完了済み。
719 リプレイ・99,784 サンプルで validation top-1 正解率 95.7% / log loss 0.213。

## 動機

- 現状のデータは上位 20 チーム + その対戦相手(計 481 チーム)に偏っている。
  コンペ参加者は数千規模おり、レート上昇過程で中位帯とも当たるため、
  1000〜2000 位まで視野に入れたデッキ分布の把握が必要。
- メタは日々変動する。「大量データで作ったベースモデル」+「直近・上位帯のデータでの調整」
  という二段構成で、安定性と追従性を両立させたい。

## 設計原理(これを忘れると判断を誤る)

1. **増やすべきはリプレイ数ではなくユニークデッキ数。**
   1 チームはほぼ同じデッキを使い続けるため、同一チームの対局を大量に取っても
   学習上はほぼ 1 デッキ分の価値しかない。「カードが見えたら → どのデッキか」の対応は
   ほぼ決定的で、1 デッキあたり数対局で学習できる。
2. **学習されるものは 2 種類に分解できる。**
   - 条件部(coef): 「観測カード → アーキタイプ」の対応。プレイヤーの強さ・時期にほぼ依存せず安定
   - 事前分布(intercept): 「何も見えないときの確率」。母集団(レート帯)と時期に強く依存
3. **マッチメイキングはレート近傍で行われる。**
   実戦で当たる相手の分布 = 自分のレート帯の分布。全体分布の再現は不要で、
   評価・チューニングは「直近の上位帯」に合わせるのが正しい。
4. **ランク重み付けより時間減衰が効く可能性が高い。**
   まず無加重 + 期間フィルタで測り、必要が数字で示されたときだけ重み付けを導入する。

## 二層データ取得戦略

| 層 | 範囲 | 取得量 | 目的 |
|---|---|---|---|
| 深層(広く浅く) | 〜2000 位 | 1 チームあたり 1〜2 エピソード | デッキリスト収集(ラベル分布・事前分布・多様性・other 検出) |
| 上位層(狭く深く) | 〜200 位 + 自チーム対戦分 | 全量(従来どおり) | 観測シーケンスの量・実戦で当たる相手の分布 |

- コスト目安: 深層 2000 チーム × 2 件 × 3.5MB ≒ 14GB。全チーム全量(数百GB)は取らない。
- リーダーボード表示 API は 1 ページ 200 件上限。深い順位の取得には kaggle CLI の
  ページネーション(Next Page Token)または leaderboard の full CSV ダウンロードを使う
  (どの経路で submission id まで辿れるかは実装時に実 CLI で検証)。
- リプレイ本体・episodes_master.jsonl は既存のフラットプール/追記式をそのまま共有する
  (深層で取ったものも同じ replays/ に入る。episode_id で重複排除)。
- 定期実行で蓄積する運用(数日おき)。episode_create_time が記録されるので期間フィルタは後から効かせられる。

## ベースモデル + チューニング層

### ベースモデル(たまに再学習)

- 全蓄積データで多クラスロジスティック回帰を学習(フェーズ1と同じ)。
- train.py は学習データの**クラス事前分布(class_priors)を weights JSON の meta に必ず記録**する。
  これがチューニング層の補正基準になる。
- 出力: `output/model/deck_predictor_weights_base.json`(ベース)。

### チューニング層(頻繁に実行、再学習なし・数秒)

**事前分布シフト補正(intercept 補正)** — 第一段階はこれのみ:

```
b'_c = b_c + log(π'_c / π_c)
```

- `π_c` = ベース学習時のクラス事前分布(meta の class_priors)
- `π'_c` = ターゲット分布 = **直近 N 日 × 上位 R 位以内**のデッキラベル分布
  (deck_labels.jsonl と episodes_master.jsonl の結合から算出。ゼロ件クラスはスムージング)
- 出力: 補正済み `deck_predictor_weights.json`(デプロイ用)。meta に
  `base_trained_at` / `adjusted_at` / `target_window`(N, R, 件数)を記録する。
- ランタイム(ml_predictor.py)は一切変更不要 — スキーマは同一で、intercept の値が違うだけ。

**自己検証則**: 観測ゼロ(`observed_cards={}`, 序盤ターン)での予測分布が
ターゲット分布 π' に近づいていれば補正は正しく効いている。

### 第二段階(必要が示されたときだけ)

- 直近データでの warm-start ファインチューニング。ただし**ベース重みへの L2 アンカー付き**
  (少量データへの過適合防止)。intercept 補正で足りない証拠が評価に出るまで着手しない。
- ランク・スコアによる sample_weight(dataset.jsonl に rank/score は記録済みなので実験は容易)。

## 評価プロトコル(すべての判断の物差し)

- **固定 validation = 「直近 N 日 × 上位 R 位以内の相手」のエピソード**(デフォルト N=14, R=200)。
  実戦で当たる分布に合わせる。エピソード単位分割・リーク防止はフェーズ1と同じ。
- レポートに追加する軸:
  - 相手ランク帯別の正解率(1〜50 / 51〜200 / 201〜1000 / 1001〜 / 不明)
  - 期間別の正解率(古い週 vs 直近週) — 時間減衰の必要性をここで判断
  - 補正前(base)vs 補正後(adjusted)の比較 — チューニング層の効果測定
- 「深層データを足したら上がったか」「チューニングが効いたか」をすべてこの物差しで測る。

## 運用フロー(定常状態)

```
数日おき:  fetch(上位層全量 + 深層1〜2件/チーム + 自チーム分)
         → extract_decks / label_decks(分布レポート確認、other 増なら定義追加検討)
たまに:    build_dataset → train(ベース再学習)
頻繁に:    adjust_prior(直近上位帯に intercept 補正)→ calibrate(エビデンス数バケット別の
           温度スケーリングでキャリブレーション補正、meta.calibration を追記)
           → デプロイ用 weights 更新
毎回:      evaluate(固定 validation で base vs adjusted 比較、top-1正解率がキャリブレーション
           前後で不変であることも確認)
提出時:    補正済み deck_predictor_weights.json を同梱
```

キャリブレーション(温度スケーリング)の詳細は
[ml-predictor-plan.md の meta.calibration 節](ml-predictor-plan.md)を参照。
