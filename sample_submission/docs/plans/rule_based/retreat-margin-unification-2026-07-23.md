## 経緯

最初の指摘（2026-07-23）: 緊急時（`needs_retreat=True`）はマージンチェックを一切通らず無条件に逃げる、
という非対称な分岐になっている。→ 当初案は「緊急時にもマージンチェックを適用する」だった。

追加のユーザー指摘: **「攻撃しなくても基本的に逃げる必要はない。にげる必要があるときを考えれば
もっとよくなる気がする」**。これを受けて、方針を「スコア差にマージンを設けて逃げを抑制する」から
**「逃げに具体的な意味がある場合だけ提案する」という条件ベースの設計に変更**する。

## 現状の設計の問題（根本）

現行の `retreat.py` は「交代先の総合スコアが現在より高ければ逃げる」という**汎用的な優劣比較**で
動いている（`pokemon_value.active_value` vs `pokemon_value.switch_target_value`）。しかしこのスコアは
role_score・bench_value・KO_REPLACEMENT_PRIORITY 順位など「抽象的な価値」の合成であり、
**「今このタイミングで逃げることに具体的な利益があるか」を直接見ていない**。

その結果:
- 何も脅威が無いターンでも、交代先のスコアがちょっと高いだけで逃げを提案しうる
  （その交代で何が変わるのか＝タイミングとしての必然性が無い）。
- 緊急時（次ターンKOされそう）は、逃げても「脅威そのもの」は消えないため、
  交代先も同じ攻撃で普通に落とされるなら、逃げても被害を1ターン先延ばしにするだけで
  実質的な利益が無いことがある。
- 現在のアクティブに何のエネルギーも投資されていない（＝失って困るものが無い）場合、
  逃げても守るものが無いので、そもそも逃げる動機が無い。

## 再設計の方針: 「逃げる必要がある」の2つの具体的トリガー（ユーザーフィードバック反映版）

`retreat.py` の判断を、汎用スコア比較ではなく、**以下の2条件のいずれかに該当する場合だけ**逃げを
提案する形に変更する。どちらにも該当しなければ `propose()` は `None` を返す（逃げない）。

### トリガーA: 回避（次ターンKOされそう、かつ逃げれば実際に助かる）

すべて満たす場合のみ成立:
1. **`needs_retreat`**: 次の相手ターンで現在のアクティブが倒されそうと判定される
   （既存の `board_features.is_likely_ko_next_turn`）。
2. **逃げれば実際に助かる**: 交代先候補（`best_switch_target`）自身も、
   `is_likely_ko_next_turn(candidate, state, your_index)` で**倒されそうと判定されない**こと。
   候補自身もどのみち同じ攻撃で倒されるなら、逃げても被害を先送りするだけで意味が無い。

**変更点（ユーザー指摘を反映）**: 当初案にあった「現在のアクティブにエネルギーが付いているか」
（＝守る価値の有無）という条件は**削除**する。理由:
- ユーザー指摘「エネルギーがついてるから守るとはならない気がする」— エネルギーの有無を
  「守るべきかどうか」の判断基準にする根拠が弱い。
- 実際のゲームエンジンの仕様上、**にげるコストで捨てるのは `retreatCost` 分だけ**で、
  それを超えるエネルギーはベンチに退避後もそのまま残る（`retreat.py` 内の既存コメント
  「にげるコスト分のエネルギーを捨てる」を参照）。つまり「エネルギーを守るために逃げる」という
  理屈自体が薄い（きぜつすれば全ロスト、逃げれば retreatCost 分だけロスト、なので
  エネルギーの多寡に関わらず「逃げた方が失うエネルギーは少ないか同等」になりやすい）。
- 本質的に守っているのは「エネルギー」ではなく**「サイドを1枚渡さずに済むこと」**であり、
  これは投資額に関係なく常に価値がある。よってトリガーAは
  「次ターンKOされそう」かつ「逃げれば実際に助かる（候補も即死しない）」の2条件のみとする。

### トリガーB: 後退での即きぜつ（交代することで、相手のバトル場のポケモンを今ターン倒せるか）

ユーザー指摘「トリガーBに関しては後退することで、バトル場のポケモンを倒せるかを判断したい」を反映し、
「なんとなく攻撃できる」ではなく**「交代先が今すぐ相手アクティブをきぜつさせられるか」**に絞る。

すべて満たす場合のみ成立:
1. **現在のアクティブでは、今ターン相手アクティブをきぜつさせられない**
   （`attack_features.can_ko` — 後述の通り既に実装済み — が現在のアクティブの
   どのワザについても False）。
2. **ベンチ候補の中に、今持っているエネルギーだけで相手アクティブをきぜつさせられるものがいる**
   （同じ `attack_features.can_ko` を候補にも適用し、True になるワザが1つでもあれば成立）。

**【設計修正・重要】逃げ先の決定方法（第1回レビューで指摘された致命的な不整合の修正）**

当初案は「トリガーBが成立したら、KOできる候補へ逃げ先を明示的に誘導する」としていたが、
実際のゲームフローでは **`retreat.py`（MAIN選択でのRETREATアクション提案）と、実際に
どのベンチへ交代するかを決める `SelectContext.SWITCH`（`switch_turn.py` が独立に処理）は
別の選択タイミングであり、両者の間に状態を受け渡す仕組みが無い**（`router.py` で
`SWITCH`/`TO_ACTIVE` は `switch_turn.py` に固定ルーティングされ、`switch_turn.handle()` は
`pokemon_value.best_switch_target` の抽象スコアだけで独立に交代先を決めている）。
そのため「retreat.py が選んだ候補が、そのまま交代先になる」保証が無く、当初案のままでは
トリガーBは成立してもKOできない別の候補に交代してしまう可能性がある。

**修正方針**: retreat.py から switch_turn.py へ状態を受け渡すのではなく、
**`pokemon_value.switch_target_value`（交代先の評価関数）自体に「今すぐ相手をKOできるなら
大きく加点する」ボーナスを追加**し、`best_switch_target`（`retreat.py` と `switch_turn.py` の
両方が使う共通の交代先選定ロジック）が自然にKO可能な候補を最優先で選ぶようにする。
これは既存の `_KO_REPLACEMENT_BASE_SCORE`（きぜつ後継優先度のボーナス、
`pokemon_value.py:26`）と同じパターンであり、新しい仕組みを追加する必要が無い。

この修正により:
- `retreat.py` のトリガーB判定は「ベンチ候補の中にKO可能なものが**存在するか**」という
  単純な真偽判定だけでよくなる（どれを選ぶかは `switch_target_value` 側の責務）。
- `switch_turn.py`（きぜつ後の強制交代など）も、KO可能な候補があれば自動的に優先するようになり、
  副次的に改善される（後述「スコープ外」の記述を修正）。

トリガーBが成立した場合、逃げ先の実際の選定は `best_switch_target`（KOボーナス込みのスコアで
自然にKO候補が選ばれる）に委ねる。交代後の実際の攻撃実行は、次の選択ターンで `attack.py` が
新しいアクティブに対して通常通り KO 判定するため、`retreat.py` 側は「交代すればKOの目がある」
ことだけを判定すればよい。

上記いずれにも該当しない場合、たとえ交代先の総合スコアが現在より高くても**逃げない**
（＝ターンを終える、または弱くても攻撃する）。

## 要件（受け入れ条件）

- [ ] `retreat.py: propose()` を、既存の「スコア差 + マージン」判定から、
      上記トリガーA／Bのいずれかを満たすかどうかの判定に置き換える。
- [ ] `pokemon_value.active_value` / `switch_target_value` によるスコア比較（role_score・
      bench_value・KO_REPLACEMENT_PRIORITY 由来の合成スコア）は、
      **どのベンチ候補に逃げるか（交代先の選定）** には引き続き使ってよい
      （トリガーが成立した後の「最良の逃げ先はどれか」の決定には有効な指標）。
      ただし**「そもそも逃げるかどうか」の判定には使わない**。
- [ ] トリガーAは「次ターンKOされそう」かつ「交代先候補も次ターンKOされなさそう」の2条件のみ。
      エネルギー投資の有無など、それ以外の「守る価値」判定は**導入しない**（ユーザー指摘により削除）。
- [ ] トリガーAの「逃げれば実際に助かる」判定は、`best_switch_target` で選んだ候補について
      `is_likely_ko_next_turn` を適用して確認する。候補も危険なら逃げを提案しない
      （＝より安全な候補が他にいないか探す、は将来の拡張候補。まずは best_switch_target の
      1候補で判定する）。
- [ ] トリガーBは「交代することで相手アクティブを**今ターン中に**きぜつさせられるか」で判定する。
      現在のアクティブの使用可能などのワザについても `attack_features.can_ko(...)` が False なら
      （＝ `attack.py` が直接そのワザを選んでKOできる状況ではない）、ベンチ候補それぞれについて
      同じ `can_ko` を適用し、True になるワザを持つ候補が1体でもいればトリガーB成立。
      `attacker_hand_size` には `attack.py:44` と同様、**自分の** `player.handCount`
      （手札依存の可変ダメージ技の推定に使う。交代の有無に関わらず自分の手札枚数は変わらないため）を渡す。
- [ ] **`attack.py` を `attack_features.can_ko` を使う実装にリファクタする**
      （既存の `attack_features.py:92-102` に `can_ko` は既に実装済みだが、`attack.py:propose()` は
      これを使わず `resolve_damage` を直接呼んで `damage >= defender.hp` を自前でループしている
      ＝重複ロジック。第1回レビューで指摘。`attack.py` を `can_ko` 利用に置き換えたうえで、
      `retreat.py` のトリガーB判定からも同じ `can_ko` を呼ぶ）。
- [ ] **`pokemon_value.switch_target_value` に「今すぐ相手アクティブをKOできるなら加点する」
      ボーナスを追加する**（既存の `_KO_REPLACEMENT_BASE_SCORE` と同じパターン）。
      これにより `best_switch_target`（`retreat.py` と `switch_turn.py` の両方が使う共通の
      交代先選定ロジック）が、KO可能な候補を自然に最優先で選ぶようになる。
      **ボーナス値は「他の全項の合計を確実に上回る」ことを設計上の要件とする**（2回目レビュー指摘）。
      `switch_target_value` の他項の実運用上の上限を見積もると:
      `attacker_score`(hp_ratio×2.0 ≤ 2.0 + energy_count×1.0。energy_countは理論上unboundedだが、
      このデッキの `ENERGY_REQUIRED_COUNT` 最大値=3程度を大きく超えることは実運用上まず無い)
      + `switch_eval._SAFE_BONUS`(3.0) + `_profile_bonus`(role_score×3.0 ≤ 3.0 + combo_bonus 1.5,
      bench_valueは減点のみなので上限には寄与しない) + `_ko_replacement_bonus`(≤ 4.0) ≈ 合計13〜15程度
      （energy_countに数枚の余裕を見ても20台）。よって新設KOボーナスは
      `attack.py` の `_KO_BONUS=1000` と同様のオーダー感で、**この合計を1桁以上上回る値
      （例: 50.0〜100.0程度）** に設定し、A/Bはこの値の微調整ではなく「その大きさで
      勝率に問題が無いか」の検証に使う（`_KO_REPLACEMENT_BASE_SCORE=4.0` のような小さい値との
      混同を避けるため、モジュール定数名にも `_IMMEDIATE_KO_BONUS` のように明確な名前を付ける）。
      energy_countが極端に大きくなる理論上の edge case（デッキのゲームプランでは通常起きない）は
      許容リスクとして受け入れる。
- [ ] 回帰テストを `tests/unit/` に追加する。最低限:
      - トリガーA成立（次ターンKO見込み・候補は安全）→ 逃げを提案
      - トリガーA不成立（候補も同じ攻撃で倒される）→ 逃げない
      - トリガーA不成立（脅威が無い）→ 逃げない
      - トリガーB成立（現在のアクティブではKO不可、候補ならKO可能）→ 逃げを提案
      - トリガーB不成立（現在のアクティブでも既にKO可能＝attack.py側で完結、retreatは不要）→ 逃げない
      - トリガーB不成立（どの候補でもKOできない）→ 逃げない
      - どちらのトリガーも不成立（脅威なし・KOの目もない）→ 逃げない
        （＝これまでの「スコア差さえあれば逃げる」挙動が無くなっていることを確認）
      - `switch_target_value` のKOボーナス: KO可能な候補が他の候補よりスコアが高くなることを
        単体で検証するテストも追加する。
- [ ] 自己対戦A/B（`scratchpad/ab_retreat.py` は前回セッションのローカル一時ファイルで
      リポジトリ未追跡のため**新規作成**。同様のペアA/B比較ハーネスを新たに書く）で以下を確認する:
      - 逃げの発生回数が大きく減ること（意味のない逃げがほぼ消えること）
      - 勝率に有意な悪化が無いこと（本当に必要な場面まで見送っていないか）
      - トリガーB成立時に、実際にKO可能な候補へ交代できていること（`switch_target_value`の
        KOボーナスが意図通り機能しているかの実地確認）
      - **強制交代（きぜつ後の`TO_ACTIVE`等）を含む展開でも回帰が無いこと**（KOボーナスが
        `switch_turn.py` にも波及することの意図しない弊害が無いかの確認）
      - ハング・不正選択などの回帰が無いこと

## スコープ外（今回は変更しない）

- `weights.py` の `end`（-1000）や他カテゴリの重み。根本原因の説明には登場するが、
  retreat 側を条件ベースに変えることで対処するため、ここは触らない。
- `switch_turn.py` 自体のコード変更は不要（`pokemon_value.switch_target_value` の
  KOボーナス追加により、`switch_turn.py` は変更しないまま自動的に恩恵を受ける。
  ※第1回レビュー時点の「switch_turn.pyは無変更でよい」という結論自体は正しかったが、
  その根拠づけ（状態受け渡し不要になる設計への修正）が今回追加された）。

**【2回目レビュー指摘・意図的に許容する副作用】** `switch_turn.py` が処理する
`SelectContext.SWITCH`/`TO_ACTIVE` は、`retreat.py` 発の能動的な交代だけでなく、
**相手ターン中に自分のアクティブがきぜつして強制的に交代する場面**も含む
（`cg/api.py` のコメント参照）。この文脈でも新設KOボーナスがそのまま効くため、
「今すぐ相手をKOできるか」が交代先選定に影響する。これは意図的に許容する:
どのみち次の自分のターンでその交代先が攻撃機会を得るため、「相手をKOしうる」という属性は
強制交代の場面でも一般的に価値があると考えられる（安全性を無視するわけではなく、
`_SAFE_BONUS` 等の既存項と合算されるため、極端に危険な候補だけがKOボーナスだけで
選ばれるわけではない）。ただし想定外の弊害が無いか、自己対戦A/Bの中で強制交代を含む
展開でも回帰が無いかを確認する（要件セクションのA/B確認項目に含める）。

   状況が悪くても必ず交代する」になり、小さすぎると `_KO_REPLACEMENT_BASE_SCORE` 等の既存
   ボーナスに埋もれて選ばれない可能性がある。実装時にA/Bで調整する想定。
2. トリガーBで複数のベンチ候補がKO可能な場合、`switch_target_value` の合成スコア
   （role_score・bench_value・KO_REPLACEMENT_PRIORITY・新設KOボーナス）で自然に順位付けされる。
   「ダメージが最大の候補を優先」のような明示的なtie-breakは設けない（KOできる時点でどれも
   目的は達成されるため、合成スコアに委ねる）。この方針でよいか確認したい。
