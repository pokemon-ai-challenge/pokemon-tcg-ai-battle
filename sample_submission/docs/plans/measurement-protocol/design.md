## 0. なぜこのフェーズか(問題定義)

新アルゴリズム([[project_neural_agent_design]] の信念×Transformer×ISMCTS 構想)を組む前に、
**その真価を判定できる測定台が無い**。これが全ての実験の律速である。

### 0.1 転移失敗の連鎖 —— 実証済み negative の一覧

| 施策 | offline | 実戦 | ゲート判定 |
|---|---|---|---|
| Tier1 identity 特徴 | 一部微増 | 43–44% | 転移せず |
| Tier3 consequence 特徴 | +0.1〜0.2pt or 悪化 | 35–55%(不安定) | 転移せず |
| 容量増 M64/M128 | +0.5pt 単調・過学習なし | 49.0% / 49.3% | 転移せず |
| outcome/advantage 加重 BC(案C) | — | 43–52%、β0.5 は 900 で 50.67% | 不採用 |
| PIMC + hidden info(ml_policy 上) | — | 52% / 55%(各100) | 有意差なし |

これらは全て「効果ゼロ」と結論されてきた。**しかしその結論は測定の検出力に支えられていない。**

### 0.2 現行ゲートは、あり得る効果量のほとんどを検出できない

現行の採用ゲートは「head-to-head N 試合で Wilson 95%CI 下限 > 0.5」。
`_diag_phase0_power.py`(閉形式)の実測:

**検出力 0.8 に必要な試合数(真勝率別):**

| 真勝率 | 必要 N | 現実性 |
|---|---|---|
| 50.5% | **78,379** | 不可能 |
| 51.0% | 19,603 | 不可能 |
| 52.0% | 4,924 | ほぼ不可能 |
| 53.0% | 2,178 | 高コスト |
| 55.0% | 773 | 可能 |
| 58.0% | 300 | 容易 |
| 60.0% | 198 | 容易 |

300 試合で通過するには **55.67% 以上**が必要(検出力: 真52%で 0.113、真50.5%で 0.042)。

→ **§0.1 の施策群が居る「真 50〜52%」の帯は、数千〜数万試合ないと本物か否かを判定できない。**
過去の "negative" の多くは **「効果ゼロ」ではなく「測れていなかった」**([[project_neural_agent_design]] H3 の結論)。

### 0.3 二重の含意 —— 「もっと強く測る」だけでは足りない

上表は同時に2つを示す:

1. **測定を強くする余地はある**(paired 化・逐次化・graded 化で必要 N を数倍削れる)。
2. **だが真 50〜52% の効果は、測れたとしても戦略的に無意味**。+0.5〜1pt を追って数万試合を焼くのは非合理。

→ 本フェーズのゴールは **「測る道具の検出力を上げる」と「測る価値のある効果量に絞る」の二正面**。
具体的には、(a) 逐次検定で無駄な試合を焼かず決定可能な結論を出し、(b) 二桁 pt が見込める介入
(新アーキ・自己対戦リーグ)にリソースを寄せられる測定台を作る。RL ドラパルトの +12.3pt が
700 試合で有意に測れた([[project_neural_agent_design]] M3)のは効果が大きかったから —— これが基準線。

## 1. 検証で確定した「ハーネスの物理的制約」(2026-07-25 実測・コードで確認)

分散削減の王道は CRN(共通乱数: 同じシャッフル・コイン列で candidate と control を対戦させ、
運の分散を相殺する)。これが使えるかは cg エンジンの RNG 構造次第なので実測した(付録A に再現手順)。

| 問い | 実測結果 | 根拠 |
|---|---|---|
| シード API はあるか | **無い** | `cg/sim.py`: `BattleStart.argtypes = [POINTER(c_int)]`(カード配列のみ)。cg バインディング全体に `seed`/`srand` シンボル 0 |
| 新規プロセスで再現するか | **No**(3 回とも別指紋) | 付録A T1 |
| 同一プロセス内で再現するか | **開幕のみ Yes / フルゲーム No** | 付録A T2/T3 |
| 点差シグナルは取れるか | **Yes** | 付録A T4(終局に `prize` 残枚数・`deckCount`・active/bench・勝ち筋種別) |

### 1.1 RNG 構造(実測から逆算)

- **開幕のシャッフル**(山札順・初手・サイド)は **プロセス毎に固定**。同一プロセスで
  `battle_start` を何度呼んでも step0 の内部状態は完全一致(付録A T2)。
- **対戦中のコイン投げ・サーチ後の再シャッフル**は **プロセス全体で進む大域ストリーム**から引かれ、
  対戦ごとにリセットされない。同じ行動列でも 2 試合目は 1 試合目の RNG 消費量に依存して分岐する
  (付録A T3: 同一行動なのに step1 で既に割れる、フルゲーム勝者も一致しない)。

### 1.2 含意 —— 完全 CRN は不可能、「開幕まで」の部分 CRN のみ

- candidate と control に **同じコイン列**まで揃えることはできない。
- 揃えられるのは **同じ初手・同じサイド・同じ山札順**まで(= 1 プロセス = 1 つの固定開幕 world)。
- しかも 2 試合目の中盤乱数は 1 試合目の消費に依存して汚れる → **部分 CRN は「確実な勝ち」ではなく
  「開幕分散が全分散の主成分なら効く任意ボーナス」**。採用前に効果を実測する必要がある(§3-③)。

これは [[project_pimc_prod_validation]] の「先手ゲーの分散が config 差を埋もれさせる」仮説の物理的正体。

### 1.3 RNG の正体(バイナリのエクスポート表・シンボルから確定、2026-07-25)

- **cg.dll のエクスポートは 13 関数のみ**(`AgentStart / AllAttack / AllCard / BattleFinish /
  BattleStart / GameInitialize / GetBattleData / SearchBegin / SearchEnd / SearchRelease /
  SearchStep / Select / VisualizeData`)。**シード関数は無い**(隠し API も無し) → 公開 API 経由の
  シード指定は不可能。エンジン(`cg/`・cg.dll)は改変禁止(CLAUDE.md)なのでシード追加も不可。
- **`libcg.so`(未 strip)がリークした内部シンボル**に `std::random_device` のコンストラクタと
  `std::mt19937`(メルセンヌツイスタ)の `_M_gen_rand` が存在。→ **RNG は「`random_device`(OS
  エントロピー)で `mt19937` をシード」。しかも開幕がプロセス内で一定(T2)= 再シードは 1 回のみ**。
- **含意**: (1) 新規プロセス毎に別シード(random_device)なので **再実行での再現は不可**。
  (2) だが seed が **1 回きり + 状態はプロセスメモリ上**なので、**fork でメモリ複製すれば真 CRN が成立**
  (§3-b)。エンジンの協力は不要。

## 3. 提案プロトコル(レバレッジ順・RNG 構造への依存が低い順)

評価軸: **効果(検出力への寄与)・実装コスト・RNG 依存・転移リスク・採用前に要る検証**。

### ① 逐次検定(SPRT)で固定 N ゲートを置換 ★最重要・RNG 非依存・プロトタイプ検証済(付録C)

最小有意効果 δ_min(採用に値する最小の真勝率上乗せ)を先に決め、Wald SPRT で
`H0: p ≤ 0.5` vs `H1: p ≥ 0.5 + δ_min` を **逐次**判定する。1 試合ごとに対数尤度比を更新し、
**3種類**の decision を返す(明確な負けを早期に殺し、微差は決定可能な結論で止める):

| decision | 意味 | 条件 |
|---|---|---|
| `PROMOTE` | 採用 | LLR ≥ A = ln((1−β)/α) |
| `FUTILITY` | 不採用確定(δ_min 未満と確定) | LLR ≤ B = ln(β/(1−α)) |
| `TRUNCATED_NO_PROMOTE` | 予算 N_max 到達・境界未到達(不採用だが H0 確定でない) | n ≥ N_max |

**N_max 到達時は LLR 符号で H0/H1 へ強制分類しない**(統計的に未確定のため)。`TRUNCATED` は運用上
「採用しない」に倒すが `FUTILITY` とは区別して記録する。

**検定パラメータ(2026-07-25 レビュー確定)**: α=0.05, β=0.10 を**固定**(変更種別で階層化しない)。
「どの程度の改善を要求するか」は **δ_min のみ**が担う:

| 変更の種類 | δ_min | p1 | 根拠 |
|---|---|---|---|
| 大規模アルゴリズム変更(新アーキ / ISMCTS / DMC 等) | **0.05** | 0.55 | 複雑さ・保守・レイテンシのコストに見合う高い bar。真 ≥0.55 なら ASN ~690 で安く検出、+3pt 止まりの大改造は正しく棄却 |
| 小変更(重み / 特徴 / config 微調整) | **0.03** | 0.53 | 保守コストが低いので +3pt で採用可 |

α/β まで種別ごとに変えると評価契約が複雑化するため固定。より厳しい最終 Champion gate が要れば後続で別途設計。

**プロトタイプ実測(付録C, MC 2万試行, δ_min=0.03, α=.05, β=.10, N_max=3000)**:
- 較正 OK: 真 0.50 で PROMOTE 4.4%(≒α)、真 0.53 で PROMOTE **84%**。
- **名目 power と実効 PROMOTE 率は区別する**: 名目 SPRT power = 1−β = 0.90(打ち切りなしの漸近保証)。
  実効 PROMOTE 率 = N_max 込みの実際に PROMOTE になる割合 = **84%@p1=0.53**(打ち切り ~6% は
  TRUNCATED_NO_PROMOTE)。**「β=.10 = 実効 power .90」とは書かない**。**N_max は検出力に効く予算パラメータ**。
- 明確な負けは早期 FUTILITY: 真 0.40→ASN 165 / 0.46→~360 / C1 filter 相当 0.427→**ASN 215**。
- **正直な再評価: SPRT の価値は「試合数削減」ではなく「決定可能性」**。razor's-edge の真 0.50〜0.52 は
  ASN 1000〜1600 と固定 300 より**多く**かかる。だがこれは SPRT の欠陥でなく「50% と 53% の区別に
  数千試合要る」(§0.2)の可視化。固定ゲートが「inconclusive」で終わる所を、SPRT は「不採用」と**答える**。
- ASN 表は **§0.3 の定量的裏付け**: 微差の測定は本質的に高コスト、二桁 pt なら ASN が 300〜700 に落ちる。

- 効果: ◎(決定可能性) / 実装コスト: 低(head-to-head ランナーに停止則を巻く) /
  RNG 依存: 無 / 転移リスク: 無 / **確定済**: α=.05・β=.10・δ_min(上表)・3分類判定。残るは N_max の値のみ。

### ② graded outcome(サイド差) ── **却下(推定量に使わない)**、記述的診断としてのみ記録

当初案は「サイド差を一次スクリーニング統計に」→ 検証で却下 →「分散削減の共変量に」→ **これも撤回**。
2 段階で却下した。

**検証(2026-07-25、実リプレイ 1,996 試合、対戦ゼロ、付録B)**:

| 指標 | 値 | 含意 |
|---|---|---|
| 記録上マージン符号が勝者と一致 | 70.1%(+ tie 18.4%) | 記録は「勝利の一手適用前」=真値の下限。46%は勝者残≤1で取り切り寸前 → 真の一致はもっと高い |
| **敗者 deckout(deck=0)で決着** | **13.8%** | サイド差では見えない勝ち筋。マージンが 0/負でも勝つ |
| 敗者 no-pokemon(盤面0) | 13.5% | 同上(一部はサイド優位と相関) |
| point-biserial r(margin, win) | **0.643**(r²=0.41) | 中程度。勝敗分散の 41% しか説明しない |

**却下理由(1: 単独スクリーニング)**: サイド差は **deckout チャネルに構造的に盲目**。deckout はこの競技
リプレイで 13.8%、かつ **自エージェントの敗因では 25.9%**([[project_deckout_loss_cause]])を占める。
マージン単独でスクリーニングすると、**山札切れ改善(自分の最大級の敗因の一つ)を系統的に見落とす**。

**却下理由(2: CUPED 共変量、2026-07-25 レビューで撤回)**: 終局サイド差は **treatment(config)後に
実現する outcome 変数**であり、CUPED が要求する **pre-experiment 共変量(treatment に非依存)ではない**。
post-treatment 変数で勝率を調整すると推定量が「勝率」から「サイド差条件付き量」へずれ、**config の勝率効果を
bias する**(媒介/collider)。→ CUPED は使わない。

**採用する使い方(記述的診断のみ)**:
- **推定量は生の二値勝率のみ**。SPRT も勝率 CI も **サイド差で調整しない**。
- サイド差・**勝ち筋種別(prize-out / no-pokemon / deckout / error、併発は捨てず記録)は記録**し、
  「config がどのチャネルで効くか」を見る診断に使う(推定量には非接続)。将来は **全勝ち筋に単調な合成
  outcome** の設計余地(§後続)。
- 妥当な分散削減の道: **CRN(fork、③-b)** と **手番均衡(g%2、実装済)**。加えて **pre-treatment 共変量**
  (先攻/後攻・初期盤面・初期手札=treatment 前に決まる変数)による回帰調整は post-treatment のサイド差と
  違い不偏で、**将来 optional** の妥当な候補(MVP 不要、手番均衡で足りるか先に確認)。
- 効果: ○(診断価値) / RNG 依存: 無 / 転移リスク: 無(推定量は生勝率)。

### ③ CRN(共通乱数)による分散削減 ○条件付き ── 2 系統ある

**③-a 部分 CRN(Windows・同一プロセス逐次)**: 1 プロセス = 1 開幕 world として candidate と
control を**両手番**で対戦させ、開幕運を相殺して McNemar で解析。ただし中盤コインは揃わない(§1.1)。
開幕分散が支配的なら中(2〜4x)、そうでなければ小。RNG 依存: 有。要検証(開幕分散の割合)。

**③-b 完全 CRN(Linux・fork)★**: エンジンの RNG は `std::mt19937` を `std::random_device` で
**プロセス毎に 1 回シード**(§1.3 の追記)。この状態はプロセスメモリ上にあるため、**ゲーム開始直前に
`os.fork()`** して親=candidate / 子=control を走らせると、両者は同一 mt19937 状態を継承し
**同じ初手・サイド・コイン列を分岐点まで完全共有** = 真 CRN。T3(逐次 2 試合が中盤で割れる)は
1 試合目の RNG 消費が原因で、fork は両者を同一消費位置から出発させるため回避できる。エンジン無改造。

- 効果: ◎(開幕+中盤の運を相殺、検出力を大きく底上げ) / 実装コスト: 中 /
  RNG 依存: 有(fork でメモリ複製) / 転移リスク: 無 /
  **前提: Linux ランタイム**。laptop / GPU desktop とも **Windows(os.fork 無し)** と判明(2026-07-25)。
  使うには WSL2 導入 → repo の `libcg.so` を python3+ctypes でロード(`cg/sim.py` は非 Windows で .so 自動選択)。
  **要検証(導入後): fork 子で同一行動フルゲームのハッシュが一致するか(= 二段 RNG の再シード有無)を実証してから採用**。

- 先手/後手バランス(現 `collect_parallel.py` の `g%2`)は CRN と独立に有効な層化。無条件で維持。

### ④ discordant 率を上げる標的評価 ○

微調整 config は control と決定の ~85% が一致し、情報は残り 15% にしか無い(discordant 46/300)。
変更が触る決定(例: 攻撃判断)が **頻出かつ重要なマッチ/局面**で測れば、discordant が増え McNemar が効率化。

- 効果: ○(実効 N を増やす) / 実装コスト: 中(評価マッチの選定) /
  RNG 依存: 無 / 転移リスク: 中(標的が偏ると外的妥当性↓、④は⑤と外部妥当性ガードで補正)。

### ⑤ 強い固定参照相手 ○ ← アルゴリズム側 "worthy opponent" への橋

ミラー vs control は先手分散が巨大で決定もほぼ一致。より識別力の高い固定相手にすると効果シグナル
自体が拡大する。round_robin の相手は弱すぎて production が既に 68.8%([[project_neural_agent_design]] H1a)
= ゲートが 50% 近傍で発火しない問題も、参照相手の質で改善。これは self-play リーグ投資と直結する。

- 効果: ○ / 実装コスト: 中〜高(強い相手の用意) / 転移リスク: 相手選定に依存 /
  **注: これは測定と "worthy opponent" 構築の共通部品。アルゴリズム本体トラックと合流する点。**

### 外部妥当性ガード(全 lever 共通)

**スクリーニングは vs-control head-to-head(高検出力)で、採用確認は vs-field(外的妥当性)で行う。**
これを分けないと [[project_pimc_prod_validation]] の「head-to-head で勝つ → 本番に転移せず」を再演する。
vs-field 評価は `match_context._load_own_deck_ids()` が常に deck.csv を読む制約が障壁(既知)。

## 4. 推奨シーケンス(最小コスト・最大確実性の順)

1. ~~**② の相関検証**(既存ログ、対戦ゼロ、最速)~~ **✅ 完了(2026-07-25)**: 実リプレイ 1,996 試合で
   検証 → **サイド差は単独スクリーニング不可(deckout に盲目、r=0.64)**。CUPED 共変量も撤回(§3-②)、
   サイド差・勝ち筋は**記述的診断のみ**。**次の設計余地 = 全勝ち筋に単調な合成 outcome の定義**。
2. **① SPRT ラッパー**(RNG 非依存・低コスト・最大効果) ← **現在の最優先**: 固定 N ゲートを置換。
   検定契約は確定(α=.05/β=.10/δ_min/3分類、§3-①)。推定量は生の二値勝率、勝ち筋種別を併記。
   → 実装計画 `implementation-plan.md`(Step 0 着手可)。
3. **④ 標的評価 + ⑤ 参照相手の質**: 情報/試合を増やす。⑤はアルゴリズム側の worthy opponent と共有。

## 5. 却下 / 保留

- **エンジン API 拡張(シード引数追加)**: cg.dll にシード関数が無く(§1.3)、`cg/`・DLL は改変禁止 = 不可能。
- **同一プロセス逐次でのフルゲーム再現**: 中盤で崩れる(§1.1)= 単純逐次では不可(fork なら可、§3-b)。
- **再実行での特定試合の再現(リプレイ)**: random_device がプロセス毎に別シード(§1.3)。
  厳密再現には entropy 横取り(Linux は `random_device` の /dev/urandom 経路を LD_PRELOAD、Windows は
  `rand_s` を Detours 等で hook)が要り、脆く実装依存 = **保留**。CRN 目的なら fork(§3-b)で足りる。
- **真 <1pt 効果を測り切る大規模 N**: 78,379 試合(§0.2)。非合理につき追わない。効果量を上げる方針(§0.3)。

## 付録A: 実測プローブの記録(再現手順)

プローブは使い捨て(scratchpad)。結論の監査用に要点を残す。cg エンジンは read-only、production 無変更。

- **T1 新規プロセス決定性**: fresh process で `battle_start(deck, deck)` 直後の内部状態
  (`search_begin_input`)を sha1。3 プロセスで `11186d33` / `1d5cfda2` / `a01e0e45` = **全て別**
  → プロセス起動時に非決定シード。
- **T2 プロセス内開幕決定性**: 同一プロセスで `start→finish→start`。両者の step0 指紋が **完全一致**
  → 開幕シャッフルはプロセス毎固定。
- **T3 プロセス内フルゲーム決定性**: 決定論エージェント(常に先頭 minCount 個)で 2 フルゲーム。
  勝者 0/226手 vs 1/208手 = **不一致**。step5 まで同一行動の run 同士でも **step1 で分岐**
  (共有プレフィックス 1/8)→ 中盤 RNG は大域ストリームで汚染。
- **T4 点差可用性**: 終局 State で `players[i].prize` 残枚数・`deckCount`・active/bench 数・
  `result`(勝者)が読める(例: winner=1 が 3枚取得、敗者は全滅で敗北)= graded outcome 実装可能。

再現コード雛形(scratchpad に保管、必要なら `kaggle_replays/_diag_measure_*.py` に landing 可):

```python
# T1/T2: 開幕指紋
from cg.game import battle_start, battle_finish
obs, sd = battle_start(deck, deck)          # deck = deck.csv 先頭60
fp = sha1(obs["search_begin_input"].encode()).hexdigest()  # プロセス毎固定 / プロセス間で別
battle_finish()

# T4: 終局サイド差
# ループで battle_select し result != -1 まで進め、
# margin = players[opp].prize_len - players[me].prize_len を算出
```

## 付録B: サイド差↔勝率 相関検証(2026-07-25、§3-②の根拠)

`kaggle_replays/replays/` の実リプレイからランダム 1,996 試合を抽出(対戦ゼロ)。
各試合: 勝者 = `d["rewards"]` の argmax、終局盤面 = 最終 step の `observation.current`。
注意: 最終観測は「勝利の一手適用前」で `current.result` は常に -1 → 記録マージンは真値の下限。

| 指標 | 値 |
|---|---|
| valid N | 1,996(error/DNF 負け 0.2%、skip 1) |
| マージン符号が勝者と一致(記録値) | 70.1% |
| 引き分け(取り分同数) | 18.4% |
| マージン ≤ 0 で勝利(代理の失敗) | 11.5% |
| 勝者残 ≤ 1(取り切り寸前) | 46.3% |
| 敗者 deckout(deck=0) | **13.8%** |
| 敗者 no-pokemon(盤面 0) | 13.5% |
| マージン ≤ 0 勝利の内訳 | deckout 167 / no-pokemon 96 / other 334 |
| point-biserial r(margin, win) | **0.643**(r²=0.41) |

800 サンプルでも 70.8/18.3/10.9%・deckout 13.0%・r=0.659 とほぼ同一(安定)。
**結論**: サイド差は deckout(自敗因の 25.9%)に盲目。単独スクリーニングは却下、CUPED 共変量も撤回
(post-treatment 変数、§3-②)。**記述的診断としてのみ**記録する。スクリプト: scratchpad
`_diag_margin_vs_winrate.py`(push 無し)。

## 付録C: SPRT プロトタイプ動作特性(2026-07-25、§3-①の根拠)

Wald SPRT(`H0: p≤0.50` vs `H1: p≥0.50+δ_min`)。scratchpad `sprt_prototype.py`(push 無し、
増分 API `SPRT.update(win)` は実運用の決定関数にそのまま使える)。MC 2万試行、δ_min=0.03、
α=.05、β=.10、N_max=3000。**3分類判定(N_max で符号強制分類しない、2026-07-25 修正)**。境界 A=+2.890 / B=−2.251。

較正確認: 真 0.50 で PROMOTE 4.4%(≒α)。真 0.53 で **実効 PROMOTE 率 84.3%**(≠ 名目 power 0.90=1−β。
