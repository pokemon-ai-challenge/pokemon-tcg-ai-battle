## この文書の役割

design.md が **「何を・どう作るか」** を定義するのに対し、本書は **「なぜその手法を採ったのか・どの代替案をなぜ捨てたのか」** だけを記録する。設計そのもの(入出力仕様、特徴量リスト、重み JSON スキーマ等)は design.md を正とし、ここでは繰り返さない。

前提として、以下の制約・状況が全ての判断の背景にある。

| 項目 | 内容 | 判断への影響 |
|------|------|------|
| 学習データ | Kaggle 上位プレイヤーのリプレイ 4,698 件(完結ゲーム。両者の observation・行動・順位付き) | 完結ゲームなので最終勝敗が確定ラベルとして使える。局面数は数十万規模 |
| 提出環境 | Kaggle。1手あたり時間制限あり | 推論は JSON 重み + numpy/純Python が安全(`ptcg_ai/opponent_modeling/ml_predictor.py` の deck_predictor で実績あり) |
| ゲーム特性 | 不完全情報(相手手札・山札・伏せカード非公開)、行動空間は可変長の選択肢リスト | 神視点学習と推論時入力のズレ、固定行動空間の非成立 |
| サーチ API | `cg/api.py` に determinize 済み状態を進める `search_begin` / `search_step` | 神視点バリューは探索の葉評価として後段で活きる |
| チーム方針 | 予測確率のキャリブレーションは慎重側(温度 T >= 1.0、生の見積もりより強気にしない) | 過信は探索・リスク判断で危険 |

Step1 の目的は「勝率予測器(バリュー関数)を教師ありで作り、単体で精度検証できる状態にする」こと。以降、各判断を「採用 / 理由 / 却下した代替案」で述べる。

## 1. 教師ありバリュー学習を最初に作る

**採用:** リプレイの各局面に「そのゲームの最終勝敗」をラベル付けし、勝率を予測する回帰器を教師あり学習する。これを ML エージェント群の最初の実装物とする。

**理由:**

- データが既にある。`kaggle_replays/extract_training_data.py` が `(observation, action)` ペアを順位重み付きで JSONL 出力する。ここに「そのエピソードの最終勝敗」を結合するだけで、追加のデータ生成(自己対戦・シミュレーション)なしに学習セットが完成する。
- **単体で精度検証できる。** バリュー関数は「この局面の勝率」という明確な回帰ターゲットを持ち、val/test で AUC・較正誤差を測れる。エージェント全体を対戦させなくても良し悪しが分かるため、開発ループが速く失敗の切り分けが容易。
- **失敗の切り分けが容易。** 教師あり学習は「データ → ラベル → モデル → 指標」の各段が独立に検証できる。後述の探索や自己対戦は複数の可動部が絡むため、まず土台としてバリュー単体を固めておくと、後段で問題が出たときの原因分解ができる。

**却下した代替案:**

- **ゼロからの自己対戦強化学習(AlphaZero 型)を最初に作る。** 却下。
  - 弱い初期方策どうしの自己対戦は「悪い手を悪い手で咎める」局面ばかりを生み、悪癖を強化データとして学習してしまうリスクがある(ml-agent-plan.md の基本方針とも一致)。
  - 本ゲームは不完全情報である。AlphaZero 型をそのまま適用するには determinization かベリーフ状態の管理が必要で、探索木の各ノードで `search_begin` に相手の非公開情報を与える必要がある。ネイティブエンジン(`cg.dll`/`libcg.so`)呼び出しのコストと相まって、自己対戦のスループットが厳しい。
  - 学習が回らないときに「データが悪いのか・探索が悪いのか・報酬設計が悪いのか」を切り分けにくく、デバッグ困難。
- **ルールベース評価関数(`ptcg_ai/board_evaluation/`)の改良を続ける。** 却下。手作りの評価軸には表現力の上限があり、相互作用する特徴の重みを人手で調整し続けるコストが高い。学習で重みを最適化する方が伸びしろがある。ただしルールベースの特徴量はエンコーダの素材として流用する(design.md 参照)。

**補足(自己対戦を完全否定はしない):** 自己対戦は Step4「BC/バリューで初期化した後のファインチューニング」に位置づける。Step1〜3 で強いバリューと方策ができた後なら、初期方策が弱いことに起因する悪癖リスクは解消される。順序の問題であって、手法そのものの否定ではない。

## 2. 勝敗のモンテカルロラベル

**採用:** 各局面のラベルを「そのエピソードの最終勝敗(勝ち=1 / 負け=0、必要なら順位由来の連続値)」とする。局面から終局までを実際のリプレイ結果で一意に決めるモンテカルロ方式。

**理由:**

- リプレイは **完結したゲーム** である。序盤・中盤・終盤のどの局面も、そのゲームがどう終わったかが既に確定している。したがって最終勝敗ラベルは追加の推定を一切挟まず取得でき、モデルやロールアウトに起因するバイアスが入らない。
- 実装が最も単純で、ラベル生成に可動部がない。Step1 の「まず土台を固める」目的に合致する。

**却下した代替案:**

- **TD 学習・ブートストラップ(自分の価値推定で次状態を評価してラベルを作る)。** 現段階では却下。
  - TD が有効なのは、自前の方策・価値でロールアウトしたり、終局まで到達しないエピソードを扱う場合。今回は完結ゲームのオフラインデータなので、終局勝敗という真値がある。そこにわざわざ自分の(まだ存在しない/未熟な)価値推定を混ぜるのは、不要な複雑さとバイアス源を持ち込むだけ。
  - ブートストラップは「価値がまだ良くない段階では価値のノイズを価値に伝播させる」性質があり、Step1 の初期段階と相性が悪い。

**ノイズへの対処(既知の弱点):** 序盤局面は最終勝敗との相関が弱く、ラベルがノイジーになる(同じ序盤盤面でも勝ちも負けもある)。対処方針:

- サンプル数で均す。数十万局面規模あるため、序盤の勝率は平均に回帰する。
- **ターン層別で評価する。** ターン帯ごとに AUC・較正を出し、「序盤で予測が弱い」ことをバグではなく既知特性として可視化する。
- 必要ならターンによる重み付け(勝敗が確定に近づく終盤の重みを上げる等)を後から入れる。Step1 では入れず、層別評価で必要性を判断してから追加する。

## 3. 入力は公開情報のみ(方式 a)で開始

**採用:** バリュー関数の入力を、推論時に実際に得られる **公開情報のみ** から作る。リプレイに含まれる相手の非公開情報(手札・山札・伏せカード)は学習にも使わない。

**理由:**

- **学習時と推論時の入力分布を一致させる。** 実戦の agent には相手の非公開情報は渡ってこない。神視点で学習したバリューを非公開情報が欠けた入力に適用すると distribution shift が起き、精度が読めなくなる。公開情報のみに限れば学習と推論で同じ特徴が揃い、val の数字がそのまま実戦の期待値になる。
- 依存を最小化できる。後述の推定モジュールに依存しないので、Step1 のバリューは単独で完結して検証できる。

**却下した代替案:**

- **神視点(相手の全情報を含む)でバリューを学習する。** Step1 では却下、ただし将来使う。
  - 推論時に神視点入力は作れないため、そのままではエージェントに載らない。
  - 神視点バリューが意味を持つのは **Step3 の determinization 探索**。`search_begin` に「サンプリングした具体的な相手デッキ・手札」を渡して世界を1つ確定させた後なら、その世界は全情報が既知であり、葉を神視点バリューで評価できる。神視点バリューはそのとき改めて設計・学習する(design.md の将来拡張節、および本書 8 節)。
- **公開情報 + hidden_information 推定値を最初から入力に混ぜる。** Step1 では却下。
  - `ptcg_ai/hidden_information/` と `ptcg_ai/opponent_modeling/` の推定出力を特徴に入れると、バリューの精度が推定器の精度に連動してしまい、悪化したときにどちらが原因か切り分けられない。
  - まず公開情報のみでベースラインを確定させ、**推定値特徴は「増分(delta)が測れる形」で後から追加する。** そうすれば「推定値を足して AUC が何ポイント上がったか」を定量化でき、追加の是非を根拠を持って判断できる。

## 4. モデル: ロジスティック回帰ベースライン → 小型 MLP(numpy 推論)

**採用:** まず多項ではなく二値のロジスティック回帰(勝率)をベースラインとして作り、次に小型 MLP(隠れ層 1〜2 層程度)へ拡張する。いずれも **オフラインで学習し、重みを JSON 出力 → numpy/純 Python で推論** する(`ml_predictor.py` と同じパターン)。

**理由:**

- **入力が手作りの密な低次元ベクトルだから巨大モデルは要らない。** 生のカードシーケンスやテキストから表現学習するのではなく、`board_evaluation/` の attack/board 特徴量を土台にした解釈可能な特徴を与える。この設定では線形〜浅い非線形で十分な表現力が出る。
- **提出環境と整合する。** deck_predictor は softmax 回帰の重み JSON を読み、純 Python の行列積 + softmax だけで推論している(`ml_predictor.py`)。同じ経路ならライブラリ依存も時間コストも既知で、Kaggle の1手時間制限内に確実に収まる。torch 等の可否確認に開発を止められない。
- **LR を先に作るのは足場のため。** 線形モデルは重みがそのまま特徴の寄与として読めるので、特徴量エンコーダのバグ検出(符号が逆、常に 0 の特徴、リークしている特徴)に使える。かつベースライン AUC を与え、MLP がそれを実際に上回るかを判定する基準になる。

**却下した代替案:**

- **GBDT(LightGBM 等)を本番モデルにする。** 却下。
  - タブラー特徴では強力で、実際「特徴量が持つ情報量の上限」を測るオフライン参考値としては使う価値がある。
  - しかし決定木アンサンブルを純 Python/numpy へ安全にエクスポートするのは、線形/MLP の重み行列を出すのに比べて手間とバグ余地が大きい。提出経路のシンプルさ(JSON 重み + 行列積)を崩す対価に見合わない。**オフラインの上限測定ツールとしてのみ使い、提出モデルにはしない。**
- **Transformer / 深い NN。** 却下。データ量(数十万局面)と提出環境の時間・依存制約に対して過剰。表現学習が必要なほど入力が生でもない。過学習と推論コストの両面で不利。

## 5. エピソード単位の train/val/test 分割

**採用:** 分割はエピソード(1ゲーム)を単位に行う。同一エピソードから生成された全局面は必ず同じ split に入れる。

**理由:**

- 1ゲームは多数の局面に展開され、隣接する局面は盤面がほぼ同一(1手分しか違わない)かつ最終勝敗ラベルが共通。局面単位でランダム分割すると、**train とほぼ同一のサンプルが val/test に漏れ**、精度を過大評価する典型的なリークになる。
- `extract_training_data.py` の出力は `episode_id` を持つので、エピソード単位の group split はそのキーで実装できる。

**却下した代替案:**

- **局面単位のランダム分割。** 却下。上記リークにより val の数字が楽観的になり、実戦で乖離する。数%の改善を測りたい(ml-agent-plan.md の評価基盤方針)場面で、測定器そのものが甘くなるのは致命的。

## 6. 順位によるサンプル重み付け

**採用:** `extract_training_data.py` が各ペアに付与する `rank_at_fetch` / `leaderboard_score_at_fetch` を使い、上位プレイヤー由来の局面の学習重みを大きくする。

**理由:**

- リプレイは上位中心とはいえ強さに幅がある。「より強いプレイヤーの意思決定・勝敗ほど信頼できる教師」という仮定に基づき、順位/スコアを重みに反映すると、バリューの学習ターゲットの質が上がる。
- データパイプラインが重み用のメタ情報を既に出しているので、追加の取得コストなしに導入できる。

**注意点(効かせすぎない):** 上位に重みを寄せすぎると、実質的に少数のトッププレイヤー・少数デッキの局面ばかりを学ぶことになり、**盤面の多様性が失われて過学習** する。緩い重み付け(順位差を穏やかに反映、下位も 0 にはしない)から始め、val 性能で強度を調整する。重み付けは「効くはず」ではなく層別評価で確認する対象とする。

## 7. 保守的キャリブレーション(温度 T >= 1.0)

**採用:** 学習後、validation 上で温度スケーリング等により予測確率を較正する。ただし **生の見積もりより強気にしない**(温度 T >= 1.0 の制約)。

**理由:**

- 過信した勝率は下流で危険を生む。Step3 の determinization 探索は複数サンプル世界の葉評価を平均して手を選ぶが、バリューが過信していると **本当は不利な手を「勝てる」と誤評価して選ばせる**。リスク判断(サイド計算、リーサル受け)でも過信は致命的。
- チーム方針(確信度は慎重側に倒す = 生の見積もりより強気にしない)と整合。deck_predictor でも「エビデンスが薄い序盤ほどロジットが過信する」現象に対しエビデンス数バケットごとの温度較正を導入済み(`ml_predictor.py` の calibration 節)。同じ思想をバリューにも適用する。
- 本ゲームは序盤局面ほど勝敗との相関が弱い(2 節)ため、そもそも確率は控えめに出るべき。T >= 1.0 はその構造とも整合する。

**却下した代替案:**

- **較正なし(生ロジットの softmax/シグモイドをそのまま使う)、または T < 1.0 で確率を尖らせる。** 却下。探索・リスク判断で過信手を選ばせるため、勝率を下げる方向に働く。argmax(勝ち/負けの判定)自体は温度で不変なので、尖らせる利得はなく害だけがある。

## 8. 将来の拡張との整合

Step1 の設計は後段のステップを縛らないよう、次の2点を意識して選定している(詳細な設計は design.md、ロードマップは ml-agent-plan.md)。

- **エンコーダを「状態特徴」と「選択肢特徴」に分離する。** バリュー(Step1)は状態特徴だけで足りるが、Step2 の模倣ポリシーが扱う行動空間は `SelectData.option` の **可変長・可変個** リストである(`cg/api.py`。`minCount`/`maxCount` も可変)。固定次元の行動分類にはできないため、各選択肢を特徴化して個別スコアリングする形式が自然。Step1 の段階で状態側と選択肢側を分けておけば、Step2 は状態特徴を再利用しつつ選択肢特徴を足すだけで済み、二重実装を避けられる。
- **神視点バリュー + determinization への発展路を残す(3 節の続き)。** Step1 のバリューは公開情報のみだが、Step3 では `search_begin` にサンプリングした具体的な相手手札・山札を渡して世界を確定させ、その全情報既知の葉を神視点バリューで評価する。3 節で神視点学習を「捨てた」のではなく「後段の葉評価用に温存した」のはこのため。公開情報バリューと神視点バリューは用途が異なる別モデルとして、Step3 で改めて設計する。
