## 1. リストワイズ模倣学習(softmax + 交差エントロピー)

**採用:** 同一 `SelectData` 内の各選択肢を独立にスコアリングし、softmax で正規化した上で実際に選ばれたインデックスへの交差エントロピー損失で学習する(step2-design.md §4.1)。

**理由:**

- `SelectData.option` は**可変長・可変個**であり、固定次元の多クラス分類(「選択肢0を選ぶ確率」「選択肢1を選ぶ確率」...)は選択肢数が変わるたびにモデル構造が変わってしまい成立しない。
- 選択肢を「状態特徴 + その選択肢固有の特徴」という共通の入力形式に落とし込めば、モデル自体は「1つの選択肢の良さをスコアにする」関数1つで済み、選択肢数に依存しない。これは Step1 design.md §3.4 が最初から意図していた分離(状態特徴/選択肢特徴)をそのまま活かす形。
- 推論時も同じ構造で動く: `obs.select.option` の各要素にモデルを適用してスコアを出し、`argmax` を返すだけでよい。

**却下した代替案:**

- **固定行動空間への分類。** 却下。選択肢の意味(どのカードか、どの攻撃か)がスロット番号に対応しないため、「スロット3を選ぶ」という学習は無意味。
- **ペアワイズ学習(2つの選択肢のどちらが良いか、を全ペアで学習)。** 却下。選択肢数が多い決定点(手札からのカード選択等)ではペア数が組合せ的に増え、リストワイズ(softmax-CE)で同じ情報をより安く学習できるため不要。
- **選択肢ごとに独立した2値分類(「選ばれるか否か」をロジスティック回帰で学習)。** 却下ではないが不採用。同一 `select` 内の選択肢は互いに排反(1つしか選ばれない)なので、softmax による相対比較の方が問題の構造に合っている。独立2値分類は「どの選択肢も選ばれない/複数選ばれる」確率を排除できず、比較が歪みうる。

## 2. ベースラインに現行 `rule_based_agent` の一致率を使う

**採用:** オフライン評価のベースラインとして、一様ランダムに加えて「記録済み `observation` に対し現行 `rule_based_agent(obs)` を再実行し、プロの選択とどれだけ一致するか」を測る(step2-design.md §5.1)。

**理由:**

- Step1 のベースライン設計(design.md §5.1: 自明な指標を明確に上回ることを要求する)と同じ思想だが、Step2 では「ランダムに勝てるか」だけでは判断材料として弱い。選択肢数が少ない決定点(YES/NO 等)では一様ランダムでも高い一致率が出てしまい、モデルの価値を測れない。
- `rule_based_agent` は observation のみを入力とする関数であり、記録済みリプレイの `observation` に対して**オフラインで安全に再実行できる**(対戦を回す必要がない)。これにより「今のルールベースが上位プレイヤーの判断とどれだけ近いか」という、Step2 が本当に知りたい問い(模倣ポリシーは今のルールベースを超えるか)に直接答えられる。
- 既存コードを**読み取り専用で呼ぶだけ**であり、design.md/step2-design.md の「`rule_based/` は変更しない」制約に抵触しない。

**却下した代替案:**

- **一様ランダムのみをベースラインにする。** 却下。上記の通り、選択肢が少ない決定点で自明に高い一致率が出るため、モデルの付加価値を切り分けられない。
- **現行ルールベースとの対戦(オンライン)で比較する。** 却下(先送り)。対戦リーグ基盤が未整備(step2-design.md §5.2)であり、Step1 と同じ理由(まず単体で精度検証できる指標を固める)で、オフライン一致率を先に確定させる。

## 3. 初期スコープを `maxCount == 1` の単純選択に限定

**採用:** 複数選択(`maxCount > 1`)を Step2 の初期スコープから外し、独立スコアの貪欲法(または既存 `rule_based_agent` への委譲)でフォールバックする(step2-design.md §2.4)。

**理由:**

- 旧 `pairs.jsonl`(1,956 行、全アーキタイプ混在)での実測で `maxCount == 1` が 93.6% を占めた。大半の意思決定点は単純選択であり、複数選択の最適化に開発コストを先に割くのは費用対効果が悪い。
- 複数選択(例: 手札を N 枚捨てる)は選択肢間の**組み合わせ**が意味を持つ場合があり(捨てるカードの組み合わせで手札構成が変わる)、独立スコアリングの枠組みをそのまま当てはめると理論的に最適とは限らない。これは Step2 のリストワイズ・スコアリングという設計そのものの限界であり、無理に押し込むより明示的にスコープ外とする方が誠実。
- Step1 が「まず土台を固める」ために神視点学習や TD 学習を後回しにしたのと同じ順序の判断: まず大部分を占める単純選択で模倣ポリシーの有効性を検証し、複数選択の最適化(組合せ最適化的な拡張)は必要性が確認できてから着手する。

**却下した代替案:**

- **最初から複数選択にも対応する(選択肢集合のサブセット選択問題として定式化する)。** 却下。実装・学習の複雑度が大きく上がる一方、対象決定点の割合は小さく(§2.3 実測で 6.4%)、Step2 の主目的(単純選択での模倣ポリシーの有効性検証)に対して過剰投資。

## 4. モデル: 線形ベースライン → 小型 MLP(共有重み、numpy/純Python 推論)

**採用:** Step1 と同じパターン(design.md §4.1、algorithm-selection.md §4)を踏襲し、まず選択肢特徴のみの線形モデルをベースラインとして作り、次に状態特徴 + 選択肢特徴を入力にした小型 MLP(選択肢間で重み共有)へ拡張する。学習はローカル、提出物は JSON 重み + 純 Python 推論。

**理由:**

- Step1 の algorithm-selection.md §4 で確定した提出環境・依存関係の制約(Kaggle の時間制限、`ml_predictor.py`/`value_model.py` と同じ推論パターンの実績)がそのまま Step2 にも当てはまる。車輪の再発明を避け、同じ経路を使う。
- 選択肢ごとに独立に前向き計算する「重み共有」構造は、選択肢数が可変でもモデルサイズが変わらないという実装上の利点があり、§1 のリストワイズ設計と自然に整合する。

**却下した代替案:**

- **選択肢ごとに別々のモデルを `OptionType` 別に学習する。** 却下(現時点)。特徴量自体は `OptionType` 別に設計する(step2-design.md §3.2)が、モデル(スコア関数)は共有し、特徴の差異で表現する方がパラメータ数・学習データの分断を抑えられる。`SelectContext` 別の評価(§5.1)で特定の種類が著しく弱ければ、その種類だけ個別モデル化を検討する。
- **Transformer 等でカード列を直接エンコードする。** 却下。Step1 と同じ理由(データ量・提出環境制約に対して過剰、手作り特徴で十分な表現力が出る想定)。

## 5. キャリブレーションは Step2 では必須にしない

**採用:** Step1 の温度較正(T >= 1.0)を Step2 では必須要件にしない(step2-design.md §4.3)。

**理由:**

- Step1 のキャリブレーションは「勝率という確率」を過信させないためのもの。Step2 の softmax 出力は「この選択肢集合の中でどれが一番良いか」という相対比較にしか使わず(`argmax` で決定を1つ返す)、確率の絶対値そのものをリスク判断に使う設計にはなっていない。argmax は温度で不変なので、較正しなくても Step2 の意思決定(選択肢を1つ選ぶ)には影響しない。

**却下ではなく先送りにした理由:** Step3 の探索で模倣ポリシーを「相手の行動モデル」や「探索の事前分布」として使う場合、複数候補への確率配分(PUCT の prior 等)が意味を持つようになり、そのときは確率の較正が必要になりうる。Step2 の時点でこれを見越して較正機構を作り込むのは時期尚早(Step1 の「まず公開情報のみでベースラインを確定させ、増分を測ってから追加する」という順序の考え方と同じ)。Step3 設計時に改めて検討する。

## 6. 対戦リーグ(オンライン評価)基盤は Step2 の完了条件に含めない

**採用:** `ml-agent-plan.md` が挙げる評価基盤(500試合以上のリーグ)の構築を、Step2 の完了条件から外す。オフラインの Top-1 一致率(§2 のベースライン込み)のみで PASS/FAIL を判断する。

**理由:**

- Step1 が「config 接続・対戦リーグは Step2/3 で選択肢スコアリングの仕組みが揃ってから」(design.md §5.2、2026-07-20 訂正済み)としていた前提が、Step2 でようやく揃う。しかし評価基盤(リーグランナー)自体は本ブランチ系統にまだ存在せず、これをゼロから作るのは Step2 のスコープ(模倣ポリシーの学習・検証)とは別の作業量を持つ。
- 過去に別系統ブランチ(`feature/ml-architecture-implementation`)で自己対戦データ収集・A/B ハーネスを作った形跡があるが、モジュール構成(`src/decision/` 系)が現行の `ptcg_ai/` とは別物で直接移植できない。掘り起こしと移植の判断は Step2 完了後、必要になった時点(Step2 完了直後、または Step3 着手時)で改めて行う。

**却下した代替案:**

- **Step2 の一部として対戦リーグ基盤も新規に作る。** 却下(先送り)。Step2 の主目的(模倣ポリシーがオフラインで意味のある精度を出すか)を確認する前にオンライン評価基盤へ投資するのは、Step1 の「失敗の切り分けが容易な順序で進める」という基本方針(algorithm-selection.md §1)に反する。オフライン PASS を確認してから、対戦リーグという次の可動部を足す。

## 7. カード identity の学習済み埋め込み(card_embedding、2026-07-20 追加)

**背景:** Step2 初回のオフライン評価(PASS 判定後、step2-offline-evaluation.md)で、`select_type=MAIN`(全体の61.6%、最も精度が低いカテゴリ)をさらに `OptionType` 別に分解したところ、`PLAY`(手札からカードを出す、n=2,350)が精度39.0%、`ATTACH`(どうぐ/エネルギー装着、n=600)が精度20.5%と際立って低いことが判明した。原因は、`encode_options()` の選択肢特徴がカード種別(ポケモン/アイテム/どうぐ/サポート/スタジアム/基本エネルギー/特殊エネルギー)の7分類までしか区別しておらず、同じ種別内の個別カード(「博士の研究」と「ハイパーボール」等)やエネルギーの種類(草/闘/超 等)を一切識別できていないため。

**採用:** `CardData.cardId` をキーにした**学習済み埋め込み(embedding)** を選択肢特徴とは別枠で追加する(`encoder.encode_option_card_ids()`、`policy_model.py` の `card_embedding` ブロック)。次元は8に固定(判断者: 本方針の担当者。パラメータ数は `(card_id_max+1) × 8` 程度で、学習データ規模(147,705件)に対して過大ではない)。

**理由:**

- カード名をロジックに直書きする(if/elseでカード固有の分岐を書く)のではなく、`card_id` を特徴としてモデルに渡し、**データから個別カードの傾向を学習させる**。これは `attack_features.py` が弱点・抵抗力判定で `card_cache.get_card(attacker.id).energyType` を参照している(カードID自体は使うが、特定カードの名前・効果をハードコードしない)のと同じ思想であり、design.md/ml-agent-plan.md の「カード名・カードIDのハードコードはしない」方針(ロジックの分岐にカード名を使わない、という意味)には抵触しない。
- **状態特徴・選択肢特徴の連続値ベクトルとは別チャンネルにする。** カードIDは連続値ではなく離散的な識別子であり、平均・標準偏差で標準化する対象ではない(隣接するIDに意味的な連続性は無い)。埋め込みという別の入力経路にすることで、既存の `encode_options()`(65次元、テスト済み・安定)を変更せずに追加できる。

**将来の拡張(デッキ非依存性)を重視した設計判断:**

- 埋め込みテーブルは**学習に使ったデッキ(フーディン)ではなく、ゲーム全体のカードデータ(`all_card_data()`)を基準にサイズを決める**(`card_id_max = max(c.cardId for c in all_card_data())`、コードにハードコードせず動的に計算)。これにより、将来別のデッキのリプレイで Step2 を再学習する場合も、`encoder.py`/`policy_model.py`/学習パイプラインのコードは一切変更不要で、埋め込みテーブルの中身(学習された値)だけが新しいデータに応じて変わる。
- 学習データに出現しないカード(そのデッキで使われないカード)の埋め込みは未学習のまま(初期値近辺)になるが、これは安全側の劣化であり、クラッシュや異常な出力にはつながらない(`policy_model.py` の `_card_embedding()` が範囲外・未識別の `card_id` を予約枠 index 0 にフォールバックする設計とも整合)。

**却下した代替案:**

- **学習データ(フーディンデッキ)に出現するカードだけの小さな one-hot/埋め込みテーブルにする。** 却下。実装は簡単だが、別デッキで再学習する際にテーブルの再設計(カード集合の洗い出し・インデックス割り当てのコード変更)が必要になり、「デッキが変わってもコードは変えずに済む」という拡張性の要件に反する。ゲーム全体のカードプールは1,267種(2026-07-20時点)と埋め込みテーブルとして十分小さいため、全カードを対象にする追加コストはほぼ無い。
- **カード効果テキスト(`CardData` に効果テキストがあれば)を汎用的にパースして特徴化する(`attack_features.py` の可変ダメージ推定と同様のアプローチ)。** 却下(見送り)。トレーナーズカードの効果テキストの構造化はポケモン技のダメージ推定より遥かに多様(ドロー・サーチ・破棄・回復…)で、汎用パーサの実装コストが埋め込みより大幅に高い。まず埋め込みで識別情報の欠如という核心の問題を解消し、効果テキストの構造化は効果が頭打ちになってから検討する。
- **もっと大きい埋め込み次元(例: 32)にする。** 却下(現時点)。学習データ規模・過学習リスクとのバランスから8次元を初期値とし、オフライン評価で効果を確認してから次元を調整する(埋め込み次元のチューニングは次イテレーションの候補として残す)。
