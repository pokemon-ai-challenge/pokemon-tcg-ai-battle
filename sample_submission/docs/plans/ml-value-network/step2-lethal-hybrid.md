## 1. 動機

Step2(模倣ポリシー)は、ローカル対戦リーグ(同一デッキのミラー戦、500試合)で
`rule_based` に86.4%勝利した(step2-offline-evaluation.md §8)。しかし実際にKaggleへ
提出したところ(2026-07-20、submission 54857624)、実戦相手28試合(自分同士のミラー戦1件を除く)
での勝率は **14勝14敗 = 50.0%** だった。

この乖離の説明として最も筋が通るのは、step2-offline-evaluation.md §7.3 で既に判明していた
非対称性である: `select_type=MAIN` を実際に選ばれた `OptionType` 別に分解すると、
**`ATTACK`(技選択)だけは `rule_based` が模倣ポリシーを圧倒的に上回っている**
(`rule_based` 94.9% vs 模倣ポリシー60.5%、プロの選択との一致率)。`rule_based` は
確定リーサル探索(`ptcg_ai/search/lethal_simple.py`、以下 lethal_simple)を持っており、
技選択は「ダメージ計算+探索」で最適解が求まりやすい領域である一方、模倣ポリシーは
リプレイからのパターン学習でしかなく、同じ精度の打点計算・詰み筋の読みを内在的には持たない。

ミラー戦(同一デッキ同士)では、模倣ポリシーが他の局面(PLAY/ATTACH/ABILITY/EVOLVE/END)で
`rule_based` を大きく上回る優位性がこの弱点を覆い隠していたが、**相手デッキが多様な実戦では
「確定していたリーサルを逃す」「自分の脅威を見誤る」といった致命的なミスの頻度がより強く
勝敗に響いている可能性が高い**(明確な統計的証明ではなく仮説だが、実戦データ(接戦が多く
速攻で崩れているわけではない)とも矛盾しない)。

## 2. 方針: Step3(determinization探索)ではなくハイブリッド化を先に行う

Step3(相手の非公開情報をサンプリングした探索、ml-agent-plan.md ロードマップ「3. 探索との結合」)
は最終的に取り組む価値があるが、サンプラー・探索中の相手行動モデル・時間管理など未着手の部品が
多く、着手から検証可能になるまでの作業量が大きい。一方、`rule_based` が既に持っている
確定リーサル探索(lethal_simple)は**team共通インターフェースとして最初から汎用設計されている**
(後述§3)。模倣ポリシーが弱いと分かっている一点(確定リーサルの見逃し)だけを、既存の実績ある
部品で埋める方が、低コスト・低リスクで実戦への効果を早く確認できる。

**したがって、Step3着手より先に、`ml_policy_agent` に lethal_simple を組み込むハイブリッド化を
行う。** これはStep3を無駄にしない(lethal_simple は将来Step3の「葉ノードでの確定的な戦術判断」
としてもそのまま使える)。ハイブリッド化後に再度実戦検証し、なお不足があればStep3に進む。

## 3. 既存の仕組み(参照実装、変更しない)

`ptcg_ai/action_selection/selector.py` の `select_action()` が `rule_based_agent` から
呼ばれる際の流れ:

1. `core.config.load_config()` で config(既定 `configs/rule_lethal.json`)を読み、
   `lethal_search` セクション(`enabled`/`module`/`time_limit_ms`/`max_depth` 等)を取り出す。
2. `enabled` かつ `obs.current is not None` なら、`lethal_simple.search(obs.current, select.option, context)`
   を呼ぶ。`context` は `{"observation": obs, "config": lethal_config, "hidden_state_factory": ...}`
   ( `hidden_state_factory` は `hidden_information.search_state_stub.build_dummy_search_state(obs, full_deck)`
   を返す0引数callable。相手の非公開情報はまだ本物の推定に接続されておらず、ダミーの仮データで埋める
   一時的なスタブ——lethal_simple 自体はこれを外から受け取るだけで、中身がスタブかどうかは関知しない)。
3. `lethal_simple.search()` は「今の自ターン内で確定的に勝てる手順があるか」を探索し、あれば
   最初の選択(インデックス列)を、無ければ `None` を返す(タイムアウト・エラー時も `None`。
   例外を投げない設計)。`select_action()` 側も `try/except` で二重に保護している。
4. 有効な行動が返れば(`is_valid_action()` でcontract検証: `minCount<=len<=maxCount`・重複無し・
   範囲内)それを採用。無ければ通常のポリシー(`rule_based` の場合は `router.route(obs)`)に委ねる。

**重要: `lethal_simple.py` はモジュールdocstringで「Entry point (team common interface)」と
明記されており、`rule_based` 専有ではなく最初からチーム共通の再利用可能インターフェースとして
設計されている。** `search_state_stub.build_dummy_search_state()` も同様に汎用(呼び出し元を
問わない、一時的なプレースホルダ実装であることが明記されている)。したがって
`ptcg_ai/search/`・`ptcg_ai/hidden_information/` から直接importして呼ぶことは、
`rule_based/`・`action_selection/` を変更・依存させない方針(step2-design.md §1)に抵触しない
(これらは `action_selection` クラスタの外にある共有部品)。

## 4. 設計: `ml_policy_agent.py` への組み込み

`selector.select_action()` は最終フォールバックが `router.route(obs)`(rule_baseのルール
エンジン)に固定されており、そのまま流用すると模倣ポリシーではなくルールベースに落ちてしまう。
そのため `selector.py` は変更・import せず、**「lethal_simple を試し、無ければ通常の処理へ」という
同じ制御フロー(グルーコード)だけを `ml_policy_agent.py` 内に複製し、フォールバック先だけを
`PolicyModel` によるスコアリングに差し替える**。

```
ml_policy_agent.agent(obs)
  └─ obs.select is None            → デッキ選択(既存のまま、変更なし)
  └─ obs.select is not None
       ├─ _try_lethal(obs)         → 確定リーサルが見つかれば採用(NEW)
       └─ 見つからなければ         → 既存の PolicyModel スコアリング(maxCount==1: argmax /
                                       maxCount>1: 貪欲フォールバック、変更なし)
```

`_try_lethal(obs) -> list[int] | None` は `selector.select_action()` の手順1〜4をそのまま
複製する(config読み込み・`lethal_simple.search()` 呼び出し・contract検証・例外保護)。差分は
「フォールバック時に `None` を返して呼び出し元(`ml_policy_agent`)に処理を戻す」点のみ
(`router.route()` は一切呼ばない)。`is_valid_action()`(contract検証、6行程度の純粋関数)も
`selector.py` からimportせず複製する(`action_selection/` への依存をゼロに保つため)。

デッキ(`hidden_state_factory` に渡す `full_deck`)は既存の `ml_policy_agent._get_model()` と
同様のキャッシュパターンで取得する(`read_deck_csv()` を毎回呼ばない)。

### configの扱い

新規config(`configs/ml_policy.json`)は作らない。`lethal_search` の設定
(time_limit_ms・max_depth 等)は `rule_based` 専用の値ではなく探索そのものの汎用パラメータで
あり、既定config(`configs/rule_lethal.json`)をそのまま `core.config.load_config()` の既定
呼び出し(引数なし)で読む。config名に `rule_lethal` という名前が付いているのは既存の命名
(Step1以前からの既定名)であり、意味上は「探索込みの標準設定」を指す。将来紛らわしくなる
ようなら config のリネームを検討するが、本タスクのスコープ外とする。

## 5. スコープ外・既知の限界

- **「確定リーサルを逃さない」ことしか直さない。** 確定リーサルが無い局面でどの技を選ぶか
  (複数の非リーサル技から最善を選ぶ判断)は引き続き模倣ポリシーのスコアリングに委ねる。
  ATTACK の一致率(60.5%)が丸ごと94.9%に近づくわけではない。
- **相手の非公開情報はダミー(スタブ)のまま。** `build_dummy_search_state()` は相手の手札・
  山札を実在しないプレースホルダで埋める。これは `rule_based` が現在運用している内容と全く同じ
  制約であり、本タスクで新たに悪化するものではないが、認識しておくべき前提として明記する。
  相手の脅威(相手が次ターンに何をしてくるか)を読む探索ではなく、あくまで**自分のこのターン
  内で確定的に勝てるかどうか**の判定に限定される(lethal_simple のスコープそのもの)。
- **PLAY/ATTACH/CARD 等、他の弱点には影響しない。** これらは引き続き model の精度に依存する。
- **オフライン評価(`kaggle_replays/policy_net/evaluate.py` の Top-1一致率)は今回のスコープでは
  再計測しない。** 変更するのは推論時のエージェント挙動(`ml_policy_agent.py`)であり、
  `PolicyModel` 自体・学習パイプラインには手を入れないため、オフライン精度の数値(59.2%等)は
  そのまま有効。効果検証はオンライン(ローカル対戦リーグ・実際のKaggle再提出)で行う。

## 6. 検証計画

1. **単体テスト**: `_try_lethal()` が (a) リーサル局面で正しい行動を返す、(b) リーサルが無い
   局面で `None` を返し通常のスコアリングにフォールバックする、(c) `lethal_search.enabled=false`
   のconfigでは常に `None` を返す、(d) 例外時にクラッシュせず `None` を返す、ことを確認する。
   `sample_submission/tests/unit/test_ml_policy_agent.py` に追加する。
2. **ローカル対戦リーグでの再検証**(`league/run_league.py`、既存のまま変更不要):
   `ml_policy`(ハイブリッド後) vs `rule_based` を同一デッキミラー戦500試合で再実行する。
   期待: 追加のみで既存ロジックを壊していないため、勝率は**従来(86.4%)と同等かそれ以上**に
   なるはず(悪化していたら実装のバグを疑う)。`ml_policy` vs `ml_policy`(旧: ハイブリッド無し
   vs 新: ハイブリッド有り、で比較)を追加で回せると、ハイブリッド化単体の純粋な効果も測れる
   (時間があれば実施)。
3. **実戦(Kaggle再提出)**: ビルド・提出手順は `sample_submission/README.md` 「CLIから提出する
   場合」を参照。提出後、`kaggle_replays/fetch_my_episodes.py` で新しい対戦ログを取得し、
   前回(50.0%、n=28)と比較する。サンプルが少ないうちは断定的な判断をしない(既に一度、
   小標本で早計な判断をしないよう注意喚起済み)。

## 6.5 実装後の計測結果(2026-07-21)

### 探索の発火頻度・健全性

40試合(`ml_policy` vs `rule_based`、同一デッキ)で計測:

| 指標 | 値 |
|---|---|
| ポリシー意思決定点 | 2313 |
| lethal 探索が実際に走った回数 | 132(残りサイド>2 等の安価なガードで大半は即 return) |
| リーサル検出(found) | 47 |
| ポリシーを上書きした回数 | 45(約1.1回/試合) |
| timeouts | 66(50%) |

**発火はしている**(no-op ではない)。オーバーヘッドは 177ms/試合程度で無視できる。

### `time_limit_ms` は上げても無意味(反証済み)

timeout 率が50%と高かったため 100/300/1000ms を比較したが、**timeout 率も検出率もほぼ横ばい**
(57/110・71/141・59/123、found 36%/36%/39%)。時間切れは「あと少しで解けた」のではなく
探索空間が単に広すぎるケースであり、予算を10倍にしても検出は増えず所要時間だけ10倍
(6s→55s/40試合)になる。**100ms のまま据え置く。**

### `max_remaining_prizes` は 2 -> 3 に引き上げ(採用)

| 設定 | searches | found | timeouts | 所要 |
|---|---|---|---|---|
| max_remaining_prizes=2 | 95 | 28 | 48 | 5.0s |
| max_remaining_prizes=3 | 410 | 55 | 296 | 30.1s |

検出が約2倍になる。懸念は「相手の非公開情報がダミーのため、手順が長くなる3サイド
リーサルは実際には成立しないのではないか」だったが、健全性を直接計測したところ:

| 設定 | リーサル発火した試合の勝率 | 発火しなかった試合の勝率 |
|---|---|---|
| max_remaining_prizes=2 | **32/32 = 100%** | 20/28 = 71.4% |
| max_remaining_prizes=3 | **40/40 = 100%** | 17/20 = 85.0% |

`verify_rejects=0`。誤検出は観測されなかった(ただし「発火した試合=既に優勢」という
選択バイアスは含むため、100% は探索の健全性の証拠であって勝率改善量の推定値ではない)。
所要は 750ms/試合程度で許容範囲。

なお `max_remaining_prizes` を共有 config(`configs/rule_lethal.json`)側で変更すると
`rule_based` の挙動まで変わってしまうため、**`configs/ml_lethal.json` を新設**して
`ml_policy` だけがこれを読む形にした(§4「新規configは作らない」からの意図的な逸脱)。

### 実戦ログ再分析で判明した別の敗因(本タスクのスコープ外)

前回提出(54857624、14勝14敗)の28試合を再分析したところ、**負け14件のうち4件(29%)が
山札切れ**だった。他に2件がベンチ壊滅。勝ち試合と負け試合のターン数分布はほぼ重なっており
(平均10.6 vs 10.9)、速攻で崩されているわけではないという §1 の前提とは整合する。

**訂正(2026-07-21、再検証)**: 当初「山札切れ4件のうち1件はサイドを5枚取った状態からの
敗北」と記録していたが、これは誤りだった。当該記録は `turn=0`(対戦開始前のセットアップ処理、
`State.turn` のドキュメント上「先攻1ターン目より前の時間」を指す)の観測を含めて `prize` 配列の
最小長を取ってしまった測定ミスに起因する(セットアップ中は prize 配列がまだ正しく埋まって
いない一時的な状態を拾ってしまう)。`turn>=1` かつ自分が実際に意思決定した(`status=="ACTIVE"`)
局面のみに絞って山札切れ4試合を再測定したところ、実際の最大サイド獲得数はそれぞれ
3枚・1枚・3枚・2枚で、いずれも5枚には遠く及ばなかった。**「優勢だった試合を落とした」という
根拠は無く**、むしろ拮抗ないし劣勢の試合が長引いて山札切れに至ったと見るのが妥当。

一方で「確定リーサルの見逃しが敗因」という §1 の仮説そのものは、**このリプレイデータでは
確認も反証もできない**(各 ATTACK 選択時点でリーサルが存在したかの判定には
`lethal_simple` 相当の再計算が必要)。§1 は依然として仮説である。

ただし山札切れ敗北は `max_remaining_prizes` 引き上げの追加根拠になる: 勝ち切れる局面を
1ターン早く畳めるほど、グラインドして山札切れで落とす負けを減らせる。
**山札切れそのものへの対処(デッキ構築・ドロー枚数の見直し)は本タスクのスコープ外**とし、
別途検討する。

## 6.6 実戦ログでの比較(2026-07-21、両提出の追加データ取得後)

`kaggle competitions episodes <submission_id>` で提出ごとにエピソードIDを正確に分離して
再分析した(2提出間でエピソードIDの重複は無いことを確認済み)。

| | imitation-only(54857624) | hybrid(54860450) |
|---|---:|---:|
| 実戦試合数(ミラー戦除く) | 39 | 24 |
| 勝率 | 22/39 = 56.4% | 11/24 = 45.8% |
| 95%信頼区間(Wilson) | [41.0%, 70.7%] | [27.9%, 64.9%] |
| 山札切れ負けの割合 | 4/17敗 = 23.5% | 5/13敗 = 38.5% |
| 平均ターン(勝ち/負け) | 10.7 / 10.9 | 10.5 / 11.2 |
| 対戦相手の平均レーティング | 591.2(n=39) | **666.7(n=23)** |

**単純比較してはいけない。** 両信頼区間は大きく重なっており(統計的に有意差なし)、
かつ**対戦相手の平均レーティングがhybrid側で75点も高い**(自分のレーティングが
557→600に上がった結果、より強い相手とマッチングされるようになったため)。
勝率が下がったように見えるのは相手プールの強さの違いで大部分/全部説明できる可能性があり、
現時点のデータだけでは「hybridが実戦で効いたか」を判定できない。

エラー・タイムアウト起因の異常終了は0件(hybrid側24試合を個別確認、`statuses`に
異常値なし)。lethal_search追加によるオーバーヘッドが実戦で問題化した形跡は無い。

山札切れ負けの割合は両提出とも高水準(23.5%/38.5%)で、依然として本タスクのスコープ外の
別問題として残っている(§6.5参照、ただし「優勢を無駄にした」根拠は無いことは既に訂正済み)。

## 6.7 核心仮説の直接検証(2026-07-21): 支持されず

§1 の動機は「見逃しリーサルが実戦の敗因になっている」という仮説だったが、これまで
間接的な勝率比較でしか裏付けを試みておらず(しかも§6.6で交絡ありと判明)、直接検証は
未実施だった。ハイブリッド化前の提出(54857624)の負け試合17件について、自分が
`SelectType.MAIN` を選べた**全ての意思決定点**(合計450件超)で実際に
`lethal_simple.search()`(実戦と同一の `configs/ml_lethal.json` 設定)を呼び、確定リーサルの
有無を直接判定した(このリポジトリ側で再実行し再現性も確認済み)。

**結果: 17敗中、確定リーサルを見逃していた試合は1件(5.9%)のみ。** しかもそのケース
(episode 87119769)も、見逃した時点(ターン7)から実際の敗北(ターン8)までの差はわずか
1ターン。残り16件(94%)は、負けるまでのどの局面でも確定リーサル自体が存在しなかった。

**結論: 「見逃しリーサルが実戦の敗因」という §1 の核心仮説は支持されない。** 実戦勝率が
ローカルミラー戦(86%超)より大幅に低い(約50%台)理由は、リーサルの見逃しではなく、
別の要因(§6.6で判明した対戦相手の強さ・多様性、山札切れ、あるいは学習データがフーディンの
ミラー戦想定に偏っていることによる非ミラー対面での弱さ等)にある可能性が高い。

**ただし、本タスク(ハイブリッド化)自体を後悔する結果ではない。** 実装はローカルで健全性が
確認済み(§6.5)、実戦での悪影響も無く(§6.6)、コストの低い保険として妥当な投資だった。
単に「実戦のギャップを説明する主因ではなかった」というだけであり、次の優先度判断の材料として
