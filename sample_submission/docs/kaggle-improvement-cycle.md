# Kaggle ログ改善サイクル（自動実行プロセス）

このファイルは **Kaggle の試合ログが渡されたときに自動で実行するアルゴリズム** を定義します。  
ユーザーが `*-0.json` / `*-1.json` ファイルのパスを提示したら、このファイルを読み込み  
**ステップ 1 から順番に全ステップを自動実行する**。  
各ステップには **担当エージェント** が明示されており、引き継ぎ先も指定されている。

---

## 実行トリガー

ユーザーが以下のどれかを提示したとき：

- Kaggle から取得した `{game_id}-0.json` や `{game_id}-1.json` ファイルのパス群
- Kaggle の成績ページのスクリーンショット（試合数・スコア等）
- 「Kaggle の結果を見て改善して」という指示

---

## エージェント役割分担の全体像

```
[渡されたKaggleログ]
        ↓
[Step 1] ログ解析
  担当: 提出後改善AI (Sonnet)
  → 勝敗・相手アーキ・ゲーム長 を抽出、集計表を作成
        ↓
[Step 2] パターン分析
  担当: ベンチマーク分析AI (Haiku)
  → アーキ別勝率集計・ローカルとの乖離比較・敗北パターン分類
        ↓
[Step 3] 改善優先度の決定
  担当: 提出後改善AI (Sonnet)
  → 判断ルールに従い「何を1つ直すか」を決定
        ↓
[Step 4a] ログ詳細解析（乖離・バグ疑いのとき）
  担当: デバッグAI (Sonnet)      ← 全敗・乖離10%+・バグ疑い のときのみ
  → 悪手ターンの特定・修正方針の言語化
        ↓
[Step 4b] 戦術方針の策定（新アーキ対策・戦略変更のとき）
  担当: 戦術評価AI (Sonnet)      ← MatchupPolicy新規追加・重み再設計のときのみ
  → DeckPlan の変更案・対策方針の言語化
        ↓
[Step 4c] コードの実装
  担当: コーディングAI (Sonnet)
  → matchup_policy.py 等を実際に変更する
        ↓
[Step 4d] レビュー
  担当: 合理性チェックAI (Haiku)
  → 不正選択・型エラー・エッジケースがないか確認
        ↓
[Step 5] ローカルベンチマーク検証
  担当: ベンチマーク分析AI (Haiku / Sonnet)
  → 30試合計測 → 採否判定
        ↓
[Step 6] ドキュメント更新
  担当: 提出後改善AI (Sonnet)
  → STATUS.md / ORCHESTRATOR.md / strategy-knowledge.md を更新
        ↓
[Step 7] 次サイクル準備
  担当: 提出後改善AI (Sonnet)
  → バックログ登録 + Kaggle 提出チェックリスト確認
```

## ステップ 1：ログの解析

**担当エージェント:** 提出後改善AI (Sonnet)  
**次へ:** ステップ 2（ベンチマーク分析AIへ引き継ぎ）

### 1-1. ファイルの識別

渡されたファイルリストから `-0.json` / `-1.json` を特定する。

| ファイル名 | 意味 |
|-----------|------|
| `{id}-0.json` | 我々が **Player 0**（先攻 = 奇数ターンに行動） |
| `{id}-1.json` | 我々が **Player 1**（後攻 = 偶数ターンに行動） |
| `{id}.json` | フルリプレイ（超大型ファイル・読まない） |

> `{id}.json` のみ渡された場合は「`-0` / `-1` のログファイルを取得してください」とユーザーに依頼する。

### 1-2. 各試合の勝敗・情報の読み取り

各 `-N.json` を `Read` ツールで読み込み、以下を抽出する。

**相手アーキタイプ:**  
`opp_arch=` を含む TRACE 行を検索し、最後に出現した値を使う。  
（例: `reason=score=10 opp_arch=crustle` → `crustle`）

**勝敗判定（最終エントリの `stderr` から）:**

| 最終 TRACE の内容 | 判定 |
|-----------------|------|
| `reason=pick_N`（N ≥ 1） | **勝利** — 最後のサイドカード取得 |
| `reason=end_turn` で終了 | **敗北** |
| `reason=attack` で終了（直後に `pick_N` なし） | **敗北** |
| `reason=use_ability` で終了 | **敗北** |
| エントリが 15 行以下かつ turn ≤ 4 | **不明**（相手エラー/タイムアウトの可能性） |

**ゲーム長:** 最終エントリの `turn=N` の値。

**低スコアSWITCH回数:**  
`ctx=SWITCH sel=X reason=score=Y` のうち、Y ≤ 5 の行を数える。

### 1-3. 集計表の作成（必ず出力する）

```
| ゲームID   | P# | 相手アーキ      | 勝敗 | ターン | 根拠              |
|-----------|----|--------------|----|------|----------------|
| 81976680  | P1 | dragapult_ex  | 勝  | 18   | pick_3 取得     |
| 81977172  | P1 | ogerpon_bullet| 敗  | 26   | attack後空行終了 |
...
```

**→ この表をそのままステップ 2（ベンチマーク分析AI）に渡す。**

## ステップ 2：パターン分析

**担当エージェント:** ベンチマーク分析AI (Haiku — 解釈が必要な場合は Sonnet)  
**入力:** ステップ 1 の集計表  
**次へ:** ステップ 3（提出後改善AIへ引き継ぎ）

### 2-1. アーキタイプ別集計

```
アーキタイプ別勝率:
  dragapult_ex:    X勝 Y敗 (Z%)
  crustle:         X勝 Y敗 (Z%)
  ogerpon_bullet:  X勝 Y敗 (Z%)
  ...
  合計:            X勝 Y敗 (Z%)
```

不明試合はカウントから除外し「N件: 相手エラーの可能性」と記録する。

### 2-2. ローカルベンチマークとの比較

`docs/STATUS.md` の「アーキタイプ別勝率詳細」と照合する。

| 相手 | Kaggle実戦 | ローカル基準 | 乖離 | フラグ |
|-----|-----------|------------|------|-------|
| dragapult_ex | % | 81% | % | |
| crustle | % | 73% | % | |
...

乖離の判定：

| 乖離 | フラグ |
|-----|-------|
| −10%以上（Kaggle が低い） | `[要調査]` |
| ±5% 以内 | 許容範囲 |
| +10%以上（Kaggle が高い） | ローカル計測が少ない可能性 |

### 2-3. 敗北パターンの分類

負けた試合のログから以下を分類する：

| パターン | 判定条件 | 意味 |
|---------|---------|------|
| 超短期敗北 | turn ≤ 10 で敗北 | 序盤の事故・先手不利 |
| 長期膠着敗北 | turn ≥ 20 で敗北 | 詰め切れない・リソース切れ |
| 低スコアSWITCH多発 | SWITCH score ≤ 5 が 3 回以上 | 交代判断の消極さ |
| 攻撃なしで敗北 | `reason=attack` がほぼない | エネルギー不足/進化不足 |
| 特定アーキに全敗 | そのアーキに 0勝 N≥3敗 | MatchupPolicy 未対応 |

**→ 2-1 / 2-2 / 2-3 の結果をまとめてステップ 3（提出後改善AI）に渡す。**

## ステップ 3：改善優先度の決定

**担当エージェント:** 提出後改善AI (Sonnet)  
**入力:** ステップ 2 のパターン分析結果  
**次へ:** 改善タイプに応じてステップ 4a / 4b / 4c のいずれかへ

以下を**上から順に**評価し、最初に該当したものを今回の改善対象とする。

```
優先度 高:
  1. 特定アーキへの勝率が 0%（試合数 ≥ 3）
     → MatchupPolicy 追加 → ステップ 4b（戦術評価AI）へ

  2. Kaggle 勝率がローカルより −10%以上（試合数 ≥ 5）
     → ログ詳細解析 → ステップ 4a（デバッグAI）へ

  3. 特定アーキへの勝率が 50% 以下（試合数 ≥ 3）
     → 戦術方針見直し → ステップ 4b（戦術評価AI）へ

優先度 中:
  4. 全体勝率がローカルより 5〜10% 低い（試合数 ≥ 10）
     → ログ詳細解析 → ステップ 4a（デバッグAI）へ

  5. 超短期敗北が 30%+ の試合で発生
     → 序盤セットアップの見直し → ステップ 4b（戦術評価AI）へ

優先度 低:
  6. 長期膠着敗北が多い・低スコアSWITCH多発
     → 終盤判断の調整 → ステップ 4b（戦術評価AI）へ

  7. 改善余地がない / 試合数が少なすぎる（< 5試合）
     → STATUS.md を更新して今回のサイクルを終了
```

> **デッキ構成の問題（カード不足等）が疑われる場合は人間に確認を求める。**  
> デッキ変更はコードで自動化できないため、このサイクルでは扱わない。

## ステップ 4a：ログ詳細解析

**担当エージェント:** デバッグAI (Sonnet)  
**入力:** 敗北した試合の `-N.json` ファイル群  
**実行条件:** 優先度 2 / 4 のとき（ローカルとの大きな乖離・バグ疑い）  
**次へ:** ステップ 4c（コーディングAI）へ修正依頼を渡す

デバッグAI は `docs/agents/debug-agent.md` に従って動作する。  
このステップでは**コードを変更しない**。修正の方向性を言語化して終了する。

**引き継ぎ時に渡すもの:**

```
- 問題のターン番号・コンテキスト名
- 観察した動作（何が起きたか）
- 推定原因のカテゴリ（BUG / LOGIC_ERROR / WRONG_PRIORITY 等）
- コーディングAI への修正依頼の内容
```

---

## ステップ 4b：戦術方針の策定

**担当エージェント:** 戦術評価AI (Sonnet)  
**入力:** ステップ 3 の優先度判定 + 対象アーキタイプ名  
**実行条件:** 優先度 1 / 3 / 5 / 6 のとき（MatchupPolicy 新規・戦略変更）  
**次へ:** ステップ 4c（コーディングAI）へ方針を渡す

戦術評価AI は `docs/agents/tactics-agent.md` に従って動作する。  
このステップでは**コードを変更しない**。対策方針を言語化して終了する。

以下を検討・出力する：

- 対象アーキタイプの脅威（どのポケモン・どの攻撃が問題か）
- `MatchupOverride` の設定案（`max_bench_size` / `boss_rush` / `boss_rush_target_ids`）
- ターゲット候補のカードIDは `src/knowledge/meta_decks.py` の `DECK_RECIPES` から特定する
- `only_for_decks` が必要かどうか（マリィ専用 or Lucario専用 or 全デッキ共通）
- `docs/strategy-knowledge.md` への追記事項

**ターゲット選択の指針:**

| パターン | 対処 |
|---------|------|
| 進化前の小型Basic（HP ≤ 70） | boss_rush で引き出してワンパン |
| エネルギー供給役（メガニウム・ソルロック等） | 取ると相手の攻撃力が落ちる |
| EX ポケモン（2枚サイド） | 場に出たら即攻撃優先 |

**引き継ぎ時に渡すもの:**

```
- 実装する MatchupOverride の設定値（フィールド名と値）
- ターゲットのカードID（boss_rush_target_ids）
- 変更対象ファイル名（matchup_policy.py 等）
- strategy-knowledge.md への追記内容
```

---

## ステップ 4c：コードの実装

**担当エージェント:** コーディングAI (Sonnet)  
**入力:** ステップ 4a または 4b の修正方針  
**次へ:** ステップ 4d（合理性チェックAI）

コーディングAI は `docs/agents/coding-agent.md` に従って動作する。

**MatchupPolicy 追加の場合（最頻パターン）:**

```python
# src/knowledge/matchup_policy.py の MATCHUP_OVERRIDES に追加
"<アーキタイプ名>": MatchupOverride(
    max_bench_size=2,                                    # ベンチ上限（ex散布対策）
    boss_rush=True,                                      # ボスの指令優先
    boss_rush_target_ids=[XX],                           # ターゲットのカードID
    only_for_decks=frozenset({"maries_obstagoon_ex"}),  # デッキ限定の場合
),
```

実装後に `docs/strategy-knowledge.md` に知見を記録すること（コードだけ書いて終わりにしない）。

**引き継ぎ時に渡すもの:**

```
- 変更したファイルパス・行番号
- 変更の概要（何をどう変えたか）
- 合理性チェックAI に確認してほしい観点
```

---

## ステップ 4d：レビュー

**担当エージェント:** 合理性チェックAI (Haiku)  
**入力:** ステップ 4c の変更内容  
**次へ:** 問題なければステップ 5（ベンチマーク分析AI）へ / 問題あればステップ 4c へ差し戻し

合理性チェックAI は `docs/agents/review-agent.md` に従って動作する。

**確認観点（このステップ固有）:**

- `matchup_policy.py` の `only_for_decks` がデッキ名と一致しているか（誤植でスルーされるバグ多発）
- `boss_rush_target_ids` のカードIDが `meta_decks.py` の実在IDと一致しているか
- 不正選択（インデックス範囲外）が起きないか
- 既存アーキタイプの動作に影響していないか

**問題ありの場合:** コーディングAI に差し戻す（ステップ 4c を再実行）。  
**問題なしの場合:** ステップ 5 へ進む。

## ステップ 5：ローカルベンチマーク検証

**担当エージェント:** ベンチマーク分析AI (Haiku — 結果解釈が複雑なら Sonnet)  
**入力:** ステップ 4c の変更済みコード  
**次へ:** 採用 → ステップ 6 / 取り消し → ステップ 4b か 4c へ差し戻し

### 5-1. 検証コマンドの選択

```bash
cd sample_submission

# 特定アーキタイプのみ確認（最速・最低30試合）
python src/tests/run_bench_suite.py --games 30 --decks <対象アーキ名>

# 汎用ロジック変更のとき（両デッキ × 全アーキ）
python src/tests/run_bench_suite.py --games 30

# マリィのみ全アーキ確認
python src/tests/tier_s_benchmark.py --games 30 --my-deck maries
```

### 5-2. 採否の判定ルール

| 結果 | 判定 | アクション |
|-----|------|----------|
| 対象アーキ +5%以上 かつ他アーキが悪化なし | **採用** | ステップ 6 へ |
| 対象は改善したが他アーキが −5%以上悪化 | **条件付き採用** | `only_for_decks` でデッキ限定化して再計測 |
| 変化なし（±3%以内） | **保留** | 試合数を 60 に増やして再計測してから判断 |
| 対象も改善なし、または悪化 | **取り消し** | git で変更を元に戻し、4b で別アプローチへ |

**引き継ぎ時に渡すもの（採用の場合）:**

```
- 計測日・試合数・使用コマンド
- 改善前後の勝率比較テーブル
- 統計的な評価（差が誤差内か否か）
```

## ステップ 6：ドキュメント更新

**担当エージェント:** 提出後改善AI (Sonnet)  
**入力:** ステップ 5 の採用が確定した計測結果  
**次へ:** ステップ 7

以下を**必ず全て**更新する：

### 6-1. `docs/STATUS.md` の更新

1. **「最終更新」行** — 日付と実施内容を1行で記録
2. **「アーキタイプ別勝率詳細」テーブル** — 新しい計測値を上書き
3. **「最近の作業ログ」** — 先頭に新項目を追加（形式: `### YYYY-MM-DD ⑫ <作業名>`）
4. **「今すぐやること」** — 「Kaggle 提出」に更新

### 6-2. `docs/ORCHESTRATOR.md` の更新

「改善履歴」テーブルに1行追加：

```
| v11 | <変更内容の要約> | <ローカル勝率%> | <Kaggle スコア（あれば）> |
```

### 6-3. `docs/strategy-knowledge.md` の更新

新しい知見があれば `[META-XXX]` 形式で追記する。  
ベンチマーク分析AI が「検証済み」と判断した項目は `状態: 検証済み` に変更する。

## ステップ 7：次サイクルの準備

**担当エージェント:** 提出後改善AI (Sonnet)

### 7-1. 未対応課題をバックログに登録

今回対処できなかった優先度 中/低の課題を `docs/STATUS.md` の「アクティブバックログ」に追加する。

### 7-2. Kaggle 提出チェックリスト

以下を確認してから「次は Kaggle に提出してください」とユーザーに報告する：

```
□ deck.csv が提出用デッキと一致しているか
□ main.py の get_deck_plan() が正しい DeckPlan を返すか
□ src/ ディレクトリが main.py と同じ場所にあるか
□ ORCHESTRATOR.md の改善履歴が記録されているか
```

## 繰り返しサイクルのルール

このプロセスは **1 回の Kaggle 結果につき 1 つの改善を実施して終了** する。  
複数の問題が見つかっても、最高優先度の 1 つだけを実装してベンチマーク確認する。  
（複数を同時に変えると、どの改善が効いたか判断できなくなる）

次の Kaggle ログが渡されたときに再びステップ 1 から実行する。

## エージェント別 担当ステップ早見表

| エージェント | モデル | 担当ステップ | 役割の要約 |
|------------|------|-----------|---------|
| **提出後改善AI** | Sonnet | Step 1, 3, 6, 7 | ログ解析・優先度決定・ドキュメント更新・次サイクル準備 |

| **合理性チェックAI** | Haiku | Step 4d | 変更後のコードレビュー |

## 禁止事項

- ログが 5 試合未満のデータで方針を変更しない
- `cg/` フォルダを変更しない
- コードとデッキを同時に変更しない（どちらが効いたか不明になる）
- ステップ 5（ベンチマーク検証）をスキップして「改善した」と報告しない
- `strategy-knowledge.md` の `状態:` を証拠なく「検証済み」にしない
- ステップ 4a〜4d を全部スキップして「MatchupPolicy を直接変えればよい」と判断しない
  （デバッグAI / 戦術評価AI → コーディングAI → 合理性チェックAI の順は守る）
