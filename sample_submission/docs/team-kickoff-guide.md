# 初心者チーム向け：最初の集まりで決めること

この文書は、開発やチーム作業にまだ慣れていないメンバーが多い場合に、**最初の集まりを有意義にするための進行ガイド**です。

[ai-development-roadmap.md](./ai-development-roadmap.md) は「何をどの順で実装するか」を示す中長期ロードマップです。  
この文書は、それとは別に、**最初の会議で何を決めるか、どの順番で話すか、何を会議の成果物にするか**をまとめます。

---

## この文書の役割

- `ai-development-roadmap.md`
  - AIの実装段階
  - 実装の優先順位
  - 完了条件
- この文書
  - 初回会議の進め方
  - 最初にそろえる共通認識
  - タスク分担の決め方
  - 会議後に残すべき文書

`roadmap` に会議運営や細かい合意事項まで全部書くと読みづらくなるため、**会議のやり方は別紙に分ける**方針にします。

---

## 最初の集まりの目的

最初の集まりでは、いきなり実装を始めるのではなく、まず次の3つをそろえます。

1. 最初の目標をそろえる
2. 共通で使う実装ルールをそろえる
3. 並列で進められる分担に落とす

初心者チームでは、ここを飛ばしてすぐ書き始めると、次の問題が起こりやすいです。

- 同じものを別々に作ってしまう
- `main.py` に直接ロジックを書き足して競合する
- テストやログの形式が人によってバラバラになる
- 「何が終わった状態か」が分からない

最初の会議の目標は、**強いAIを作ることではなく、迷わず着手できる土台を決めること**です。

---

## 最初の会議で決めるべきこと

以下の順番で決めると進めやすいです。

### 1. 今回の最初のゴール

最初に決めるのは「今どこまでを目標にするか」です。

初心者チームなら、まずは `Level 0` を最初のマイルストーンにするのが安全です。

```text
Level 0:
- 合法手を返せる
- contextごとに意味のある選択ができる
- DecisionTraceで理由が追える
- 固定シナリオで最低限の確認ができる
```

この会議で確認すること:

- 最初の1〜2週間で目指すのは `Level 0` か
- `Level 1` は次の段階として切り分けるか
- 最初の対象デッキを1つに絞るか

### 2. このリポジトリで触る場所と触らない場所

次に、作業境界をそろえます。

このリポジトリでは、少なくとも次を共有しておきます。

- 主に触るのは `main.py` と、必要なら追加して使う `src/` や `tests/`
- `deck.csv` は使用デッキの定義
- `cg/` はコンペ提供エンジンなので変更しない
- `docs/` は開発用文書

この会議で確認すること:

- `main.py` は提出用の薄い入口として保つか
- 内部ロジックを `src/` に逃がすか
- `cg/` を変更しないことを全員の共通ルールにするか

2人で始めるなら、最初は次のような最小構成を共有しておくと衝突しにくいです。

```text
sample_submission/
├─ main.py                     # 提出用の入口。最小変更にとどめる
├─ deck.csv                    # 使用デッキ
├─ cg/                         # 変更しない
├─ docs/
│  ├─ ai-development-roadmap.md
│  └─ team-kickoff-guide.md
└─ src/
   ├─ decision/                # 手の選び方
   ├─ knowledge/               # カード知識、デッキ方針
   └─ tests/                   # 固定シナリオや簡単な確認
```

この段階では、`src/` の中身がまだ空でも構いません。  
大事なのは「1人は `main.py` と入口の整理」「もう1人は `src/` 側の下書き」というように、作業場所を先に分けられることです。  
`__pycache__` のような実行キャッシュは共有対象ではないため、残さない前提にします。

### 3. 最初に共通化する実装項目

ここが最重要です。  
個別実装より先に、チーム全体で共通に使うものを決めます。

最初に共通化したい候補は次の4つです。

- `SelectContext` ごとのルーター
- カード情報辞書
- `DecisionTrace`
- 固定シナリオテスト

この会議で確認すること:

- どの共通項目を先にチームで作るか
- その共通項目を1人で作るか、2人以上でペアで作るか
- 完成前でも他メンバーが使える最小形をどこに置くか

### 4. 共通インターフェース

並列開発をするなら、先に関数やデータの形を決めます。

最初に決めておきたいもの:

- ルーター関数の入口
- policy関数の引数と戻り値
- `DecisionTrace` の最低限の項目
- `DeckPlan` の最小項目
- テストケース1件あたりの書き方

この会議で確認すること:

- まだ中身が未完成でも、型や返し方だけは固定するか
- ログ形式を1つに統一するか
- テストケースの置き場所を統一するか

### 5. 最低限の品質基準

初心者チームほど、「とりあえず動いた」で止まりやすいので、最低限の確認方法を先に決めます。

最初の段階で決めておきたい基準:

- 例外を出さない
- 不正な選択を返さない
- ログから選択理由が追える
- 固定シナリオで意図した手を選べる

この会議で確認すること:

- 何を満たしたら `Level 0` 完了とするか
- 手元確認だけでよいか、最低限のテストを必須にするか

### 6. 分担の単位

人ごとではなく、**成果物ごとに分ける**方が進めやすいです。

2人チームなら、最初は次のように分けやすいです。

- A: `main.py` の入口整理、ルーター接続、提出境界の維持
- B: `src/` 側の共通ロジック、カード知識、固定シナリオの下書き

人数が増えたら、そのあとで `decision`、`knowledge`、`tests` に分割していけば十分です。

この会議で確認すること:

- 誰が何の成果物を持つか
- 依存関係が強いものを誰が先に出すか
- 1人で抱えすぎる担当がないか

### 7. 連携のルール

分担を決めても、連携方法が曖昧だと止まりやすいです。

最初に決めておきたいこと:

- どのタイミングで統合するか
- 困ったときにどこへ相談するか
- 仕様変更が出たら誰が文書を更新するか

初心者チームなら、次くらいの軽いルールで十分です。

- 毎回いきなり大きくマージしない
- 共通項目を変える前に一度共有する
- 毎日または節目ごとに短く進捗確認する

### 8. 文書の役割分担

文書は最初から増やしすぎると逆に読まれません。  
最初は役割を分けて、少数に絞るのがよいです。

おすすめは次の3種類です。

- `ai-development-roadmap.md`
  - 段階、優先順位、完了条件
- この文書
  - 初回会議の進め方
- 決定事項メモ
  - その会議で何を決めたか

会議で確認すること:

- 「長期方針」と「今回の決定事項」を同じ文書に混ぜないか
- 誰が文書の更新担当になるか
- AIには要約・整形・反映を任せる形にするか

---

## 最初の会議で決めなくてよいこと

初心者チームでは、最初から決める範囲を広げすぎないことも大事です。

最初の会議では、次のものは後回しで構いません。

- Level 2 以降の細かい戦術
- 本格的な探索アルゴリズム
- 相手デッキ推定
- 高度な評価関数
- すべてのカード個別対応

最初は、**Level 0 を作るために必要なことだけ**に絞ります。

---

## 初回会議のおすすめ進行

初心者チームなら、60〜90分程度で次の順番がおすすめです。

### 0. 共有する前提を読む

会議前または会議の最初に、最低限次を全員で確認します。

- `sample_submission/README.md`
- `docs/ai-development-roadmap.md`
- この文書

### 1. 今回の目標を決める

例:

```text
今回の最初の目標は Level 0 完了
対象デッキはまず1つ
まずは meaning のある合法手を返す構造を作る
```

### 2. 共通項目を決める

例:

```text
- ルーターは先に共通化する
- DecisionTrace の形式を固定する
- カード辞書は共通利用にする
- 固定シナリオテストを最低3件作る
```

### 3. 分担を決める

例:

```text
A: router / main.py 境界
B: card database / DeckPlan 最小版
C: setup / attach / attack 方針
D: trace / scenario test / benchmark
```

### 4. 統合ルールを決める

例:

```text
- 共通インターフェース変更は共有してから行う
- 1日1回、短い進捗確認をする
- 困ったら個人で抱えず、会話ログかチャットに残す
```

### 5. 会議の成果物を残す

会議が終わったら、少なくとも次を残します。

- 今回の目標
- 共通項目
- 分担
- 完了条件
- 次回までの宿題

---

## 会議後に残すべき最低限の文書

初回会議の後には、次のような短い記録を残すと次が楽になります。

```text
meeting-date:
goal:
first-milestone:
common-items:
owners:
done-definition:
next-actions:
open-questions:
```

これを長文議事録にしすぎる必要はありません。  
**次に何をするかが分かる短い決定メモ**で十分です。

---

## AIの使い方

このチームでは、人がまず話し合って方向を決め、その後の整理をAIに任せる形が向いています。

AIに任せやすいこと:

- 会議メモの要約
- 決定事項の整理
- 文書の清書
- `roadmap` に入れる内容と別紙に出す内容の仕分け
- チェックリスト化

人が先に決めた方がよいこと:

- 今回の目標
- 実装境界
- 共通インターフェース
- 誰がどこを担当するか
- 何を完了とみなすか

---

## この文書を使うときの考え方

この文書は、全員が開発に慣れてからもずっと使うためのものではありません。  
最初の数回の会議で、**迷わず話し合う順番をそろえるための補助輪**として使います。

最初の会議で全部を決めきる必要はありません。  
ただし、少なくとも次の4つはその場で決めることをおすすめします。

- 最初の目標
- 共通項目
- 分担
- 完了条件

ここが決まると、以後の会議は「何を話すか」で迷いにくくなります。
