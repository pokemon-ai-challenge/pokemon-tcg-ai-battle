# rule_agents — 手書きルールベース3種

環境上位のデッキ3つ（オーロンゲ／メガルカリオ／ジュラルドン）を、それぞれの勝ち筋に合わせて
人手で書いたルールベースエージェント。`league/` から対戦相手として使えるほか、
`diagnose.py` で「なぜ負けたか」を測りながら手を入れるための土台でもある。

```
rule_agents/
├── framework.py     エンジンとのやりとりだけを引き受ける共通部分（デッキ知識ゼロ）
├── grimmsnarl.py    オーロンゲ（マーニーのオーロンゲex）
├── lucario.py       メガルカリオex
├── archaludon.py    ジュラルドン／ブリジュラスex
├── diagnose.py      改良ループ用の計測スクリプト
└── decks/*.csv      各デッキ60枚
```

## Kaggle に出せる形にする

`sample_submission/` の本提出物(ML方策)とは別に、「この手書きルールベース単体で
提出したらどうなるか」を試したいときは `build_submission.py` で小さな tar.gz を作れる。

```bash
cd opponents/rule_agents
python3 build_submission.py grimmsnarl --out submissions/grimmsnarl_rule_submission.tar.gz
python3 verify_submission.py submissions/grimmsnarl_rule_submission.tar.gz --opponent dragapult_rule --games 100
```

**`verify_submission.py` を必ず通してから提出すること。** `fallback_calls` が 0 で
あることが、判断ロジックが実際に動いている証拠になる。

### 実際に起きた事故: 提出物が一度も判断せずに負け続けた

Kaggle の実戦リプレイ2試合(ep90110524 / ep90111221)を `replay_review.py` で読み下したところ、
**118手すべてが保険用のダミー行動だった**ことが分かった。内訳は

- `minCount >= 1` の選択 99回 → すべて `[0]`(先頭の選択肢)
- `minCount == 0` の選択 19回 → すべて `[]`(何も選ばない)

で、これは当時の `_fallback_action` の出力と完全に一致する。つまり main.py 内で
`rule_agents` の読み込みに失敗し、**判断ロジックが一度も動かないまま**試合が進んでいた。
結果として、

- パンクアップ(デッキから悪エネルギー最大5枚)で **0枚**しか付けず、オーロンゲexは
  最後までエネルギー0のまま**一度も攻撃できなかった**
- ボスの指令を、攻撃できない場面で無駄打ちした
- 1ターン目にベロバーを下げてマンキーを前に出し、盤面を止めた

**厄介なのは、対局がエラー無く完走してしまうこと。** 例外も違法手も出ないので、
勝率が落ちる以外に異常が見えない。この事故を二度と起こさないために入れた対策:

1. **読み込み失敗を必ず stderr に出す**(理由・cwd・候補ディレクトリ・traceback)。
   次にもし起きても、Kaggle のログを見れば原因が分かる。
2. **読み込み経路を二重化**。通常の import が失敗したら、`cg` の在り処から逆算した
   バンドル位置を使って、ファイル指定で直接読み込む(`sys.path` の状態に依存しない)。
3. **import 時にネイティブ呼び出しをしない**。`all_card_data()` / `all_attack()` は
   遅延化した(`framework._LazyTable`)。import 時に呼ぶと、失敗した環境で
   モジュールごと落ちて上記の状態になる。`cg.api` から取り込む名前も実際に使う分だけに絞った。
4. **保険の行動自体をまともにする**。先頭固定をやめ、殴れるときは殴り、サーチでは
   取れるだけ取るようにした。ドラパルト相手60試合で、取れるサイドが 0.22 → 1.92 枚に改善
   (それでも弱い。あくまで保険で、本来は 1〜3 で発生させないことが重要)。
5. **検証を別プロセス・複数環境で行う**(`verify_submission.py` の手順1)。
   同一プロセスで検証すると、検証側が先に import した `cg` などが `sys.modules` に残り、
   本番では失敗する読み込みが通ってしまう。

## 判断の形

どの `SelectContext`（エンジンが何を選ばせているか）でも、やることは
「選択肢の配列から何個か選ぶ」で共通している。そこで **全選択肢に点数を付け、高い順に
`minCount`〜`maxCount` 個返す**という形に統一した。個数超過・重複・範囲外といった
ルール違反が構造的に起きない。

点数は `framework.py` の `S_*` 定数を帯として使う。1手打つたびにエンジンが選択を
やり直させるので、**点数の大小がそのまま1ターン内の行動順になる**。

| 帯 | 値 | 意味 |
|---|---|---|
| `S_MUST` | 90000 | 逃すと負ける／勝ちを逃す手 |
| `S_KEY` | 70000 | デッキの核（主軸への進化、ふしぎなアメ） |
| `S_TOOL` | 60000 | 道具付け |
| `S_DEVELOP` | 50000 | たねポケモンをベンチに出す |
| `S_SEARCH` | 40000 | サーチ・ドローのアイテム |
| `S_ENERGY` | 30000 | エネルギー付け |
| `S_RETREAT` | 20000 | にげる |
| `S_REFRESH` | 15000 | 手札を丸ごと引き直すサポート（やることを済ませてから） |
| `S_ATTACK` | 10000 | 攻撃（＝ターン終了） |
| `S_END` | 100 | 何もせずターン終了 |
| `SKIP` | -1 | 選ばない |

「リーリエの決意」のような**手札を山に戻して引き直すサポートを `S_REFRESH` に置いてある
のは意図的**。エネルギーを貼り、進化させ、アイテムを使い切ってから最後に手札を入れ替える
という順番が、点数の大小だけで自然に出る。

デッキ固有の判断は `Strategy` のフック（`play_score` / `attach_score` / `evolve_score` /
`attack_score` / `want_in_hand` など）を上書きして書く。`framework.py` はカードIDを
一切知らない。

## 使い方

### 対戦（勝率を測る）

```bash
cd sample_submission
python3 ../league/run_league.py \
  --agent-a grimmsnarl_rule --agent-b lucario_rule \
  --deck-a opponents/rule_agents/decks/marnie_grimmsnarl_ex.csv \
  --deck-b opponents/rule_agents/decks/mega_lucario_ex.csv \
  --games 300 --workers 8
```

`--deck-a/--deck-b` には必ず対応するCSVを渡すこと。エージェントは自分のデッキ内訳を
前提に山札の残りを推定しているため、実際に使うデッキと食い違うと判断がずれる。

### 計測（なぜ負けたかを見る）

```bash
cd sample_submission
python3 ../opponents/rule_agents/diagnose.py --round-robin --games 100
```

勝率に加えて、主役が場に出たターン、最初にワザを撃てたターン、使ったワザの内訳、
「ワザを撃てるのに撃たずに終えた回数」、決着理由（サイド／山札切れ／バトル場が空）を出す。

未対応の `SelectContext` に落ちたときは環境変数で警告を出せる。

```bash
RULE_AGENT_DEBUG=1 python3 ../opponents/rule_agents/diagnose.py --a grimmsnarl_rule --b lucario_rule --games 50
```

|---|---|---|---|
| **オーロンゲ** | — | 0.460 | 0.564 |
| **メガルカリオ** | 0.540 | — | 0.552 |
| **ジュラルドン** | 0.436 | 0.448 | — |

エラー0件、未対応の選択文脈も0件。

**勝率は乱数の種を変えるだけで±0.05〜0.07動く。** 400試合規模でも「別々に走らせた2回の
結果を引き算する」ことはできないので、改良の効果を測るときは必ず**同じ種・同じ相手で
前後を比べる**こと（このREADMEの数字もそう測っている）。

残っている弱点は2つ。

- **メガルカリオが最後まで場に出ない試合が8〜15%ある。** リオルが3枚しかないうえ、
  倒されるとサイドを3枚渡すので、土台が尽きると立て直せない。
- **ジュラルドンは負けた試合の約半分が「バトル場が空」。** ベンチに出せるたねが
  ジュラルドン4枚とジーランス1枚しかない構造的な弱さで、展開の優先度を上げても
  完全には消えていない。

## 改良ループで実際に直したこと

計測 → 原因を1つ特定 → 直す → 再計測、を回した記録。数字はすべて `diagnose.py` の出力。

### 1. バトル場が空になって負ける（最大の敗因だった）

ジュラルドン同型60試合のうち37試合がこの負け方だった。自分の2ターン目時点でベンチが
平均1.2体、うち14試合はベンチが空。「ベンチを埋めるとボスの指令で弱いところを
引きずり出される」と考えて展開を絞りすぎていたのが原因。

盤面のポケモンが2体以下ならベンチ展開を最優先にする規則を3デッキ全部に入れた結果、
この負け方はジュラルドン同型で 37 → 14 試合、オーロンゲ戦で 25 → 13 試合に減った。

### 2. 前のポケモンにエネルギーが乗らず、11ターン目まで殴れなかった

ジュラルドンの最初の攻撃が平均11.1ターン目（同型では12.3ターン目）だった。1試合を
1手ずつ表示して追うと、原因は2つ:

- エネルギーを**ベンチの**ジュラルドンから貼っていた（「進化前から積んでおく」つもりで
  ベンチ側の点数を高くしていた）。前がエネルギー0のまま放置される。
- 進化させるジュラルドンを「バトル場にいるかどうか」だけで選んでいた。エネルギー0の
  ジュラルドンがブリジュラスexになるので、鋼3個が揃うまで何ターンもかかる。

前から貼る・エネルギーが多い方を進化させる、に直して、最初の攻撃は 11.1 → 6.8 ターン目、
同型では 12.3 → 7.1 ターン目になった。勝率も対オーロンゲで 0.37 → 0.47。

### 3. エネルギー0のポケモンが前に出ると、盤面が完全に止まる

オーロンゲでマンキーがバトル場に出た試合を追うと、5ターン以上何もできていなかった。
にげるにはエネルギーが要るので、エネルギー0だと**ワザも撃てず、にげることもできない**。

「前のポケモンがワザも撃てず逃げることもできないなら、逃げるためだけにエネルギーを
1枚貼る」を3デッキ共通の規則として入れた（`framework.retreat_blocked`）。
「ワザの選択肢が無いままターンを終えた回数」が1試合あたり 2.0〜2.9 → 1.4〜1.8 に減り、
平均試合時間も短くなった。

### 4. オーラジャブ（130）をメガブレイブ（270）より優先していた

メガルカリオの使用比が オーラジャブ 2.3 : メガブレイブ 1。本来は交互に撃つのが素の形。
オーラジャブに付けていた「トラッシュから闘エネを回収できる」加点が +700 で、
打点差140をひっくり返していた。+60 に下げた。

### 5. パンクアップの5枚を1体に集めていた

オーロンゲexの特性は基本悪エネルギーを最大5枚持ってこられるが、ワザに必要なのは2枚。
残り3枚が遊んでいた。控えのベロバー／ギモーに配るよう点数を組み直した
（控えが進化すれば、そのエネルギーがそのまま次のアタッカーになる）。

### 6. 先攻/後攻の判断が逆だった（オーロンゲ）

「先攻はサポートを使えないので、初動が全部サポートのオーロンゲは後攻が良い」と考えて
後攻にしていた。メガルカリオ相手に200試合ずつ測ると逆で、後攻 0.39〜0.40 に対して
先攻 0.44〜0.46。オーロンゲexが場に出るターンも 9.9 → 8.9 と1ターン早くなる。
2段階進化を組むのに使える手番が1回増える方が、サポート1枚を我慢する損より大きかった。

### 7. 「今殴れるか」の判定に、エネルギーの枚数を使っていた

前のポケモンが殴れないときに控えと交代する規則を入れたが、判定を
「ついているエネルギーの数 ≥ ワザのコスト数」で書いていたため取りこぼしがあった。

- ユキワラシに悪エネルギーが1枚ついていても、こおりのつぶて（水1）は撃てない（**種類**が違う）
- ソルロックのコズミックビームは、ベンチにルナトーンがいないと**発動条件**を満たさない
- リオルのかそくづき／メガブレイブには「**次の番は使えない**」制限がある

いずれも枚数だけでは分からない。**エンジンがワザの選択肢を出しているかどうか**
（`ctx.attack_options`）で判定するように変えた。これが唯一の正確な情報源になる。

### 8. エネルギー1枚が無いために何ターンも止まる

「前がエネルギー0で、ワザも撃てず逃げることもできない」局面が、150試合でオーロンゲ側に
126回（ベロバー83回・マンキー43回）、ルカリオ側に133回あった。必要なのはエネルギー1枚
だけなのに、サーチやドローの優先順位でエネルギーが下位にいたため手札に来ていなかった。

この局面に限りエネルギーの欲しさを最上位（950）に引き上げた。あわせてルカリオ側では、
ルナトーンの特性で**手札の最後の1枚を捨てない**ようにした（場にまだエネルギーが
必要な子がいるときだけ）。

なお、ここは締めすぎても失敗する。一度「常に1枚残す」にしたところ、引く枚数が減って
メガルカリオexを最後まで引けない試合が 16 → 26 / 150 に増えた。

### 9. エネルギー0のリオルを進化させていた

エネルギー0のリオルをメガルカリオexにすると、オーラジャブ（闘1）すら撃てない340HPが
前に立つ。150試合で59回あった。進化先の選び方を「バトル場にいるか」だけでなく
「エネルギーが乗っているか」で決めるように変えた（ジュラルドンで同じ直し方をしたのと同型）。

### 10. サイド3枚を渡す殴り合いを避ける（メガルカリオ）— この回で一番効いた

メガ進化ポケモンexは倒されるとサイドを**3枚**渡す。相手のブリジュラスex／オーロンゲexを
倒しても取れるのは**2枚**なので、相打ちを続けるとサイドレースで必ず負ける。

そこで「この番に倒しきれず、かつ次の番にメガルカリオが落とされる」ときは、
**ポケモンいれかえでメガルカリオを下げ、サイド1枚のリオル等を身代わりに差し出す**
ようにした。渡すサイドが3枚から1枚に減る。

同じ乱数の種で400試合ずつ比べると、対ジュラルドンは 0.540 → 0.608。対オーロンゲは
0.557 → 0.542 とわずかに下がったが誤差の範囲で、合計では明確にプラス。オーロンゲ相手に
効きにくいのは、シャドーバレットがベンチにも30ダメージを飛ばすため、下げても
削られ続けるからだと考えている。

### この回（7〜10）の効果を、同じ乱数の種で測った結果

勝率は乱数の種を変えるだけで7ポイント近く動くので、改良の効果は**同じ種・同じ相手で
前後を比べる**形でしか測れない。基準には、この回で触っていないジュラルドンを使った。

| | 改良前 | 改良後 |
|---|---|---|
| メガルカリオ vs ジュラルドン（400試合） | 0.525 | **0.603** |
| オーロンゲ vs ジュラルドン（400試合） | 0.555 | 0.550 |
| オーロンゲ vs メガルカリオ（旧）（400試合） | 0.443 | **0.480** |

メガルカリオは明確に強くなった（+7.8ポイント）。オーロンゲは、オーロンゲexが場に出る
ターンが 8.2 → 7.8、ワザを撃てないターンが 2.15 → 2.00 と動きは良くなったものの、
ジュラルドン相手の勝率には表れなかった。メガルカリオ相手には +3.7 ポイント。
「立ち上がりが速くなっても、ジュラルドンの耐久には勝率として効かない」ということだと
見ている。

### 直したが効果が無かったもの

**ユキメノコ（凍てつく霧）を出す条件**。この特性は特性を持つポケモン**全員**にダメカンを
乗せるので、メガルカリオex（特性なし）相手だと、こちらのオーロンゲexとマンキーだけが
削られる。そこで「相手の特性持ちの方が多いときだけ出す」に変えたが、300試合での勝率は
0.387 → 0.390 でほぼ変わらなかった（そもそもユキメノコが立つ試合が少ない）。
理屈は正しいので採用しているが、勝率への寄与は測れていない。
