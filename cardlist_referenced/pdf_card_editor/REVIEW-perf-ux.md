- 注: リンクはデッキ選択時のみ表示。プレビューの自動テストは BaseWeb セレクトボックスを開けない制約があり、

## ✅ 絞り込み状態を画面移動で保持（第7弾）

印刷/作業リストタブへ移動して戻るとカード画面の絞り込みが初期化される問題を修正。
原因は Streamlit が「その実行で描画されなかったウィジェットのキーをセッションから破棄する」挙動。

- `_render_card_screen` 先頭で、検索/ラベル/デッキ番号/並び順/表示数の各ウィジェット値を
  専用領域 `st.session_state["card_filter_state"]` に退避・復元する標準パターンを実装。
  - キーが破棄されている（=他タブから戻った）ときだけ復元し、操作中の値は上書きしない（`if key not in session_state`）。
  - 復元時はラベル/並び順/表示数を選択肢に対して検証（不正値はスキップ）、デッキ番号は既存ガードで補正。
- ページ番号(cardpage)は元々ウィジェットでなく手動セッション値のため既に保持される。
- 注: プレビューの自動テストは Streamlit の input/select に合成入力をコミットできない制約があり、
  画面描画が無事なこと＋標準パターン準拠で担保（実ブラウザの操作では保持される）。

## ✅ ラベル↔デッキの階層化（第6弾）

「ラベル(アーキタイプ)の中にデッキ(レシピ)がある」関係を明示し、絞り込みをきれいにした。

- 取得時に **アーキタイプ↔デッキの対応 `deck_archetype`（deck_id→アーキタイプ名）** を作成し、
  `pdf_state` に保持（`deck_card_quantities` と同じくセッション保持。取り込みで再生成）。
- カード画面の **「デッキ番号」候補を、選択中の「ラベル」に属するデッキだけにスコープ**。
  従来はカード所属ベースで汎用カード経由に他アーキタイプのデッキが混ざっていたが、
  `deck_archetype` をラベル名(正規化一致)で引くことで混入を解消。
  実データ検証: ラベル選択でそのアーキタイプのデッキ数に**正確に一致**（例: ドラパルトex→101、12/12アーキタイプでOK）。
- ラベル選択時は **デッキ表示から重複するアーキタイプ名を省略**（例:「6月7日 神奈川県 ベスト16（fVkF）」）。
- 注: アーキタイプ名が単一カード名に一致しない「○○バレット」系3種はラベル化されない（既存の「ラベル=カード名」設計の制約）。
  必要なら、これらもラベル化する拡張は可能。

## ✅ Tier取り込みの実用化（速度・デッキ一覧・採用枚数印刷）（第5弾）

既にデッキ単位のラベル付け・絞り込み・採用枚数つき印刷は実装済みだったが、
取り込みが全レシピ逐次取得で数分かかり実用に耐えなかった点を改善。

- `_fetch_tier_adopted_cards` を **並行取得(ThreadPoolExecutor, worker=8)** + **進捗コールバック** + **当日ディスクキャッシュ**
  (`.cache/tier_ranking/<日付>.json`) に刷新。`@st.cache_data` は廃止しディスクキャッシュへ。
  - 注: サイトの応答が遅く、全1442レシピの初回取得は約7分（worker16はサイト側スロットリングで逆に低速だったため8に設定）。
    2回目以降（同日）はキャッシュ命中で即時。日付が変わると最新データで再取得。
- `_import_tier_cards` に **st.progress の進捗バー**（「デッキレシピを取得中 n/total」）を追加。
- デッキ表示名を **レシピの og:title から「アーキタイプ 日付 開催地 順位」** に整形（例: ドラパルトex 6月7日 神奈川県 3位）。
  `_format_deck_option` も読みやすい名前＋短縮IDに。
- カード画面に **2段階絞り込みの誘導**（ラベル(アーキタイプ)→デッキ番号→採用枚数つき印刷）キャプションを追加。
- 検証（実関数＋ウォームキャッシュ）: あるデッキ→ `_add_deck_to_print_queue` で **29種/63枚**、各カードが採用枚数(4×,3×,2×,1×)で印刷キューへ。
  ※カード名が複数収録に一致すると合計が60をやや超える場合あり（既存の名前照合仕様）。

## 1. WEBアプリの速度向上

### 1-1.【最重要】カード一覧の全件レンダリング

`_render_card_table()`（[app.py:1946](app.py:1946)）は、表示対象の全行に対して
**1行ごとに以下を生成**しています:

```
st.columns([8列])  +  st.checkbox  +  st.markdown × 約8  +  区切り線 markdown
≒ 1行あたり約11個の Streamlit 要素
```

カード1267件なら **1回の再実行で約14,000個の Streamlit 要素**を生成・送信します。
Streamlit は「ウィジェット操作のたびにスクリプト全体を再実行」するため、
並び替え・絞り込み・ボタン押下・検索のたびにこの14,000要素を作り直しています。
これが体感の遅さの主因です。

**改善案（いずれか）:**

1. **ページング（最も簡単で確実）**
   - 1ページ 50〜100件にし、`visible_df.iloc[start:end]` だけを `_render_card_table` に渡す。
   - 要素数が 14,000 → 約1,000 になり、体感は劇的に改善します。
   - 作業リストのカードは「現在ページ内のもの」だけ下部セクション表示にすればロジックも単純。

2. **`st.dataframe` の行選択機能に置き換え（中期）**
   - `st.dataframe(df, selection_mode="multi-row", on_select="rerun")` は
     **ネイティブで仮想スクロール**するため数千行でも軽い。
   - チェックボックス1267個が不要になり、「選択を反映」フローも `event.selection.rows` で取れる。
   - 注意: 現在のホバープレビュー（`_build_name_anchor_html` の `data-*` 属性）は
     `st.dataframe` のセル内 HTML では効かないため、プレビューの出し方を
     「選択行 → 右ペインに大きく表示」に寄せるか、別途 `ImageColumn` でサムネ列を持たせる検討が必要。
   - メイン機能（ホバー表示）を残したいなら、まずは案1のページングが安全。

3. **遅延描画**: 検索/絞り込みで件数を絞ってから表示する運用を促す
   （初期表示で全件を出さない。例: 検索 or ラベル選択するまでは先頭100件のみ）。

> 推奨ステップ: **まず案1（ページング）**で即効性を取り、
> 余裕があれば案2（`st.dataframe`）へ移行。

### 1-2. 検索のベクトル化

`_filter_cards()`（[app.py:1636](app.py:1636)）は `working.apply(lambda row: ..., axis=1)` で
1267行を Python レベルでループしています。検索1文字ごと（確定時）に毎回実行されます。

**改善案:** 連結済みの小文字検索キー列を **一度だけ**作って `str.contains` でベクトル化:

```python
# カタログ読込時に1回だけ作る（card_df に列を持たせる）
card_df["_haystack"] = (
    card_df["card_id"].astype(str) + " " + card_df["name"] + " " +
    card_df["label"] + " " + card_df["expansion"] + " " +
    card_df["collection_no"].astype(str) + " " + card_df["target_page"].astype(str)
).str.casefold()

# 検索時
mask = card_df["_haystack"].str.contains(re.escape(needle), regex=True, na=False)
```

行ループが消え、検索が体感で即時になります。

### 1-3. プレビューURL生成の `stat()` 連打

`build_preview_url()`（[app.py:301](app.py:301)）は呼ばれるたびに `pdf_file.stat()` を実行し、
これが `_render_card_table` の**全行**から呼ばれます（1267回/再実行）。
PDF は1ファイルなのに、毎行ディスクへ `stat` しています。

**改善案:** 描画ループの前に version_token を **1回だけ**計算して使い回す:

```python
version_token = str(pdf_file.stat().st_mtime_ns)  # ループ外で1回
# 各行は token を渡して URL を組むだけ
```

`build_artifact_url` も同様にキャッシュ可。

### 1-4. 毎回再構築している重い前処理をキャッシュ

- **一覧 DataFrame**: [app.py:372](app.py:372) で毎再実行ごとに 1267 行の `pd.DataFrame` を内包表記で再構築。
  さらに `_filter_cards`/`_sort_cards`/`_order_cards_for_display` で `.copy()` を多数。
  → ベースの df は `@st.cache_data`（pdf_path + fingerprint をキー）で1回だけ作り、
    ラベル列だけ再実行時に更新する形にすると、毎回の DataFrame 生成コストが消える。
- **PDF候補探索** `_discover_pdf_candidates()`（[app.py:640](app.py:640)）は
  182MB PDF を含むフォルダを毎再実行で `rglob("*.pdf")`。
  → `@st.cache_data(ttl=...)` 化、もしくはセッションに一度だけ。

### 1-5. その他（軽微）

- [app.py:28](app.py:28) `importlib.reload(_pdf_card_tool)` は開発用。本番運用では削除して通常 import に。
  （reload は毎プロセス1回だが、不要なら外す方が安全）
- カタログ/アセット/プレビューはすでにディスク + `st.cache_data` でキャッシュ済み＝良い設計。
  巨大PDFのロード自体はボトルネックになっていない。
- プレビュー画像はホバー時に HTTP サーバ経由で遅延生成＝良い。`Cache-Control: max-age` も付与済み。

## 2. UI / UX の向上

### 2-1.「短い・情報が平坦」への回答 ＝ ジャンプ率（視覚的階層）

ご指摘の「ジャンプ率」はまさに有効な概念です。現状の一覧は
**全セルがほぼ同じ文字サイズ・同じ濃さの表**で、目線の止めどころがありません。

**改善案: 必要な情報を大きく、補助情報を小さく。**

- **カード名**を最も大きく・太く（一覧の主役）。例: 名前 16〜18px / 太字。
- カードID・エキスパンション・コレクション番号・元ページは **補助情報**として
  小さめ・淡色のメタ行に集約（例: `SV1a / 073 / p.412` の1行）。
- **ラベル / 状態チップ**（作業リスト・印刷 x2）は色付きで一番目立たせる
  （これが「必要な情報」そのもの）。チップは既に実装あり＝活かす。
- 印刷枚数など数値は **大きい数字 + 小さい単位**で（メトリクス的に）。

ジャンプ率の目安: 主役（カード名）と補助（メタ情報）で **1.4〜1.6倍**の差をつけると
「短い1行でも情報が立ち上がって見える」状態になります。

### 2-2. 表 → カード型グリッドという選択肢

「カードを見るためのツール」である以上、テキスト表より
**サムネイル付きカードグリッド**の方が目的に合います。

- 1枚 = 小さなカード画像 + カード名 + ラベル/状態チップ + チェック。
- ホバーで現状の拡大プレビュー（メイン機能維持）。
- ただしサムネを全件出すと重いので **1-1のページングが前提**。
- まずは表のジャンプ率改善（2-1）だけでも体感は大きく変わるので、グリッドは次段階で。

### 2-3.「チェック → 選択を反映」の2段階がわかりにくい

`st.form` でまとめて反映する設計は**再実行を減らす点で正しい**のですが、
初見では「チェックしたのに右に出ない」と感じます。

**改善案:**
- 「選択を反映」ボタンに未反映件数バッジを出す（例: `選択を反映 (3件未反映)`）。
- フォーム内チェックの変更を検知して、ボタンを `type="primary"` で点灯/強調。
- もしくは 1-1 案2（`st.dataframe` 選択）に移行すると、この2段階自体が不要になり最もスッキリ。

### 2-4. 検索の体験

- プレースホルダは良い。`key=` を付けてセッション保持し、絞り込み中の件数を
  「**1267件中 42件**」のように分母付きで表示すると安心感が出る（現状は「表示件数: N」のみ）。
- ラベル絞り込み・並び順・グループ化はチップ/トグルで現在の絞り込み状態を可視化。

### 2-5.【重要】操作側（右ペイン）も主役と脇役が同じ重さで並んでいる

ご指摘の通り、**操作パネルこそ階層が必要**です。一覧（2-1）と同じ問題が
右ペインでも起きていて、「あまり目立たせなくていい機能」や「その機能の下の補足情報」が
主要操作とまったく同じ視覚レベルで縦に積まれています。

#### 現状（印刷タブ `_render_print_tab` [app.py:1066](app.py:1066)）の並び

上から下まで、ほぼ**同じ重さ**で積まれています:

```
caption（説明文）
現在の作業選択（subheader + dataframe）   ← 各タブで重複表示
印刷キュー（subheader + ボタン4個 + 枚数調整リスト）
─── divider ───
印刷設定（subheader + caption + selectbox + mm入力×3）   ← めったに変えない
#### 3. 印刷用PDFを書き出す（h4 + caption）
保存先パス（text_input）                  ← 上級者向け
[印刷用PDFを書き出す] ボタン              ← ★本当の目的が一番下・通常ボタン
```

**問題点（具体）:**

1. **本来の目的「PDF出力」ボタンが一番下に、しかも目立たない。**
   作業リストタブの出力ボタンは `type="primary"`（[app.py:1041](app.py:1041)）なのに、
   印刷タブの出力ボタンは `type` 指定なし（[app.py:1100](app.py:1100)）＝**色も付いていない**。
   主役ボタンの扱いがタブ間で不一致。これは明確に直すべき。

2. **めったに変えない詳細設定が常時フル表示。**
   カード幅/高さ/余白(mm)（`_render_print_settings` [app.py:1557](app.py:1557)）は
   既定 63×88×2 でほぼ固定なのに、`number_input` 3つが常に主要操作と同列で見えている。
   → `st.expander("詳細設定（サイズ・余白）", expanded=False)` に畳む。

3. **保存先パス入力**も上級者向け。既定パスは決まっているので、
   普段は「出力先: …」と**淡色テキストで現在値だけ表示**し、
   変更したい人だけ expander で開ける形に。

4. **説明 caption が多く、操作と同じ高さで縦を圧迫。**
   各 `st.caption`/バナー（「印刷に必要な情報だけを…」等）は
   **1行・淡色**に抑えるか、ボタンの `help=` ツールチップへ逃がす。

5. **「現在の作業選択」プレビューが印刷タブ・作業リストタブで重複**
   （`_render_selected_cards_preview` [app.py:1118](app.py:1118)）。
   subheader + dataframe で毎タブ場所を取る。1か所（共通ヘッダ）に集約するか折りたたみに。

6. **見出し機構が混在**: `st.subheader` / `st.markdown("#### 3. …")` / `st.write` が混ざり、
   階層が文字サイズでなく**番号「3.」頼り**になっている。見出しレベルを統一する。

#### あるべき階層（操作側のジャンプ率）

```
【主役】 [PDFを書き出す] ← primary・大きく・各タブ上部 or 末尾固定で目立たせる
【準主役】印刷キュー / 作業リスト本体（枚数・並べ替え・外す）
【脇役】 詳細設定(mm)・保存先パス  → expander に畳む（既定は閉じる）
【補足】 説明文              → 1行淡色 or help ツールチップ
```

ポイントは「**変える頻度 × 重要度**で3段に分け、低頻度・低重要のものは畳む**」ことです。
そうすれば縦も短くならず、押すべきボタンが一目でわかります。

### 2-6. 印刷キューの行UIも同じ観点で

`_render_print_queue_section`（[app.py:1469](app.py:1469)）の各行は
カード名・ラベル・枚数・[外す] が**等幅で並列**。
カード名（主）を太く、ラベル（補助）を淡色小さめ、枚数 stepper と [外す] は右端に寄せると
1行でも情報が立ち上がります（2-1 と同じジャンプ率の考え方）。

### 2-7. 視覚デザインの一貫性

- `_inject_app_styles()`（[app.py:1684](app.py:1684)）に色がハードコードされている。
  主要色（アクセント / 作業リスト色 / 印刷色 / 淡色）を **CSS変数**にまとめると、
  ジャンプ率調整や濃淡の一括変更が楽になる。
