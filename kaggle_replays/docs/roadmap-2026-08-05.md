## 0. 過去の報告の訂正

### 0-1. 「教師一致率の天井 0.7685」は天井ではない

`diagnose_errors.py` の「同一状態」は **166次元の状態特徴を丸めたハッシュ**で判定していた。
だが状態特徴には**カードの同一性が入っていない**（手札は pokemon/trainer/energy の3つの数だけ、
盤面のポケモンは HP・打点など汎用数値11個だけ）。

手札 {ネストボール, ハイパーボール, 博士の研究} と {ボスの指令, ナンジャモ, アカマツ} は**同一ベクトル**。
比較対象も行動の意味ではなく**選択肢配列のインデックス**。

**0.7685 は「上位プレイヤーの手が割れている度合い」ではなく、
「エンコーダがどれだけ別局面を同一視しているか」の測定値。BC飽和の根拠にならない。**

### 0-2. 「Top-1 と勝率は乖離する」は雑な一般化

切り順特徴（Top-1 +0.84pt / 勝率 ±0）の正確な読み方は
**「教師の不一致のうち、価値がゼロの部分を学習した」**。
ポケカの切り順は多くの局面で本当にどちらでもよく、等価な場面で
「その人がたまたま選んだ順」を当てても勝率は定義上動かない。

### 0-3. 「モデル容量は効かない」はスコープ付き

正しくは「**この239次元の入力では**律速していない」。入力を増やした後は再測定する。

### 0-4. にげるコスト・サイド価値が効かなかったのは事前に分かった

選択肢特徴に**すでに `target_card_is_ex` がある**。情報量ゼロの特徴を足していた。
→ **チェックリストに追加**: 追加する特徴が既存特徴から自明に導出できないことを、
`FEATURE_NAMES` / `OPTION_FEATURE_NAMES` を grep して確認する。

| lucario | 0.510 | 0.530 | +2.0pt |

**出発点が低いほど伸びる。** 新BCの出発点（0.757/0.682/0.816）は旧BCの到達点を既に超えている。
**RLが効かなくなったのではなく、RLが埋めていた穴をデータが先に埋めた。**
学習曲線は **20〜25反復で飽和**（60反復のうち35反復は無駄）。

### 情報量から見たRLの限界

- RL 60反復 ≒ 30,720試合 × 1bit ≒ 31 kbit を、1試合80決定に**薄く拡散**
- BC marnie ≒ 68,000決定点 × 約2.5bit ≒ 170 kbit を、**決定点に直付け**

**RLが学べるのは粗い行動傾向だけ。「17択の中でどの対象を選ぶか」は原理的にRLの帯域に乗らない。**

## 3. 探索の絞り込み（実測に基づく）

### 3-1. 方策は正解を上位に入れている（recall@k、実測）

| 選択肢数 | n | @1 | @3 | @5 | @10 |
|---|---:|---:|---:|---:|---:|
| 5-8 | 25,196 | 0.655 | 0.914 | 0.985 | 1.000 |
| **9-16** | 11,519 | 0.531 | 0.843 | 0.930 | **0.988** |
| **17+** | 2,693 | 0.377 | 0.635 | 0.746 | 0.864 |
| 全体 | 85,218 | 0.739 | 0.938 | **0.978** | **0.994** |

**Top-1 0.739 に対し recall@5 は 0.978。24pt 分が「候補にはあるが順位が違う」＝探索が決着させられる形。**
弱い帯ほど効きしろが大きい（9-16 で +45.7pt、17+ で +48.7pt が理論上の幅）。

### 3-2. コストは「幅」ではなく「深さ」と「どこを探索するか」で決まる

**平均選択肢数は 5.37 しかない。** 上位10手に絞っても 1.12分の1 にしかならず、
幅の絞り込みでコストは大きく下がらない。効くのは:

| 絞り方 | 効果 |
|---|---|
| **探索する決定点を選ぶ**（9択以上のみ） | 決定点の16.7%。誤答の31.8%が集中 |
| **深さを切る**（終局まで→自ターン終了まで） | 100手 → 15手程度 |
| **重複候補を潰す**（後述） | 17+ で **4.35分の1** |

実数で引き直した見積もり:

```
9択以上(13.3決定) × 上位10手(平均9.4候補) × ターン内15手  ≒ 1,900 step/試合
決定化3回なら                                          ≒ 5,600 step/試合 → 2.2秒/試合
```

**Expert Iteration が現実的なコストに収まる。**
1試合1ビットの勝敗を80決定に配る代わりに、各決定点で探索が出した行動分布を教師にする。
供給される教師情報が2桁変わり、細かい識別にその決定点で信号が届く。

> **注**: `2,500手/秒` はメモリ記載の過去実測（別ブランチ・別マシン）。**測り直す**。

### 3-3. 重複候補の潰し込み（知識不要・完全に安全・効果大）

`(選択肢の種類, card_id)` が同じ候補は実質的に同じ手。実測:

| 選択肢数 | 総候補 | 重複除去後 | 削減 |
|---|---:|---:|---:|
| 5-8 | 36,155 | 24,596 | 1.47x |
| 9-16 | 28,284 | 14,174 | **2.00x** |
| 17+ | 12,823 | 2,951 | **4.35x** |

「トラッシュする基本エネを4枚から選ぶ」のような、どれを選んでも同じ選択肢が大量にある。
**探索が最も重い帯を4分の1にできる。無条件でやる。**

### 3-4. セオリーによる枝刈りの価値は「速度」ではなく「精度」

葉の評価が粗い（ケーシィとノコッチを HP 50/70 でしか区別できない）と、
**探索は「評価関数がたまたま高く見積もった悪手」を選ぶ**。深く読むほど誤差を最大化する手を掘り当てる。
ここで「ポケカ的にありえない手」を先に切れば、**評価関数の誤差が悪手に化けるのを防げる**。

規則として書けるが評価関数が気づけない例:

- 次のターンに倒される確定のポケモンにエネを付ける
- キーカードの最後の1枚をトラッシュする
- 理由なく ex をベンチに出す（相手に2枚取りされる）
- 制約の強いサーチでしか取れない対象を、汎用サーチで取る（ポフィンの例）

**ただしハード除外は天井を作る。** 誤って正解を切れば、どれだけ深く読んでも届かない。実測コスト:

```
上位5手に絞る → 正解の 2.2% を失う   （17+ では 25.4%）
上位3手に絞る → 正解の 6.2% を失う
```

**方策が最も弱い帯ほど、枝刈りで正解を失うリスクが高い。** よってソフト（優先度付け）を主とする。

## 4. 最大の障害は「葉をどう評価するか」＝ ポケカの知識

探索は候補を作れるが、**どれが良いかを判断する関数がなければ意味がない。**
そしてここが今いちばん壊れている。

**Critic（RLの価値関数）が見ているのは方策と同じ166次元**（`train_v3.py:38`）。
そこに card_id も特性も入っていない。

具体例（ユーザー指摘）: 手札にポフィンとテレパス超エネルギーがあるとき、
ポフィンでノコッチ、エネルギーでケーシィを取るのが正しい。カードテキストで裏づけ済み:

```
テレパス超エネルギー → 基本【超】ポケモンを2匹まで      ← ケーシィは取れるがノコッチは取れない
ポフィン            → HP70以下の基本ポケモンを2匹まで  ← どちらも取れる
```

**制約の強い道具でしか取れないものを、汎用の道具で取ってはいけない。**
ところが現在の表現では:

- 方策はポフィン解決時に「手札にテレパス超エネルギーがある」ことを**知る手段がない**
- Critic/葉評価はケーシィとノコッチの違いを **HP 50 か 70 か**としか見ない
  （ノコッチの価値は「ノココッチに進化して3枚引ける」ことだが、その情報はどこにもない）

**学習アルゴリズムの問題ではなく表現の問題。表現を直さない限り、
BCでもRLでも探索でも、この判断は学べない。**

### 葉評価に入れるべきポケカの知識

| 知識 | 入れ方 | 現状 |
|---|---|---|
| カードの同一性 | 手札19次元・山札残19次元・トラッシュ19次元（**デッキの異なるcard_idは実測でちょうど19種**） | 全部ゼロ |
| デッキの回し方 | `rule_based/deck_plan.py` に `search_priority` 等の知識が既にある。葉評価に接続 | 未接続 |
| 相手が誰か | `OpponentDeckEstimator`（別ブランチ）。ポケカは対面で立ち回りが根本的に変わる | 未接続 |
| ハードカウンター | 例: イワパレスの特性でexの打点が0になる。汎用の打点計算では表現できない | 未対応 |
| 相手のトラッシュ | 完全な公開情報なのに未使用。「相手はボスを何枚使ったか」はサイドレースの計画に直結 | 未使用 |

      **決め手は F の比較。** ハンマーを first move にしたロールアウトは 75.3% で KO に到達するが、
      **実際に選んだ手（PLAY/EVOLVE）を first move にしても 78.8% で KO に到達する。**
      探索から見ると、どちらを選んでも同じくらい倒せている。差が付かないので方策の順位で決まる。

      ```
      ハンマーを撃つ   手札 −1 → 打点 −20、確実に目の前を倒す
      引く・並べる     手札 +3 → 打点 +60、別の勝ち筋も開ける
      ```

      Powerful Hand の打点は手札枚数に比例するので、**ハンマーを使うこと自体が自分の打点を下げる**。
      診断も「攻撃した世界のうち13.0%は攻撃時点で既に非lethalだった」と検出している。

      **「7割を逃している」という当初の表現は誤り。** 探索の見立てでは互角。

      ※ この調査で得た副産物のほうが重要（→ §測定インフラの発見）:
      **`collect_pool` は素の PolicyModel だけを呼び、リーサル探索も pipeline 探索も通らない。**
      我々の全評価（B1 のスケーリング曲線、A10段階1の +10.8 Elo を含む）は
      **探索なしの BC 単体の性能**であり、提出エージェントとは別のシステムを測っている。

      以下は打ち切った当時の設計案（記録として残す）。

      当初「1次元の特徴を足して BC に学ばせる」と書いたが、**これは設計として誤り**。
      ユーザー指摘: 「エネルギーのせいで相手のポケモンが倒せないなら壊す一択でしょ」。

      **塞がれていて、剥がせて、剥がせば打点が戻るなら、剥がす以外の手はない。**
      択でないものを確率的な方策に学ばせるのは、
      ①教師データに十分な事例が要る ②それでも確率的にしか出ない ③特徴の小追加は
      これまで3回とも空振り（にげる/サイド価値 p=0.50、切り順は Top-1 +0.84pt で勝率不動）、
      と三重に不利。**決定的なルールで書けば100%出る。**

      教師データで「ハンマー実行率の天井」を測る案も**取り下げ**。
      正解が自明な局面で上位プレイヤーの実行率を測っても、100%に近い数字が出るだけで
      設計判断に使えない。測るべきは天井ではなく、**ルールの誤発火**（下記）。

      発火条件（`_estimate_variable_damage` と同じくカードIDは直書きしない。
      「相手の特殊エネを1枚トラッシュする」効果テキストで手札を走査する）:

      ```
      1. 自分のバトルポケモンの最大打点が、相手の特殊エネによって 0 になっている
      2. 手札にその特殊エネを剥がせるカードがある
      3. そのうち1枚を剥がすと、打点が実際に回復する   ← この条件が要
      → 剥がす
      ```

      **条件3が無いと無駄打ちする。** crustle は Mist 4 + Rock 4 を積んでいるので、
      バトル場に2枚ついている状況がありうる。1枚剥がしても塞がれたままなら撃つ意味がない。
      判定は「各エネを1枚ずつ外して `damage_prevented()` を引き直す」だけで済む。
      同じ理屈で、**Crustle の特性のような剥がせない防壁には発火しない**（条件1に該当しない）。

      実装位置は `ml_policy/ml_policy_agent.py` の `_select_action()`:

      ```
      _try_lethal        確定リーサル      ← ここが先。今ターン勝てるならそちらが優先
      _try_hammer        今回追加          ← 強制手なので探索予算を使わない
      _try_pipeline      BC top-k + ロールアウト
      _try_attack_hybrid ルールベース提案
      model.select_option BC 単体
      ```

      既存の `_try_attack_hybrid` が「ルールベースの判断を BC の前に差し込む」前例なので、
      同じ形で config のフラグ（既定 off）付きで足し、A/B を取れるようにする。

      **段階1（打点計算の修正）は段階2があっても要る。**
      ルールは自分の行動を直すだけで、`best_attack_damage` / `can_ko` は**盤面12体すべての特徴**として
      方策・価値関数・葉評価に入る。「相手が自分を倒せるか」の判断にも同じ数字が使われるので、
      ルールを入れても計算を直さなければ嘘は残る。

      **測るもの**: 勝率ではなく、まず**ルールの発火と誤発火**を自己対戦のログで数える。
      発火した局面で実際に打点が回復しているか、条件3が効いて2枚ついているときに
      黙っているか。これは数十試合で分かる。勝率はその後。

## 6. 指標の選び方（2026-08-06 確定）

**勝率 pt を主指標にしない。** pt は強さの線形尺度ではない:

```
0.50 → 0.53  同じ +3pt だが +20.9 Elo
0.82 → 0.85  同じ +3pt だが +37.9 Elo   ← 1.8倍の伸び
```

「計器が飽和している」と表現していた問題は、現象ではなく **pt という尺度の性質**だった。

| 用途 | 指標 | 根拠 |
|---|---|---|
| **採否の判断** | **Elo差**（勝率から `173.7 × logit(p)`） | 飽和の影響を受けず、実験間で比較できる |
| **検定** | サイド差（連続値） | 実測で必要試合数 **23%削減**（効果量 d が 0.0420→0.0480）。※以前「1.5〜2倍」と書いたのは過大。訂正 |
| **層別** | 先攻/後攻 | 実測で +7.6pt の差。分散も下がる |
| **診断** | **敗因の内訳** | 勝率が動く前に構造が見える（crustle の山札切れ17.6%はこれで判明） |

過去の成果を Elo で並べ直すと投資判断が明確になる:

| 施策 | 勝率 | Elo |
|---|---|---:|
| **BC再学習** | 0.599→0.757 | **+127.7** |
| 打点修正(crustle) | 0.593→0.614 | +15.0 |
| にげるコスト | 0.552→0.561 | +6.1（有意でない） |
| 切り順特徴 | 0.573→0.569 | −2.3 |

**BC再学習が他の8倍以上。**

> **サイド差を目的関数にしてはいけない。** 勝敗との相関は 0.84 であって 1.0 ではなく、
> 「大差負けを避けて僅差負けを増やす」方向の歪みがありうる。
> **検定統計量として使い、採否は Elo で判断する。**

## 7. 測定コストへの対処（全 Phase 共通）

- **飽和していない相手で測る**（0.82 ではなく新BCミラーの50%）。無料で分解能が上がる
- **サイド差を副指標に**（勝敗1bit → 連続値）。A2 で相関を確認
- **先攻後攻で層別**。無料。分散が下がり、「先攻でだけ悪化」も検出できる
- **敗因分解を常時ログ**（サイドレース負け / デッキアウト / ベンチ切れ）。勝率より早く動く
- **SPRT**（チームの `measurement-protocol/design.md`）。悪い案は300〜800試合で棄却できる
- **2段階**: スクリーニング δ_min=0.05（約1,250試合/群）→ 確証 δ_min=0.03（約3,500試合/群）
- **測る前に落とす**: 追加特徴が既存特徴から導出可能でないことを grep で確認
- **プールが実メタを反映していない**。実際の場は marnie 60.6% / イワパレス 26% だが、
  評価プールは4アーキタイプ等重み。**存在しない相手に最適化している**可能性がある。
  最終的な目的関数は実リーダーボードのスコア（→ A6）
