# 特徴量実験の測定計画（対照群・複数シード）

> **状態: 有効（以後この手順に従う）** — 2026-08-04。
> 試合レベルの統計（SPRT・δ_min・必要試合数）は**チームの
> `sample_submission/docs/plans/measurement-protocol/design.md` が権威**。
> 本書はそこに無い層、すなわち **「学習をやり直すと結果が変わる」分散と対照群の作り方**を足す。

---

## 0. なぜ要るか

2026-08-04 の特徴量実験で、**同じ主張を2回下方修正した**。原因はどちらも測定設計。

1. 2シードで「にげるコスト +8〜14pt、効果あり」と報告 → 3シード目 0.4378 で崩壊
2. 対照群の初回評価で「実験群 +26.8pt で圧勝」→ 評価側のバグ（後述の std 罠）

チームの設計書は**試合のサンプリング誤差**を扱っているが、
**同じ設定で学習し直すと数値が動く**ことは扱っていない。そこがこの穴だった。

---

## 1. 実測した分散（marnie、各群3シード）

| 指標 | n | シード間の標準偏差 | 3シードで検出できる差（2.5σ） |
|---|---:|---:|---:|
| 全体 Top-1 | 85,218 | 0.001 | **0.2pt** |
| にげる Top-1 | 788 | 0.053 | **10pt** |
| エネ付け Top-1 | 3,482 | 0.017 | 3.5pt |
| 進化 Top-1 | 3,727 | 0.012 | 2.5pt |

**全体 Top-1 は極めて安定だが、行動の種類に分解した瞬間にノイズが支配する。**

にげるで 5pt の差を検出するには **1群あたり13シード**必要になる（`k = 2 / (δ/(2.5·sd))²`）。
これは現実的でない。

> **結論: 行動の種類別 Top-1 を採否の判断に使わない。** 診断（どこが弱いかの当たりをつける）
> 専用とする。判断は全体 Top-1 か、勝率で行う。

勝率側はシード間分散が小さく（実測 sd 0.33pt）、**試合のサンプリング誤差（n=1200 で 1.4pt）が支配的**。
つまり勝率では **シード数より総試合数が効く**。

## 2. 手順

### 2.1 実験の前に決めること（後から変えない）

- **主指標をひとつ**。原則は「凍結プールに対する勝率」。Top-1 は副次・診断用
- **δ_min**（採用に値する最小の差）。チーム設計書の基準に合わせる:
  特徴量・重み・config の小変更なら **0.03**
- **必要な総試合数**。δ_min=0.03 を 2.5σ で検出するには **1群あたり約3,500試合**
  （p≈0.55 前提。`n ≥ 2p(1−p)/(δ/2.5)²`）
- 複数の構成を試すなら、**事前に何を試すか列挙する**（多重比較を数えるため）

### 2.2 対照群の作り方

**エンコーダを変えて旧版と比べてはいけない。** 次元が変わると既存の重みが全部使えなくなり、
凍結プールも作り直しになって、過去の数値と比較できなくなる。

代わりに **`train.py --ablate-features <名前>`** を使う。指定した特徴を 0 で潰して学習する。

```bash
# 実験群
python train.py --features F.npz --out-weights exp_s42.json --seed 42
# 対照群（次元は同一、情報だけ落ちる）
python train.py --features F.npz --out-weights ctl_s42.json --seed 42 \
    --ablate-features retreat_cost,prize_value
```

**両群は次元・データ・凍結プールがすべて同一**になるので、そのまま同じ相手と戦える。

### 2.3 シード数

| 目的 | 推奨 |
|---|---|
| 全体 Top-1 の比較 | 各群 **3シード**（0.2pt まで検出できる） |
| 勝率の比較 | 各群 **3シード**、1シードあたり 1,200試合（計3,600試合/群） |
| 行動の種類別 Top-1 | **判断に使わない**（診断のみ） |

シードは `--seed` で指定し、**両群で同じシード集合を使う**（42 / 1 / 2 など）。

### 2.4 評価

学習なしの評価だけなら `--iters 0` で回せる。

```bash
python train_pool.py --learner <arch> --learner-weights <重み> \
  --extra-registry <registry>.json \
  --eval-opponents <プール4体> --iters 0 \
  --eval-games 1200 --final-eval-games 1200
```

## 3. 踏んだ罠（必ず確認すること）

### 3.1 潰した列の std は 0 ではなく 1e-6

`--ablate-features` で潰した列は学習時ずっと 0 なので、標準化の std が
**0 ではなく 1e-6 にクリップ**される。この重みをそのまま評価・推論に回すと、

```
(実データ 2 − mean 0) / 1e-6 = 2,000,000
```

が入り、**対照群だけ数値が壊れる**。実際これで「実験群 +26.8pt で圧勝」という
真逆の結果が出た。

**対策（両方やる）:**

- 評価スクリプトにも同じ `--ablate-features` を渡す（`diagnose_errors.py` 対応済み）
- **対戦評価に使う場合は、重み JSON の該当 std を 0 に書き換える。**
  `policy_model._forward` の「std が偽なら 0」経路に落ちて、学習時と一致する

**検算:** 潰さずに評価しても学習ログと同じ Top-1 が出ることを必ず確認する。
一致しなければ罠を踏んでいる。

### 3.2 凍結プールが勝手に差し替わる

`pools.LEARNER_REGISTRY` は `policy_weights_<arch>.json` を評価用の相手として指している。
**BC を学習し直すとこのファイルが上書きされ、「凍結」プールの中身が変わる。**

学習の出力は必ず `--out-weights` で別名にし、レジストリが指すファイルを触らない。

### 3.3 エンコーダを変えると本番が試合中に落ちる

`_forward` は `range(len(state_features))` で回して `state_mean[i]` を引くため、
次元を増やすと古い重みで IndexError になる。`policy_model.py` に次元ガードを入れてあり、
不一致なら読み込まず `is_ready=False`（フォールバック）に倒れる。**ガードが出す警告を無視しない。**

## 4. チェックリスト

実験を始める前:

- [ ] 主指標をひとつ決めた（原則は勝率）
- [ ] δ_min を決めた（小変更なら 0.03）
- [ ] 必要試合数を計算した（δ_min=0.03 なら約3,500試合/群）
- [ ] 対照群を `--ablate-features` で作る設計にした（エンコーダを変えて旧版と比べていない）
- [ ] 両群で同じシード集合（3つ以上）を使う

結果を出す前:

- [ ] 対照群の重みを、潰さず評価して学習ログと一致することを確認した
- [ ] 対戦評価なら、潰した列の std を 0 に書き換えた
- [ ] 凍結プールの相手が意図したファイルを指していることを確認した
- [ ] 行動の種類別 Top-1 を判断根拠にしていない

主張する前:

- [ ] シード間の幅を併記した（平均だけ書かない）
- [ ] 差が両群の幅より大きいことを確認した
- [ ] 効かなかった場合も記録した（同じ案を再度試さないため）
