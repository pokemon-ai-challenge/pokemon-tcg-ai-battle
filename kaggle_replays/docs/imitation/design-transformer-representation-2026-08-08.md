## この文書について

このプロジェクトは、Kaggle の「Pokemon TCG AI Battle」というポケモンカードゲームの対戦 AI を
作るコンペティションに参加するためのものです。現在の対戦 AI（提出プログラム）の意思決定は、
**上位プレイヤーの実際のプレイ記録（リプレイ）を真似するように学習させたニューラルネットワーク**
（「模倣学習」= Behavior Cloning、以下 **BC**）が中心になっています。

この文書は、その BC モデルの**入力の作り方（＝盤面やカードをどんな数値の並びとしてモデルに渡すか）
と、選択肢の評価の仕方**を見直す提案です。核となる問題意識は「今のモデルはカード1枚1枚・選択肢1つ1つを
独立にしか見ておらず、手札や場のカード同士の組み合わせ（シナジー）や、他の選択肢との比較を
考慮する仕組みがない」というものです。これを、自然言語処理などで使われる **Transformer**
（複数の要素同士の関係を学習する仕組み）に近い構造を、必要な範囲だけ小さく導入することで
解決できないかを検討します。

**この文書はこの `kaggle_replays/docs/` ディレクトリの経緯を知らない人でも読めるように書いています。**
プロジェクト内で使われている略語・過去の実験結果への参照は、初出時に説明を加えます。
より詳しい経緯を追いたい場合のみ、末尾の「関連文書」のリンク先を参照してください。

## 0. 用語ミニ辞典（本文で使うものだけ）

| 用語 | 意味 |
|---|---|
| **BC（模倣学習）** | 上位プレイヤーのプレイ記録から「この局面でこの手を選んだ」というペアを学習データにして、同じような判断をするようにニューラルネットワークを訓練する手法。強化学習（自己対戦で試行錯誤する RL）とは別の学習方式 |
| **状態（state）** | ある瞬間の盤面全体（手札・場のポケモン・トラッシュの中身・ターン数など）を数値の並び（ベクトル）に変換したもの |
| **選択肢（option）** | ゲームがプレイヤーに提示する「取れる行動の候補」1つ1つ（例:「ポフィンを使う」「このポケモンで攻撃する」）。1回の判断につき数個〜十数個提示される |
| **card_id** | カード1種類ごとに振られた識別番号。「このカードはポフィンだ」「このカードはアラカザールだ」という**カードの正体そのもの** |
| **embedding（埋め込み）** | card_id のような離散的な番号を、学習によって意味のある小さな数値ベクトルに変換する仕組み。似た性質のカードは似たベクトルになるように学習される |
| **pointwise（各点ごと）スコアリング** | 複数の選択肢がある中で、**各選択肢を他の選択肢を見ずに独立に点数付けする**方式。現在のモデルはこれ |
| **Transformer / self-attention（自己注意）** | 複数の要素（単語やカードなど）の集まりを入力として、「要素同士がどれくらい関係し合っているか」を学習しながら、各要素の表現をお互いの情報を使って更新する仕組み |
| **Deep Sets** | Transformer より単純な、「順序のない集合」を扱うための仕組み。各要素を独立に変換したあと平均や最大値で集約するだけで、要素同士の直接のやり取り（attention）は行わない |
| **pooling（プーリング）** | 複数の要素のベクトルを、平均・最大値・合計などの単純な演算で1本のベクトルにまとめる操作。Deep Sets の集約はこれにあたる |
| **cross-attention（相互注意）** | ある要素（クエリ）が、別の集合（キー・バリュー）に注意を向けて関連度を計算する仕組み。この文書では「1つの選択肢が、手札や場のカード集合を見ながら自分の評価を調整する」場面で使う |
| **Value（価値・局面評価）** | 「今の局面がどれくらい有利か」を1つの数値（例: 勝率0〜1）で表したもの。個々の行動ではなく盤面そのものを評価する |
| **Elo（イロ）レーティング** | 対戦ゲームの強さを表す指標。チェスの格付けで有名。差が大きいほど実力差が大きいことを表す。本プロジェクトでは「勝率」よりも施策の効果を比較しやすい指標として使っている |
| **アブレーション（ablation）** | ある改善が「何によって効いているのか」を切り分けるため、要素を1つずつ抜いた／潰した版を作って比較する実験手法 |
| **roadmap（ロードマップ）文書** | このプロジェクトの改善作業の進め方をまとめた文書（[roadmap-2026-08-05.md](../roadmap-2026-08-05.md)）。「C2」「C5」はその文書内でつけられた作業項目の通し番号 |

## 1. 結論（先に書く）

**「今のモデルを丸ごと Transformer に置き換える」設計は推奨しません。** 小さく段階を踏んで
導入する設計にしています。理由は3つあります。

1. **過去の実験で「モデルを大きくするだけでは強くならない」ことが分かっている。**
   隠れ層のサイズを 32 → 128（4倍）にしても勝率はほぼ変わりませんでした（Top-1一致率で +0.58pt）。
   Transformer もただ大きく複雑にするだけでは同じ壁にぶつかる可能性が高いです。
2. **本番の対戦プログラムは、ライブラリに頼らない素の Python コードだけで動いています。**
   numpy すら使っておらず、1つの判断につき使える時間には厳しい制約があります（具体的な数値は
   §9 で扱いますが、この文書の初版で使った「0.4秒」という値は本番の真の制約かどうか
   未確認だったため、以後は「要実測・要確認」として扱います）。Transformer をそのまま
   実装すると計算コストが増え、この時間制約を超える恐れがあります。
3. **「カードの正体（card_id）が入力にそもそも入っていない」問題と、「入っているが選択肢同士を
   比較する仕組みがない」問題は、実は別の問題です。** 前者は安価に直せます（後述）。
   Transformer が本当に必要なのは後者だけです。両者を混同すると、安く直る問題に
   高いコストをかけてしまいます。

この設計書がやることは、「カード同士の関係」という課題を上記の2種類に切り分け、
安い方から着手し、Transformer 相当の仕組み（Set Encoder・Option Encoder と呼びます）は
**最小構成から**段階的に導入する計画を作ることです。

**もう1つ大事な原則: Transformer を「万能部品」として扱わない。** 計算量・過学習・実装コスト・
本番の推論速度という制約がある以上、「必要な情報を足す」→「必要な構造だけ足す」→
「本当に必要な箇所だけ attention を使う」という順番を守ります。モデルが見ていない情報は
どんな構造を使っても学習できないため、**構造を複雑にする前に、まず入力の情報を補うことを優先します。**

## 2. 背景 — 「カード関係が考慮されない」の具体例

ポケモンカードには、単体では機能せず、他のカードと組み合わせて初めて価値が出るカードが
多くあります。実際に問題になった例を3つ挙げます。

| 具体例 | 何が起きているか | どちらの問題か |
|---|---|---|
| 手札に「ポフィン」（HP70以下のたねポケモンなら何でもベンチに出せる道具）と「テレパス超エネルギー」（超タイプのたねポケモンしかベンチに出せない特殊エネルギー）の両方があるとき、テレパス超エネルギーは超タイプ限定なので使える対象が狭い。**制約が強い方から先に使うべき**（テレパス超エネルギーで超タイプを出し、汎用のポフィンは他に温存する） | 「テレパス超エネルギーで出す」と「ポフィンで出す」は別々の選択肢としてそれぞれ独立に点数化される。**この2つの選択肢を比べて「こちらは制約が強いから優先すべき」と判断する仕組みがない** | ② 選択肢同士を比較する仕組みが無い |
| あるポケモンは「進化すると手札を3枚引いて自分を山札に戻す」特性を持つ。このループの価値は、サーチ札（デッキから特定のカードを探して手札に加える道具）が手札にあるかどうかで大きく変わる | 場のポケモンは「HP・攻撃力」など汎用的な数値でしか表現されておらず、**「これが誰なのか」という情報がモデルに渡っていない**。加えて「手札のサーチ札と組み合わせると強い」という関係も見えない | ① カードの正体が入っていない + ② 関係を見る仕組みが無い |
| 相手が特殊なエネルギーを付けていると、自分の主力ワザのダメージが 0 になってしまうことがある。その場合は「エネルギーを剥がす道具」を最優先で使うべき | 相手の場に付いているエネルギーの正体（card_id）がモデルの入力に入っていない | ① カードの正体が入っていない |

**①「カードの正体が入っていない」問題**は、モデルへの入力に足りない情報を追加するだけで
直せます（比較的安価）。roadmap 文書ではこれを **「C2」** と呼んでいます。

**②「選択肢同士を比較する仕組みが無い」問題**は、モデルの構造そのものを変える必要があります
（比較的高価）。roadmap 文書ではこれを **「C5」** と呼んでいます。

この2つを混ぜずに順番に対処する、というのがこの設計書の骨子です。

## 3. 現状のモデルの仕組みと限界

まず、今のモデルが実際に何をしているかを説明します（2026-08-08 時点でコードを確認した内容。
**2026-08-09 に T1 を完了したため、次元数は当初の251から715に変わっています**。
以下の表は実装後の状態です）。

### 3.1 「状態」を数値の並びに変換する

1つの判断のたびに、盤面全体を **715個の数字が並んだベクトル** に変換します（実装前は251個）。
内訳は次の通りです。

| 内容 | 個数 | カードの正体（card_id）を含むか |
|---|---:|---|
| 場のポケモン（自分の場6体＋相手の場6体、各11種類の数値） | 132 | **含まない**。「HPの割合」「今つけているエネルギーの数」「攻撃力」など汎用的な数値のみ。「これはアラカザールだ」という情報はここには無い |
| **自分の場（active+bench）に何のカードが何体いるか**（T1、2026-08-09実装） | 56 | **含む**。デッキに入っている56種類のカードそれぞれについて「場に何体いるか」を数えている |
| **自分の手札に何のカードが何枚あるか** | 56 | **含む**。デッキに入っている56種類のカードそれぞれについて「何枚手札にあるか」を数えている |
| 手札・山札・トラッシュ・サイド・ベンチの枚数 | 13 | 含まない（枚数だけ） |
| **自分のトラッシュに何のカードが何枚あるか**（T1、2026-08-09実装） | 56 | **含む**。同上56語彙をトラッシュのカウントにも使う |
| **相手の場（active+bench）に何のカードが何体いるか**（T1、2026-08-09実装） | 176 | **含む**。POOL8全アーキタイプの代表デッキに含まれる全カードの和集合（157種+余裕）を専用語彙として使う |
| **相手のトラッシュに何のカードが何枚あるか**（T1、2026-08-09実装） | 176 | **含む**。同上176語彙をトラッシュのカウントにも使う |
| 状態異常・ターン経過などその他 | 27 | — |
| 相手のトラッシュの傾向（ドロー系カードが何枚など、種類ごとの集計） | 6 | 含まない。「何のカテゴリのカードが何枚」という集計であって、個別カードの識別ではない |
| 相手がどのデッキタイプらしいか、勝敗までの見通しなど | 14 | 含まない（デッキ全体としての「誰か」の確率分布であって、盤面個々のカードの正体ではない） |

つまり、**自分の手札・自分の場・自分のトラッシュ・相手の場・相手のトラッシュのすべてについて
「何のカードが何枚/何体あるか」という情報が既にモデルに入っています。** 自分側の3ゾーンは
自分のデッキに紐づく56種類の語彙を、相手側の2ゾーンは POOL8（評価・学習で使っている8
アーキタイプ）全体の代表デッキから作った176種類の語彙を、それぞれ共有しています（§5.3 の
「同じ card_id は同じ位置」という方針を、実装時にカウント特徴の段階から先取りしました）。

相手側の語彙は「相手のデッキが試合開始時点で不明」という制約があるため、自分側のように
「そのデッキ専用」の語彙ではなく、**既知のメタ8アーキタイプの和集合**という近似を使っています。
POOL8 に含まれないアーキタイプの相手と対戦した場合、語彙に無いカードは単に数えられないだけで
安全にフォールバックしますが、その分の情報は失われます（§9 論点11 に詳細と限界を記載）。

### 3.2 「選択肢」を数値の並びに変換する

提示された各選択肢（「このカードを使う」「このポケモンで攻撃する」など）は、65個の数値
（対象カードの種類・HP・攻撃力など）に加えて、**その選択肢が指しているカード1枚だけ**を
8個の数値（embedding）に変換したものが使われます。つまり「選択肢が指すカード」の正体は
実はモデルに入っています。ただしこれは選択肢ごとに独立に計算されるため、
**「他の選択肢や場の他のカードと比べてどうか」という文脈は一切持ちません。**

### 3.3 判断の仕方（pointwise スコアリング）

251個（状態）＋65個（選択肢）＋8個（そのカードの正体）＝324個の数字を1本のベクトルにつなげ、
「隠れ層32個のニューロン」を1層だけ持つ小さいニューラルネットワークに通し、1個の点数を出します。

**これを選択肢の数だけ、それぞれ独立に繰り返します。** 全選択肢の点数が出そろったら、
一番高い点数の選択肢を選びます。これが §0 で説明した「pointwise（各点ごと）スコアリング」です。
**選択肢Aを点数化するとき、選択肢Bの情報は一切見ません。**

本番の対戦プログラムはこの計算を、numpy 等のライブラリを使わない素の Python コードで行っており、
選択肢1個の点数計算に約4ミリ秒かかります（隠れ層32個の場合）。

### 3.4 現状モデルの限界（整理）

上記を踏まえ、現状の限界を6つに整理します（外部レビューの分類を採用）。

| # | 制約 | 内容 |
|---|---|---|
| **A** | 公開情報の不足 | **T1 完了（2026-08-09）により大幅に解消。** 自分側（手札・場・トラッシュ）は自分のデッキ語彙で、相手側（場・トラッシュ）は POOL8 の和集合語彙で、カードの正体が入るようになった。**残る限界**: 相手側は「既知のメタ8アーキタイプ」という近似であり、真の相手デッキそのものではない（§3.1、§9 論点11） |
| **B** | カード集合を構造的に扱えていない | 手札・場・トラッシュは本来「順序のない集合」だが、単純な集計（枚数カウント）や固定長の汎用数値でしか表現されておらず、カード間の組み合わせ・シナジーを表現しにくい |
| **C** | 候補行動を独立評価している | pointwise スコアリングにより、ある選択肢を評価するとき他の選択肢の存在を直接見ない。しかし本来の意思決定は「この行動が良いか」ではなく「今出ている候補の中でどれを選ぶべきか」である |
| **D** | 履歴情報が不足している | 現在の盤面のスナップショットだけでは、「このターンに何をしたか」「直前に何をサーチしたか」「既に使った一度きりの効果」などが失われる可能性がある。現状、これを補う仕組みは実装されていない |
| **E** | 非公開情報の推定が方策に届いていない | 相手の手札・山札は完全には見えないが、サーチ履歴やデッキタイプ推定から非公開情報を推定する仕組み（`OwnHiddenState`/`OpponentHiddenState`、§10 参照）は**既に実装済み**。ただし探索の初期化にのみ使われており、**方策（BC モデル）本体には接続されていない** |
| **F** | BC のラベル自体の限界 | 教師（上位プレイヤー）が選んだ行動を正解として学習するため、「他にも良い行動があった」「教師自身のミス」「勝敗結果の違い」「終盤の重要度が低い行動」などを区別できない。これはモデル構造の問題ではなく学習方法の問題であり、§10 で扱う |

**この設計書が主に扱うのは A・B・C です。** D・E・F はこの設計の直接のスコープ外ですが、
関連する既存実装や将来の拡張候補として §10 にまとめます（無関係ではないため、混同しないよう
明示的に切り分けます）。

## 4. 設計の基本方針

過去の実験からいくつかの教訓が得られており、それをこの設計にも適用します。
（「なぜこの方針か」を各項目に添えています）

1. **①（カードの正体を足す）と②（比較する仕組みを作る）を混同せず、①から先に、
   小さく1つずつ進める。** 過去に「複数の改善を一度に入れて、どれが効いたか分からなくなる」
   失敗が繰り返されているため。
2. **カードの正体は、まず一番単純な「枚数を数えるだけ」の形で入れてから、
   embedding（学習される数値ベクトル）に発展させる。** そうすることで
   「情報自体が足りなかったのか」「情報はあったが表現の仕方が悪かったのか」を切り分けられる。
3. **モデルを大きくすること自体を目的にしない。** §3.4 の教訓の通り、単純な拡大は効果が薄い。
   新しい仕組み（Set Encoder、後述）も最小サイズから始め、効果が確認できてから広げる。
4. **既存の手作業の特徴量は原則そのまま残す。** これまで積み上げてきたゲーム知識
   （相手の特性でダメージが無効化される計算など）には価値がある可能性が高い。新しい学習表現は
   「既存の特徴量 + 新しい表現」として付け足す形にし、いきなり既存を置き換えない。
5. **比較実験（A/Bテスト）は、同じ構造のまま一部の情報だけを潰した「対照群」と比べる。**
   構造ごと入れ替えて新旧を比べると、何が効果の原因か分からなくなるため。
6. **判断の基準は「勝率（Elo に変換した値）」を主指標にする。** モデルが教師の手をどれだけ
   真似できたか（Top-1一致率）は、実際の勝率と食い違うことが繰り返し確認されているため、
   参考程度の診断用にとどめる。**「一致率は上がったが Elo は変わらない」という結果が出た場合、
   原則としてその改善は採用しない。**
7. **1回の比較実験には、片方あたり約3,500試合、3回以上の学習やり直し（乱数シードを変えて）が必要。**
   統計的なばらつきに対して十分な精度で差を検出するため（過去の測定で必要な規模が判明している）。
   Elo は平均だけでなく、シード間のばらつき（標準偏差）も併記して比較する。
8. **「この局面ではこのカードが常に高得点」のような固定的な評価は作らない。** 同じカードでも
   自分が有利な局面と不利な局面では最適な扱いが逆転することが実験で確認されている
   （優勢な側は強いポケモンを迂闊に前に出すべきではない、など）。新しい仕組みも、
   常に周囲の状況込みで判断する形にする。
9. **改善が「何によって」効いたのかを切り分ける（アブレーション・Negative Control）。**
   たとえば「カードの正体を入れたら強くなった」という結果が出ても、それが本当に
   card_id という情報のおかげなのか、それとも単に入力の次元が増えたこと自体の副作用なのかは
   別問題です。**本物の card_id を使った版と、card_id をランダムな数字やシャッフルした数字に
   すり替えた版を比較し、ランダム版では効果が出ないことを確認して初めて「card_id の正体に
   意味がある」と言えます。** これは既存の「対照群は情報だけを潰して作る」方針の延長です。
10. **各段階に「効果が無ければ次に進まない」という打ち切り基準を先に決めておく。**
    前段階の効果を前提に次を積み増す設計なので、効果の無い土台の上に積み増すと
    何が効いているのか分からなくなるため。

## 5. 新しいアーキテクチャの設計

### 5.1 全体像

現在のモデルに、**「Set Encoder」「Option Encoder」という新しい部品を追加**します。
Set Encoder は「バラバラの複数のカードの集まり（例: 手札6枚、場の12体）を受け取り、
カード同士の関係を考慮した上で、その集まり全体を表す1本のベクトルにまとめる」部品です。
Option Encoder は「今出ている選択肢どうしを比較しながら、各選択肢の評価を調整する」部品です。

```
                 ┌─────────────────────────┐
場のポケモン12体 → │                          │
                 │   Set Encoder            │ → まとめられたベクトル（新規）
自分の手札      → │  （カード同士の関係を学習） │
                 │                          │
                 └─────────────────────────┘
                              ↓
             ┌────────────────────────────────┐
             │ 既存の 251次元（状態）＋65次元（選択肢） │  ← 今までの入力はそのまま残す
             │           + 新しいベクトルを連結         │
             └────────────────────────────────┘
                              ↓
                        Option Encoder
               （他の選択肢の存在を踏まえて調整、新規）
                              ↓
                     今までと同じ小さいネットワークで点数化
```

**既存の入力は削らず、そこに新しい情報の経路を足す形にします。** これまで積み上げてきた
手作業の知識を失わないようにするためです（§4 原則4）。

### 5.2 どの集まりを「カードの集合」として扱うか（Set Encoder の対象）

| 集まり | カードの数 | 現状 | この設計での扱い |
|---|---|---|---|
| 場のポケモン（自分6体＋相手6体） | 12（固定。空き枠は「空」として扱う） | 汎用数値11個のみ、正体なし | カードの正体（embedding）＋既存の11個の数値を1枚ずつのカードデータとして Set Encoder に渡す |
| 自分の手札 | 可変（0〜10枚程度、実データで分布を確認して上限を決める。§6.1） | 「何を何枚持っているか」の集計のみ | カード1枚1枚を Set Encoder に渡す（集計ではなく個別カードとして扱うことで、組み合わせを学習できるようにする） |
| 自分・相手のトラッシュ | 可変 | ほぼ未使用（相手トラッシュは大まかな傾向の集計6個のみ） | カード1枚1枚を Set Encoder に渡す。**相手のトラッシュは完全に見えている情報なのに、これまでほとんど使われていなかった** |
| 相手の手札 | — | 使用不可（見えない情報） | 対象外。「このカードを相手がまだ持っている確率」のような推定値は既に別の仕組みで計算されており（§10）、数値として使えるが、カード集合としては扱わない |

### 5.3 カードの表現（embedding だけでなく構造化情報も使う）

カードの正体を数値化する方法として、単に「card_id → 学習される小さいベクトル」（embedding）
だけに頼るのではなく、**カードの機能に関する構造化された情報も一緒に持たせます。**

```
カード1枚の表現 =
  [ card_id embedding,          ← 「このカードを覚える」ための表現
    カードの構造化プロファイル,   ← 「このカードが何をするか」を表す既存知識
    どのゾーンにあるか（手札/場/トラッシュ）,
    誰の持ち物か（自分/相手）,
    現在の数値（HP割合・エネルギー数など、既存の11特徴を流用） ]
```

**構造化プロファイルとは**: このプロジェクトには既に、デッキやカードの機能的な性質
（サーチ効果を持つか、ドロー効果を持つか、等）を扱う仕組みが `sample_submission/ptcg_ai/shared/`
配下の `profile_registry.py` / `profile_types.py`、および `card_roles.py`（役割分類）として
存在します。これらが持つ「機能的な意味」の情報を、card_id embedding とは別の入力として
カード表現に足すことで、**「特定のカードを丸暗記する能力」と「カードの機能を理解する能力」を
分離**できると期待されます。学習データが少ない新しいカード・レアなカードでも、
構造化プロファイル側からある程度の判断ができるようになる可能性があります。

（注: 個別ファイル `pokemon_profiles.py` 等が存在するという情報が外部レビューにありましたが、
2026-08-08 時点のコード確認では該当ファイル名は見つからず、上記の `profile_registry.py` /
`profile_types.py` および `card_roles.py` が実体でした。実装時は改めてこの2ファイルを起点に
调査すること。）

### 5.4 Set Encoder の中身は2段階で試す

いきなり本格的な Transformer を作らず、まず一番単純な version から試します。

- **段階1: Deep Sets（単純な集約のみ）** — 各カードを個別に変換したあと、
  平均・最大値・合計を取ってまとめるだけ。カード同士が直接やり取りする仕組みは無い。
  実装が軽く、計算コストも低い。
  - **平均（mean）**: 集合全体の平均的な傾向を表す
  - **最大値（max）**: 特に重要な1枚の存在を拾う（「キーカードが1枚でもあるか」に強い）
  - **合計（sum）**: 集合の規模・密度を表す（手札の枚数が多いこと自体の効果など）
  - この3種類を並べて使うことを推奨します（単一のpoolingより情報量が増えるため）。
- **段階2: Set Transformer（自己注意つき）** — 段階1に、カード同士が
  「お互いにどれくらい関係が強いか」を学習しながら情報を交換する層（self-attention）を追加する。

**この2段階を分けて試す理由**: 「複数のカードをまとめて見られるようにしたこと自体の効果」と
「カード同士が直接影響し合う仕組み（本来の Transformer らしさ）の効果」を分離して測定するためです。
段階1だけで十分な効果が出るなら、より重い段階2は不要かもしれません。

### 5.5 選択肢の点数付けをどう変えるか（Option Encoder、3段階）

いきなり本格的な仕組みを作らず、こちらも安価な方法から段階を踏んで試します。

- **段階1: 何もしない（現状のまま）** — 比較の基準点。
- **段階2: Option Pooling（最も安価）** — 各選択肢の評価に、
  「他の選択肢たちの平均・最大値」と「今出ている選択肢の総数」を単純に追加情報として
  付け足します。

  ```
  選択肢Xの新しい入力 =
    [ 選択肢Xそのものの情報（既存の65+8次元）,
      他の選択肢たちの平均,
      他の選択肢たちの最大値,
      選択肢の総数,
      盤面全体の状態（既存の251次元、または5.4のSet Encoderの出力） ]
  ```

  これだけでも「今出ている候補全体を踏まえた評価」に一歩近づきます。自己注意（attention）を
  使わないため実装コストが低く、まず試す価値があります。
- **段階3a: 決定的ポインタ参照（pointer gather、Cross Attention より軽量な選択肢）** —
  選択肢の中には「攻撃対象のこのポケモン」「にげる先のこのベンチポケモン」のように、
  **場のどのカードを指しているかが一意に決まる**ものが多くあります。この場合、
  attention のように「どこに注目すべきか」を確率的に学習させる必要はなく、
  ゲームエンジンが返す試合内で一意な識別子（例えば場のポケモン1体ごとに振られる通し番号）を
  使って、Set Encoder が作った該当ポケモンのトークン表現をそのまま取り出し（gather）、
  選択肢の特徴に連結するだけで済みます。

  ```
  選択肢 X の最終表現 = concat(card_embed(option.card_id), option_features,
                               盤面トークン群のうち option が指す1体をそのまま取り出したもの)
  ```

  **この方式には利点が2つあります。** (1) attention の行列計算が不要なので、
  素の Python でも軽く実装できる。(2) 対象が一意に決まる場面では、
  「注目先を近似的に学習する」attention よりも原理的に正確です（学習で外す余地がない）。
  ただし、この方式が使えるのは「選択肢が指す対象が一意に定まる」場合に限られます。
  対象を持たない選択肢（「はい/いいえ」「ターン終了」など）には使えないため、
  そうした選択肢向けに、学習される共通の代替ベクトル（対象なし用の embedding）を
  別途用意する必要があります。
- **段階3b: Cross Attention（対象が一意に定まらない場合の本格的な仕組み）** —
  段階3a が使えない、または段階2で効果が確認できた場合に導入を検討します。
  各選択肢を「クエリ」として、Set Encoder が作った盤面・手札のカード集合に注意を向けさせ、
  関連度を計算しながら評価を更新します。これにより「この選択肢（ポフィンで出す）は、
  手札の他のカード（テレパス超エネルギー）と比べてどうか」を選択肢自身のスコアに反映できます。

  ```
  選択肢 X の最終表現 = CrossAttention(query=card_embed(option.card_id) ++ option_features,
                                        key/value=[盤面トークン群, 手札トークン群])
  ```

**選択肢同士を完全に直接比べ合う仕組み（例えば10個の選択肢全部をお互いに self-attention
させる）は、この設計のスコープには含めません。** 実装・計算コストが最も重くなる部分であり、
まずは段階2・3a・3b で十分な効果が出るかを確認してからにします。

**段階3a と 3b は排他ではなく併用できます。** 対象が一意に決まる選択肢は段階3a（安価・正確）、
決まらない選択肢だけ段階3b（cross-attention）を使う、という使い分けが実装コストの面で
最も理にかなっています。

## 6. 学習・実装への影響

### 6.1 可変長データの扱いと上限の決め方

手札の枚数・トラッシュの枚数・選択肢の数はいずれも局面によって変わります（可変長）。
Set Encoder / Option Encoder を実装するには、これらを揃った長さのデータとして扱うための
「上限を決めて、足りない分は空きとして埋める（パディング）」処理が必要です。

**上限は勘で決め打ちせず、実際のリプレイデータから分布を測定して決めます。** 具体的には
手札の枚数・トラッシュの枚数・選択肢の数・（後述する）履歴の長さについて、
50パーセンタイル（中央値）・90・95・99パーセンタイル・最大値を集計し、
「99%のケースをカバーできる上限」のような形で決定します。極端に大きい外れ値のために
無駄にモデルを大きくしないためです。

### 6.1.1 card_id を番号（embedding の索引）に変換する台帳の管理

embedding は「card_id → 内部の連番（index）→ ベクトル」という2段階で実装するのが一般的です。
このとき、**card_id と内部連番の対応表（語彙）をどう管理するか**は見落とされがちですが、
重要な設計判断です。

- **カードの生の ID をそのまま連番として使わない。** 生の card_id が「連続した番号である」
  という前提は、新しいカードが追加されたり欠番があったりすると壊れます。必ず専用の対応表
  （`card_id → 内部連番`）を明示的に作り、ファイルとして保存します。
- **既存カードの連番は変更しない・新しいカードは末尾に追加するだけにする（追記専用）。**
  学習済みモデルは「連番Xはこのカード」という前提で重みを学習しているため、
  途中で並べ替えると、それまでの学習結果がすべて無意味になります。
- **未知のカード・空き枠（パディング）用の特別な番号を最初から確保する。** 学習データに
  無かった新しいカードに遭遇したときに落ちないようにするため、および可変長データを
  埋めるパディング用に、それぞれ専用の番号を予約しておきます。
- **対応表の内容ごと、ハッシュ値のようなもので整合性を確認できるようにする。** 学習時と
  本番推論時で対応表がずれていると、モデルは「別のカード」を見ていることになり、
  誤動作が静かに起こります。対応表が一致していることを、モデルの読み込み時に必ず検査します
  （既存の「次元が合わなければ安全側にフォールバックする」仕組み、§9 論点5、と同じ考え方の
  延長です）。

### 6.2 学習データの準備・学習（サーバー上、時間制約が緩い）

現状、選択肢の情報は「1回の判断ごとに個数が変わる」形ですでに扱われているため、
可変長のデータを扱う仕組み自体はプロジェクトに既にあります。今回は同様の仕組みを
場のポケモン・手札・トラッシュにも広げる必要があります。学習自体はこれまで通り、
時間制約の緩い環境（PyTorch, CPU）で行います。

### 6.3 本番での推論（対戦中の実際の判断、時間制約が厳しい）

**ここが一番のリスクです。** 本番の対戦プログラムは numpy すら使わない素の Python で動いています。
1つの判断あたりに使える時間について、この文書の初版では「0.4秒」という数値を使っていましたが、
**これが Kaggle 側の本当の制約なのか、プロジェクト内部の目標値なのかは未確認です。実装に入る前に
実測・仕様の確認を行い、正確な値を明記し直します**（§9 未解決事項）。

いずれにせよ、以下の最適化方針を徹底します。

- **Set Encoder の計算は1回の判断につき1回だけでよい**（選択肢の数だけ繰り返す必要はない）。
  単純な集約（Deep Sets、段階1）は行列の掛け算を伴わないため、素の Python でも軽く実装できます。
- 自己注意（Set Transformer / Cross Attention）は行列の掛け算を伴います。対象となるカードの数は
  最大でも20枚程度なので計算量自体は小さいですが、素の Python のループで書くと
  意外と時間がかかる可能性があります。numpy の利用可否をチームと相談するか、
  小規模な掛け算専用の軽量な実装に留めるかを、この段階になったら判断します。
- 選択肢ごとの点数付け（Option Encoder の段階3、cross-attention）は選択肢の数だけ計算が増えるため、
  コスト増に最も敏感な部分になります。
- embedding の参照（lookup）や、選択肢ごとに生成する一時的なデータ構造をできるだけ減らし、
  固定長のループに近づけることで、Python 特有のオーバーヘッドを抑えます。
- 十分な効果が確認できた重いモデルについては、**軽量なモデルへ「蒸留」**（大きなモデルの判断を
  真似するように小さなモデルを再学習する手法）することで、本番用に速度を落とす選択肢も
  将来的に検討します（§10）。
- 推論時間は平均だけでなく、**p50（中央値）・p95・p99**（遅い方から数えて上位1%のケース）まで
  記録します。ゲームは時間制限があるため、平均が速くても稀に遅いケースがあると危険なためです。

## 8. 効果の測定方法

- 主な判断基準は**勝率（Elo に変換した値）**とします。モデルが教師データの手をどれだけ
  真似できたか（一致率）は目安程度に使い、採用・不採用の決め手にはしません。
  **「一致率だけ上がって Elo が変わらない」場合は、原則としてその変更を採用しません。**
- 比較実験は、**片方あたり約3,500試合、3回以上の学習やり直し**で行います（乱数の運による
  ばらつきを除くため）。Elo は平均値だけでなく、シード間のばらつき（標準偏差・信頼区間）も
  合わせて報告します。
- 新しい仕組みを入れた版と入れない版を比べるとき、**入力の次元や構造をなるべく揃え、
  情報だけを抜いた「対照群」**を作って比較します（構造ごと変えて新旧を比較すると、
  何が効果の原因か分からなくなるため）。
- **Negative Control（本物の card_id と、ランダム化した card_id の比較）を必ず行います。**
  本物の card_id を使った版だけが改善し、ランダムな番号やシャッフルした番号を使った版は
  改善しない、という結果が出て初めて「card_id という情報そのものに意味がある」と言えます
  （単に入力の次元が増えたことによる副作用ではないことの確認）。
- Set Encoder のサイズ（内部のベクトルの次元数、層の数）についても、
  小さい構成から順に試し、「大きくしても変わらない」地点を確認したらそこで打ち切ります。
- **行動の種類別（攻撃・後退・道具使用・など）の一致率は、診断専用として使います。**
  「アイテムは90%当たるが後退は40%しか当たらない」のような分解は、モデルのどこが弱いかの
  当たりをつけるのに有用ですが、統計的なばらつきが大きいため、**採用・不採用の判断には
  使いません**（全体の一致率や勝率で判断します）。
- **デッキタイプ別の Elo も確認します。** 全体の Elo だけを見ていると、特定のデッキタイプにだけ
  強く・別のタイプには弱くなったモデルを見逃す可能性があるためです。
- ポフィン＋テレパス超エネルギーのように、正解が明らかな局面をいくつか手動で選び出し、
  各段階の前後でモデルの判断が実際に変わったかを個別に確認します（統計的な検定とは別の、
  設計が意図通り機能しているかの目視チェック）。対象とする局面のカテゴリ例:
  1. 制約の強いカードを先に使うべき局面（ポフィン＋テレパス超エネルギー型）
  2. 汎用カードを温存すべき局面
  3. 相手の特殊エネルギー・特性への対応（ハードカウンター）
  4. トラッシュの中身から山札の残りを推定すべき局面
  5. 終盤の勝ち筋の選択
  6. 不利な局面でリスクを取るべき局面 / 有利な局面でリスクを避けるべき局面
- **少ない試合数（数百試合程度）の比較結果は「明らかな崩壊が無いかの早期チェック」に
  とどめ、それだけで採用・不採用を確定させません。** 試合数が少ないと、本当の実力差が
  無くても偶然差がついて見えることがあります（例えば真の勝率が五分でも、300試合程度の
  比較では偶然大きな差が出る確率が無視できません）。§4 原則7の「片方あたり約3,500試合」を
  最終判断の基準とし、数百試合の結果はその前段階のふるい落としとして使います。
- **可能であれば、最終的な採否判断にはローカルの固定評価だけでなく、実際のコンペへの
  提出結果も参考にします。** ローカルの固定相手プールでの評価は、それ自体が
  「その固定相手にだけ最適化されていないか」という過適合のリスクを持ちます（§4 原則5の
  対照群作りと同じ発想を、評価相手の選び方にも適用する）。ローカル指標同士では優劣が
  つかない・僅差である場合ほど、この観点が重要になります。ただし Kaggle への提出は
  1日あたりの回数に上限があるコンペ共有の資源であるため、あらかじめ何を検証したいかの
  仮説を決めてから使う（無計画に何度も提出して一番良い結果だけを採用しない）ことを
  徹底します。

### 8.1 評価実行手順（2026-08-09 検証済み）

### 8.3 T1本番実行（2026-08-09〜10）と、`--ablate-features` の重大バグ発見・修正

**本番規模データ（全818,350決定点）で `features_marnie_grimmsnarl_ex_t1.npz` と
Negative Control用のシャッフル版をビルドし、T1（フルT1 vs ablate対照群）を3シード
（42, 1, 2）で Kaggle Notebook へ実際に投入した。3シードとも `COMPLETE` で完走し、
処置群 vs 対照群のミラー戦（3,500試合）まで完了した。**

**1回目の結果は無効と判定した。** seed=42 の結果は処置群が対照群に対し
**3500試合中3459勝（98.83%）** という極端な値だった。これは「T1特徴が効いている」
というには不自然に強すぎる差であり、[measurement-plan-2026-08-04.md](../measurement-plan-2026-08-04.md)
§3.1 が警告している既知の罠と一致する疑いを持って対照群の重み JSON を検証した。

**実際にバグを確認した。** `--ablate-features` で潰した列（学習データ内でずっと0）は、
標準化の `std < 1e-6 → 1e-6 にクリップ` という既存ロジックにより **std=0 ではなく
std=1e-6 になっていた**（464次元中464次元がこの状態）。本番推論（`policy_model.py`
の `_forward`）は `(x - mean) / std if std else 0.0` という「std が偽（0）なら
0 扱い」の分岐を持つが、std=1e-6 は真なので通常の除算が行われる。ミラー戦では
対照群への入力に **ablate されていない実際のゲーム値**（T1特徴、ゼロでない）が
入ってくるため、`(実際の値) / 1e-6` で桁違いの異常値が生成され、**対照群の判断が
数値的に壊れていた**。今回の設計書 §4 原則5「対照群は情報だけを潰して作る」を
実装する際に、この罠への対策（measurement-plan の「対戦評価に使う場合は重み JSON
の該当 std を 0 に書き換える」）を組み込み忘れていたのが原因。

**`train.py` を修正した（2026-08-10）**:
- `--ablate-features` で潰した列のインデックス（`ablate_st_idx`/`ablate_op_idx`）を、
  標準化の `std<1e-6` クリップ計算の**後**に使い、該当列の `state_std`/`option_std`
  （および `state_mean`/`option_mean`）を明示的に 0 へ上書きする。これで
  `policy_model._forward` の `if std else 0.0` 分岐を確実に踏ませる。
- 上記だけでは学習側（numpy での `(x - mean) / std` という素の除算）が std=0 で
  `0/0` の **NaN** を出すようになったため（実際に `nll=nan` を再現した）、学習側
  （`state_features_std`/`option_features_std` の計算）と自己検証用の float64 計算
  （`state_std64`/`option_std64` を使う箇所）の両方に、`np.where(std==0, 0.0, ...)`
  で std=0 の列だけ結果を 0 に固定するガードを追加した。推論側（`policy_model.py`）
  は変更していない（本番推論コードは既に正しい設計だった。学習側だけが
  ズレていた）。
- 修正後、ローカルの小規模テストで自己検証（PyTorch vs pure Python）が誤差
  1.25e-16 で PASS し、`nll` も正常な値（NaN でない）に戻ることを確認した。
  `sample_submission/tests/unit/` 全341件パスも再確認済み。

**教訓**: 「対照群を作るときの罠」として §4 原則5・measurement-plan §3.1 に文章では
記載していたが、**実装時にチェックリストとして踏襲するのを怠った。** 「知識として
知っている」ことと「実装に組み込む」ことの間にギャップが生じた実例。今後
`--ablate-features` を使う対照群を作る際は、この修正が入った `train.py`
（2026-08-10以降）を使う限り自動的に対策されるが、**同種の罠（既知の対策を新しい
実装に機械的に適用し忘れる）は他の箇所でも起こりうる**ため、対照群を使った評価では
常に重み JSON の standardization を一度検査する習慣を残す。

**次のアクション**: 修正版 `train.py` で T1 の3シードを再実行する（features.npz の
再ビルドは不要、学習からやり直すだけでよい）。1回目の結果（98.8%等）は

- T1特徴（自分・相手の盤面/トラッシュの card_id カウント、715次元中新規追加分）が
  過学習気味で、held-out的中率は保っているが実際の判断の質（相手の一手先を見た
  ときの頑健性）を落としている可能性。3シード中2シードで処置群の epochs_trained が
  対照群より少なく、この仮説と整合する。
- 評価コード（mirror-match, eval_diagnostics.py）側に、処置群と対照群で非対称な
  扱いをしてしまっているバグが残っている可能性（未検証。両モデルとも同じ
  `policy_model.py` の実行パスを通るはずだが、要再確認）。

と結論したが、**この結論は評価ハーネスのバグにより大部分が誤りだったことが後の原因調査で

### 原因調査の結果（2026-08-11 追記）

上記3仮説のうち「評価コード（mirror-match）側に処置群と対照群で非対称な扱いをしてしまって
いるバグが残っている可能性」を最初に確認したところ、**実際にバグが見つかった。**

**発見したバグ**: ミラー戦の実体は `eval_diagnostics.py` → `collect_pool.py` →
`collect_parallel._play_one` だが、この `_play_one`（`kaggle_replays/rl/collect_parallel.py`
118〜154行）は元々 RL 軌跡収集用に設計されており、**"learner" 役と "opponent" 役で意思決定が
非対称**になっている:

- **learner 役**（単一選択）: `_softmax_sample(scores, temperature=0.01, rng)` —
  温度0.01の**確率的サンプリング**（`eval_diagnostics.py` の既定温度）
- **opponent 役**: 常に `PolicyModel.select_option()` / `score_options()` による
  **純粋 greedy**（argmax、サンプリングなし）

そして `push_bc_ab_eval.py` は常に **処置群(treatment)を learner 役、対照群(control)を
opponent 役に固定**していた（`eval_diagnostics.py --learner-weights <treatment> --opponents
<control>`）。つまり「処置群が負け越す」結果は、T1特徴の中身ではなく **「learner役に
固定されると、温度サンプリングのせいで純粋greedyのopponent役より構造的に不利になる」**
という評価ハーネス側のバイアスの疑いが強い。

**検証1: ロール入れ替え（seed=42、n=400、ローカル直列実行）**。
control を learner 役、treatment を opponent 役にして再測定したところ、
control（learner役）の勝率は **46.50%**（186/400）。元の測定（treatment が learner役、
n=3500）の 37.43% と合わせて連立方程式で分解すると:

```
p(learner=treatment, opponent=control) = 0.5 + skill(treatment-control) - role_penalty = 0.3743
p(learner=control, opponent=treatment) = 0.5 - skill(treatment-control) - role_penalty = 0.4650
  => role_penalty ≈ 0.080 (8.0pt, Elo換算 約-56)
  => skill(treatment-control) ≈ -0.045 (4.5pt, Elo換算 約-32、treatmentがやや不利)
```

役割バイアス（約8pt=Elo-56）が効果の大半を占め、T1固有の効果は残っても4.5pt程度
（Elo-32）という推定になった。

**検証2: 完全対称評価（seed=42、n=400、ローカル直列実行）**。
`collect_parallel.py` はチーム既存資産のため変更せず、両陣営とも
`PolicyModel.select_option()`（greedy、サンプリングなし）に統一した新規スクリプト
（`symmetric_greedy_match.py`、役割の区別自体をなくす）で treatment vs control を
直接比較した。結果: **treatment 勝率 47.25%（189/400）、Elo -19.1**。
n=400 での標準誤差は約2.5pt なので、50%からの乖離（-2.75pt）は**統計的に有意ではない**
（約1.1SD）。検証1の分解予測（skill(treatment-control)≈-4.5pt, Elo-32）とも大まかに
整合する、桁の小さい結果。

**訂正後の結論**: 当初報告した「平均 -93.5 Elo」の**大部分（目算で6割前後）は評価
ハーネスの役割非対称性バグによるものであり、T1特徴そのものの効果ではない**。
対称評価に基づくと、T1の真の効果はごく小さい（この1シード・n=400の暫定測定では
Elo -19、有意差なし）。**「T1は実戦成績を悪化させる」という強い結論は撤回する。**
現時点では「T1は明確な改善効果を確認できておらず、悪化とも言い切れない（ほぼ無風、
やや不利な可能性はゼロではない）」が正確な要約。

## 9. リスクと未解決の論点

| # | リスク・論点 | 対応方針 |
|---|---|---|
| 1 | 本番の対戦プログラムで numpy 等のライブラリを新たに使う必要が出た場合、対戦プログラム側の管轄チームとの調整が必要 | T4が終わった時点で処理時間を実測し、早めに相談する |

| 構想 | 内容 | 現状との関係 |
|---|---|---|

| **勝敗結果を使った学習（Outcome-aware Learning）** | 勝った試合の行動を重視し、負けた試合の行動を軽視するなど、勝敗結果を学習に反映する | **既に実装済み**（学習スクリプトの `--outcome-weighting` オプション）。ただし効果は未確定（一致率が下がる一方、勝率での判定が済んでいない） |
| **行動の履歴を扱う仕組み（History Encoder）** | 「このターンに何をしたか」「直近で何をサーチしたか」を直接モデルに渡す | 現状は未実装。新規のアイデア |
| **デッキ全体の傾向を扱う仕組み（Deck Encoder）** | 自分・相手のデッキ全体の構成を1つの表現にまとめる | 相手デッキのアーキタイプ推定は既に実装済み（上記 Opponent Belief 参照）。個別カード構成までを表現するデッキ全体エンコーダは新規のアイデア |
| **勝敗のその先を学習する手法（Offline RL）** | 「この行動がどれだけ将来の勝率に影響したか」を、記録済みのリプレイだけから学習する、模倣学習よりも直接的な手法 | 未実装。データの質や、学習データに無い行動への対応など課題が多く、当面は導入しない |
| **複数モデルの組み合わせ（アンサンブル・蒸留）** | 複数の異なるモデルの判断を組み合わせたり、大きな高性能モデルの判断を小さなモデルに真似させて本番用に軽量化する | 未実装。T1〜T6 が完了し、重いモデルの方が明確に強いことが確認できてから検討する |
| **ルールベース・探索との組み合わせ** | 「明らかな手はルールベースで即決し、迷う場面だけモデルに判断させ、重要局面はさらに深く探索する」といった役割分担 | **既に本番エージェントで採用されている考え方**（確定した詰みを検出する処理が最優先、次にモデルによる候補の絞り込み、最後にロールアウトによる評価、という多段構成）。今回の設計もこの既存の枠組みの中の「モデルによる候補評価」部分を改善するものと位置づけられる |
