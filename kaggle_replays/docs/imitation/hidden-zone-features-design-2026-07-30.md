## 2. 現在の入力の全内訳

方策ネットは 239次元入力・隠れ層32・出力1 の MLP（`policy_model.py`）。選択肢ごとにスコアを出して softmax する pointwise ランキング。

### 状態特徴 166次元（1つの判断の中で全選択肢に共通）

| 区分 | 次元 | 中身 |
|---|---:|---|
| 場のポケモン | 132 | 自分6枠 + 相手6枠 × 11特徴（`present / hp_ratio / remaining_hp / damage_counters / energy_count / best_attack_damage / can_ko_defender / min_energy_shortfall / has_ready_attack / attacker_score / is_likely_ko_next_turn`） |
| 自分の枚数 | 8 | 手札枚数、手札の内訳（ポケモン/トレーナー/エネの**枚数**）、山札枚数、サイド残り、トラッシュ枚数、ベンチ数 |
| 相手の枚数 | 5 | 手札枚数、山札枚数、サイド残り、トラッシュ枚数、ベンチ数 |
| 特殊状態 | 10 | どく/やけど/ねむり/マヒ/こんらん × 2 |
| 進行 | 7 | ターン、先攻か、サポート使用済み、スタジアム使用済み、エネ付け済み、逃げ済み、スタジアム有無 |
| 集約 | 4 | サイド差、ベンチ数差、自分の場のエネ総数、相手の場のエネ総数 |

**山札・サイド・トラッシュはすべて枚数1次元だけ。中身は無い。**
手札も自分の分すら「ポケモン何枚・トレーナー何枚・エネ何枚」の3分類までで、カードの正体は無い。

### 選択肢特徴 65次元 + カード埋め込み8次元（選択肢ごとに変わる）

`opttype_*`(18) / `seltype_*`(12) / 対象ポケモンの11特徴 / 対象カードの分類（ポケモン・グッズ・道具・サポート・スタジアム・基本エネ・特殊エネ・HP・たね/1進化/2進化・ex）/ ワザの打点・KO可否・エネ不足。

**カードの正体（1,268種 × 8次元の埋め込み）が入るのは、今スコアを付けている選択肢1個についてだけ。**
盤面のポケモンすら11個の数値に潰されていて、「これはアラカザールだ」という情報は入っていない。

## 3. API から実際に取れるもの

`cg/api.py` の実物:

```python
class Card:
    id: int       # CardData ID
    serial: int   # 試合内で一意
    playerIndex: int

class PlayerState:
    discard: list[Card]          # ← 中身が見える。両プレイヤーとも
    prize: list[Card | None]     # ← 伏せ札は None
    hand: list[Card] | None      # ← 自分は中身、相手は None
    deckCount: int               # ← 枚数のみ。中身のリストは無い
```

| ゾーン | 自分 | 相手 |
|---|---|---|
| トラッシュ | **中身が見える** | **中身が見える** |
| 手札 | 中身が見える | 枚数のみ |
| サイド | 伏せ札は `None`（サーチ等で判明した分のみ見える） | 枚数のみ |
| 山札 | 枚数のみ | 枚数のみ |

**自分の山札の中身は、引き算で求まる。** 60枚は自分で決めたものなので、そこから公開ゾーン（手札・トラッシュ・場・付いているエネ/道具・判明したサイド）を引けば「山札 ∪ サイド」の多重集合が出る。`serial` が試合内で一意なので厳密に追える。

ただし**山札とサイドは分離できない**。これはポケカ本来の不確実性そのもの（「キーカードがサイド落ちしているか」問題）。

## 4. 既に実装されている（重要）

**`sample_submission/ptcg_ai/hidden_information/` が上記をすべて計算している。** 新規実装は不要。

`OwnHiddenState`:
> 自分の60枚のうち、まだ「山札かサイドか」が確定していないカードを管理する。
> `_pool`: 「山札∪サイド」全体の多重集合。不変条件 `sum(_pool.values()) == deckCount + len(prize)` を毎回検算する。
> `_confirmed_deck` / `_confirmed_prize`: 山札サーチにより「山札確定」「サイド確定」と分かった枚数。

`marginals()` は `card_id -> {"deck": p, "prize": p}` を返す（超幾何分布。確定分は 1.0 / 0.0）。
`OpponentHiddenState` も同様の API を持ち、デッキ推定器（evidence 1枚で top-1 97%）と `archetype_card_pool.json` を使う。

`match_context.update(obs)` が毎ターン更新している。

### だが方策には繋がっていない

`match_context.get_own_state()` / `get_opponent_state()` の呼び出し元は**すべて `search_adapter.to_search_begin_kwargs`**、つまり**探索木の初期化（`search_begin`）専用**。

方策側は `policy_model.py` が `encoder.encode_state_from_state(obs.current)` を**引数なしで**呼んでいる。
`encoder` には `extra_features`（「将来の hidden_information 由来特徴などの差し込み口」というコメント付き）があるが、誰も渡していない。

**推定は毎ターン計算されていて、方策だけがそれを見ていない。**

## 5. 入れる先（2026-07-30 訂正）

**訂正前の記述は誤りだった。** 当初ここには「pointwise なので `softmax(score + c) == softmax(score)`、
全選択肢に共通の値は選択に一切影響しない。状態側に入れても数学的にゼロ」と書いていた。

真なのは**線形スコアラの場合**だけ。本番の `policy_model.py` は隠れ層を持つ MLP
（239 → 32(ReLU) → 1）で、状態特徴と選択肢特徴は隠れ層で相互作用する。実局面237件で測定:

| 測定 | 結果 |
|---|---|
| 選択肢間で ReLU の活性パターンが変わった判断 | **198/200** |
| 同じ選択肢群に別の実状態を当てて argmax が変わった割合 | **69.3%** |

**状態側（`extra_features`）に入れても方策は変わる。** ゼロではない。

ただし**選択肢側の方が筋がよい**ことは変わらない。「このカードは山札にあと何枚あるか」は
選択肢ごとに値が違うので、モデルが相互作用を学習するのを待たずに直接効く。
状態側に「山札の全構成」を入れる形だと、モデルが自分で「今スコアを付けている選択肢の
カードに対応する成分」を取り出す必要があり、学習が難しい。

なお `encoder.py` に**選択肢側の差し込み口は無い**。追加するには `_option_features()` の変更が要り、これは `sample_submission/` 配下（チーム管轄）。

## 6. 具体的な特徴案

選択肢が参照しているカードの `card_id` を X とする。X は選択肢ごとに違うので、以下はすべて softmax を生き残る。

| 特徴 | 出所 | 意味 |
|---|---|---|
| `remaining_unseen(X)` | `OwnHiddenState._pool` | X はあと何枚「山札∪サイド」に残っているか |
| `p_prized(X)` | `OwnHiddenState.marginals()[X]["prize"]` | X がサイド落ちしている確率 |
| `own_discard_count(X)` | `PlayerState.discard` を数える | 自分のトラッシュにある X の枚数 |
| `opp_discard_count(X)` | 同上（相手側） | **相手のトラッシュは公開情報**。相手が何を使い切ったかが分かる |
| `opp_expected_count(X)` | `OpponentHiddenState.marginals()` | 相手がまだ X を持っている見込み |

### なぜ効きうるか（プレイ上の意味）

- **サイド落ち判定。** 進化先が1枚しか入っておらず、それがサイドなら、そのポケモンを育てる選択の価値は消える。`p_prized(X)` はまさにこれ
- **サーチをいつ使うか。** 山札に目当てが残っているかで、サーチカードを今切るか温存するかが変わる
- **トラッシュを捨てる判断。** 残り枚数を見ずに捨てると、キーカードを全部落とす
- **相手のトラッシュ。** 相手が回復札・入れ替え札を使い切ったなら、詰め方が変わる。これは**完全な公開情報なのに一切使っていない**

## 7. 期待と、悲観すべき理由

### 期待できる根拠

今日の測定で、序盤の価値関数において `opp_active_best_attack_damage` が突出して効いていた（2位の2.5倍）。
これは局面の質ではなく**相手が誰かを言い当てる特徴**で、モデルが相手の正体を知る手がかりを
「相手のバトル場の打点」しか持っていないことの裏返し。ゾーン情報は別経路の手がかりになる。

### 悲観すべき根拠（こちらが強い）

| 事実 | 出所 |
|---|---|
| 特徴量の追加は「オフライン一致率は上がるが実戦勝率は上がらない」が**安定して不成立** | チーム測定（Tier1/Tier3 とも） |
| 我々の状態×行動の交互作用も同じ（一致率 +1.2pt p=0.33、勝率 −0.5pt p=0.81） | 我々の測定 |
| モデル容量は飽和（M32→M128 で +0.58pt） | チームの容量ablation |

**「選択肢側だから今度は違う」とは言えない。** 我々の交互作用実験も選択肢側だった。事前確率は低いと見るべき。

### 実装コストが大きい

エンコーダを変えると入力次元が変わるので、**既存の重み31個すべてと非互換**になる。
BC を 147,705 decision で学習し直し、その上で RL をやり直す必要がある。
今日 +11.3pt を出した SPEC_alakazam も作り直しになる。**その場での編集ではなく、並行実験として立てるべき。**

## 8. 検証計画（やるなら）

1. **オフライン一致率で採否を決めない。** 上表のとおり一致率と勝率が乖離する事例が繰り返し出ている
2. **主指標は凍結プールに対する勝率。** 現在の基準値は BC 0.421 / SPEC_alakazam 0.534（400試合×4相手）
3. **段階を分ける。**
   - 段階A: 自分側のみ（`remaining_unseen` / `p_prized` / `own_discard_count`）。相手推定の誤差が入らないので切り分けが利く
   - 段階B: 相手側を追加（`opp_discard_count` は公開情報なので誤差なし、`opp_expected_count` は推定誤差あり）
4. **共通乱数は使えない**ので対応なしの統計量で。1,200試合で ±2.8pt
5. **多重比較を数える。** 特徴の組み合わせを複数試すなら事前登録する

### 先に測るべき安い前哨戦

**「サイド落ちが実際にどれくらい起きているか」を上位リプレイで数える。**
キーカードのサイド落ちが稀なら `p_prized(X)` は死に特徴になる。
リプレイのデッキリストと公開ゾーンから計算でき、試合を回す必要がない。
これが数%しか起きないなら、この案全体の優先度が下がる。
