# 模倣学習を良くするための調査（2026-07-30）

> **状態: 一部が実測で更新済み** — 2026-07-30 の調査。以降の実測で決着した項目がある:
> 容量拡大は**否定**（hidden 32/64/128 で差なし）、BC 再学習は**有効**（+8〜11pt）。
> outcome weighting と consequence 特徴の数値は**旧データ・旧ラベル**のもので、
> 現行データでは未検証。最新は [bc-retrain-2026-08-03.md](bc-retrain-2026-08-03.md)。

Kaggle Discussion、競技プレイヤーの証言、ポケカのセオリーを調べて、我々の模倣学習の
どこに改善余地があるかを整理した。**調査と分析のみ。実装・検証は未着手。**

---

## 0. 先に訂正：状態特徴は選択に効く

このセッション中、私は何度も「pointwise なので `softmax(score + c) == softmax(score)`、
1つの判断の中で全選択肢に共通の値は選択に影響しない」と述べた。**これは誤りだった。**

真なのは**線形スコアラの場合**だけ。本番の `policy_model.py` は隠れ層を持つ MLP
（239 → 32(ReLU) → 1）で、状態特徴と選択肢特徴は隠れ層で相互作用する。

実局面 237件で測定した:

| 測定 | 結果 |
|---|---|
| 選択肢間で ReLU の活性パターンが変わった判断 | **198/200** |
| 同じ選択肢群に別の実状態を当てて argmax が変わった割合 | **69.3%** |

**状態特徴を足せば方策は変わる。** ただし「変わる」と「良くなる」は別で、
チーム・我々ともに特徴追加で実戦勝率が上がった例はまだ無い。

（`kaggle_replays/docs/imitation/hidden-zone-features-design-2026-07-30.md` §5 の記述もこの訂正の対象。）

## 1. Kaggle Discussion から

### フィールドの構成（"Top players' methods, revealed by 30,000 games", 73票）

思考時間と起動時間から手法を推定した分析。

- **フィールドの約半分は手書きルールベースか公開サンプルbotの複製**
- **首位は重いモデルを読み込み、かつ時間を使い切っている**（RL + 制限付き探索と推定）
- **首位以外の上位は探索を使っていないように見える**

### 実際に使われているモデルの大きさ（コメント欄の自己申告）

| 順位 | モデル | 起動時間 |
|---|---|---|
| 554位 | RL, **1.7M パラメータ** | 8秒 |
| 71位 | **700k パラメータ** + 不明瞭なときヒューリスティック探索 | — |
| 1299位 | **5M パラメータ**（最高1032位） | 40秒 |
| 13位 | 「ルールベース/探索と分類されたものの多くは実際は RL/RL+探索だと思う」 | — |

**我々のモデルは約 18,000 パラメータ**（全結合 7,713 + カード埋め込み 10,144）。
フィールドの実例より **40〜280倍小さい**。

### 探索と価値関数について（トピック作成者 Abhyuday, RL勢）

> 探索がうまく働くのは状態の価値を正確に判定できるときだけ。私の場合、価値ヘッドが
> 行動Aと行動Bのどちらが良いか判別できないので探索が効かない。素の方策の判断が
> しばしば最良の一つになっている。

**我々の測定と一致する。** 序盤の価値関数はマッチアップ識別とほぼ同等だった
（AUC 0.685 対 0.652、温度1.0では 0.634 対 0.620 で区間が重なる）。独立した裏付け。

### 報酬整形の実例（同スレッド）

デッキ切れ負けが多かったので `敗北 = -1.0` を `デッキ切れ負け = -1.5` に変えたら、
相手の方がデッキ切れするようになった、という報告。**特定の失敗モードに対する
狙い撃ちの整形は効く**という実例。

## 2. 競技プレイヤーの証言（Ryan Rumble 氏、実戦トップ1%）

同スレッドで、RL勢の質問に競技プレイヤーが詳細に回答している。要点。

### シークエンシング（順序）が最重要

> **汎用ドローを先に、特定サーチを後に。**

具体例（原文の要約）: 手札にポケパッドがあり、フェザンディオシのドロー3も使える。
先にポケパッドでドラクロアを取りに行くより、**先にドロー3を打つ**。ドロー3で
プッシュコール系（ふしぎなアメ相当のサーチ）を引ければ、目当ての3枚すべてを
確定で揃えられるから。

例外は「**thin to win**」。欲しいものが確定しているなら、逆に不要牌を先に処理して
山札を薄くし、目当てを引く確率を上げる。

### プライズマップ

「2-2-2」のように、**6枚のサイドをどう取り切るかを設計する**。相手はそれを崩しに来る
（スクープアップサイクロンで2サイドポケモンを引っ込め、1サイド盤面にして相手のプランを1ターン伸ばす等）。
デッキによっては「相手に7〜8枚取らせる」形を作る。

### 明確なミスとして挙げられたもの（機械的に判定可能）

1. **ワザのコストを超えてエネルギーを付ける**（逃げる予定や特定のメタ対策なら可）
2. **山札が0枚になるカードを使う**
3. **KO が取れるのに攻撃しない**

## 4. 見つかった改善余地（優先度順）

### (1) 検証済みで昇格されていない改善がある ★最優先

`sample_submission/results/2026-07-21_skillconc_summary.md`:

> **提出候補あり: `policy_weights_configC.json`（全データ+濃縮リウェイト）**
> オフライン: 上位≤200位 held-out で **+1.49pt**（0.6080 → 0.6229）
> オンライン: 現行本番とのミラー200試合で **58.0%、95% CI [51.1%, 64.6%]**（有意）

上位への重みを `rank<=20:8.0 / <=50:3.0 / <=200:1.5 / <=1000:1.0 / 1000超:0.5 / 不明:0.2`
と濃縮する構成。**昇格判断はユーザーに委ねられたまま止まっている。**

**しかし重みファイル `policy_weights_configC.json` は全ブランチに存在しない。**
レシピは残っている（`build_features.py --weight-scheme concentrated` → `train.py --out-weights`）ので再現は可能。

**留保**: n=200 で CI 下限が 51.1% と 50% すれすれ。しかも3構成から最良を選んでいる。
我々は n=200 で選んだ best が再評価で 5〜7pt 下振れる事例を**6件**踏んでいる。
**より大きい n で追試してから昇格すべき。**

### (2) モデル容量がフィールドより2桁小さい

我々 18k に対し、フィールドの実例は 700k〜5M。

チームの容量ablation は「M32→M128 で +0.58pt、飽和」と結論しているが、
- M128 でも約 **41k** パラメータで、フィールドの実例より1桁以上小さい
- 判定に使ったのは**オフライン top-1 一致率**。我々は一致率と実戦勝率が乖離することを
  繰り返し確認している（特徴追加の実験群）

**「飽和」の結論は、試した範囲と指標の両方の意味で、勝率については未検証。**
M512 / M1024 まで伸ばして**勝率で**測る価値がある。

### (3) 手番の進行状況を表現していない

競技プレイヤーが最重要に挙げたシークエンシングは「**同じターン内で何を先にやるか**」の問題。
だが我々の状態特徴に入っている進行情報は `turn / is_first_player / supporter_played /
stadium_played / energy_attached / retreated / has_stadium` の7つだけ。

**`State.turnActionCount`（このターンに何回行動したか）は API にあるのに使っていない。**
「このターンで既に何をしたか」の履歴も無い。

モデルは「ターンのどの段階にいるか」を知らないので、**「ドローを先、サーチを後」を
原理的に学習できない。** §0 のとおり状態特徴は選択に効くので、これは意味のある追加。

### (4) 機械的に判定できるミス指標がある

競技プレイヤーが挙げた3つは、いずれもコードで判定できる。

| ミス | 判定方法 |
|---|---|
| ワザのコスト超過エネ付け | 付け先の必要エネと現在のエネ数を比較 |
| デッキ切れを起こすカード使用 | `deckCount` とドロー枚数 |
| KO が取れるのに攻撃しない | 既存の `can_ko_defender` / lethal 判定 |

**これは勝敗を使わない密な診断指標になる。** 我々が既にやった「行動分布の逸脱」分析
（逃げ2.9倍・エネルギー付け0.59倍）と同じ枠組みで、上位勢と我々のミス率を比較できる。
n=400 で勝率が動かない変更でも、ミス率の悪化なら見える。

## 5. やらない方がよさそうなこと

- **探索の強化**: Abhyuday 氏の証言と我々の測定が一致して「価値関数が行動を判別できない」
  と言っている。価値関数を良くする方が先
- **状態特徴の闇雲な追加**: 効く仕組みはある（§0）が、チーム・我々とも実戦勝率が上がった例が無い

---

## 6. 提案する順序

1. **configC の再現と、大きい n での追試**（安い。レシピは残っている。効けば即効性がある）
2. **`turnActionCount` と手番内履歴の追加**（シークエンシングの前提。安い）
3. **ミス率の診断指標を作る**（勝敗より密。1と2の効果測定にも使える）
4. **容量を M512 以上まで伸ばして勝率で測る**（重い。1〜3の後）

いずれも**判定はオフライン一致率ではなく凍結プールに対する勝率**で行う。
現在の基準値は BC 0.421 / SPEC_alakazam 0.534（400試合 × 4相手）。
